# 草案 · 诊断日志与用户可导出的问题反馈包

> 状态：**已落地**。三个批次均已实现：`Core/Diagnostics/{AppLog,Redact,DiagnosticsBundle}.swift`，全部 `print` 与散落的 `os.Logger` 已收编，设置页「通用 → 诊断」提供导出诊断日志 / 打开日志目录 / 详细日志开关。常驻行为见 `技术实现.md` §15 与 `界面布局.md` §4.5.4；本文保留脱敏规则表、容量估算与取舍依据的追溯细节。
>
> 目标：用户遇到问题时，能在设置页一键导出一份**已脱敏**的诊断包发给开发者，开发者据此定位问题；在此之前需要先把项目里散落的 `print` 收编成统一、可落盘、可轮转、默认脱敏的日志门面。

## 1. 现状

### 1.1 已有的日志手段

| 手段 | 位置 | 问题 |
|---|---|---|
| `print()` | 约 45 处，集中在 `Core/AppState.swift`（31 处）、`Core/Usage/UsageService.swift`、`Core/Pricing/PricingCatalogStore.swift`、`Core/Usage/UsageLogWatcher.swift`、`Core/Quota/QuotaPersistenceCoordinator.swift` | 走 stdout/stderr，只有从 Xcode 运行时可见；正式打包的 App 里用户拿不到，也不落盘 |
| `os.Logger` | 4 个文件：`ClaudeDesktopAuth`、`AntigravityCredentials`、`ClaudeTokenRefresher`、`CodexTokenRefresher`，subsystem 统一 `com.cc-bar` | 覆盖面只有凭据与 token 刷新；额度拉取、用量扫描、定价、持久化全部没有。且 OSLog 字符串插值默认 `.private`，用户从 Console 导出多半只看到 `<private>`，只有 `CodexTokenRefresher` 显式标了 `privacy: .public` |

### 1.2 现有诊断快照的价值与问题

`AppState.logCredentialSummary()`（`Core/AppState.swift:1941`，在凭据加载后调用）与 `AppState.logQuotaSummary()`（`Core/AppState.swift:1969`，在额度刷新后调用）已经是结构化的整机状态快照，内容质量足够定位大部分问题：各 Provider 的凭据来源、plan、过期猜测、额度来源、各窗口剩余、失败原因。

两个问题：

1. 走 `print`，用户拿不到。
2. **直接打印 PII**：Codex / Claude / Antigravity 的 `email`、Codex 的 `account_id`、Cursor 的 `userID`。这些在当前「只有开发者在 Xcode 里看」的前提下可接受，一旦要让用户把日志发出来就不可接受。

token 本身没有进日志（只打 `hasAccessToken` 布尔值），这条现状是对的，必须保持。`docs/草案-CommandCode支持-设计方案.md` §不在日志输出 token 的约定也要升级为全局规则。

### 1.3 非沙盒前提

`CCBar.entitlements` 中 `com.apple.security.app-sandbox = false`。因此可以直接写 `~/Library/Logs/CCBar/`，也可以用 `Process` 调 `/usr/bin/ditto` 打包 zip，不需要安全作用域书签。

## 2. 目标与不做

### 2.1 目标

- 统一日志门面，替换全部 `print`，现有 `os.Logger` 站点收编为同一门面的一个输出端。
- 日志**默认脱敏**：不含 token、明文邮箱、账号 ID、对话内容、项目名、请求响应体。
- 落盘到 `~/Library/Logs/CCBar/`，带体积轮转上限，不无限增长。
- 设置页提供「导出诊断日志」：产出一个 zip，Finder 中选中，用户直接拖进 GitHub Issue 或发给开发者。
- 导出包内含一份环境摘要，覆盖版本、系统、各 Provider 状态、刷新配置、缓存文件健康度。

### 2.2 明确不做

- 不做任何**自动上报 / 遥测 / 崩溃上报**。日志只在本机，只有用户主动点导出才产出文件，且不由 App 发送。
- 不记录对话内容、prompt、模型输出、文件内容。本机用量扫描只记聚合计数（文件数、行数、耗时），不记具体路径与会话标题。
- 不引入第三方日志库（CocoaLumberjack / swift-log），自研一个约 200 行的门面即可，避免依赖与包体积。
- 不做日志查看器 UI。用户看日志用 Console.app 或文本编辑器，App 内不提供浏览界面。
- 不改变现有 `privacyMode` 设置的语义——那是**界面**打码开关，与日志脱敏是两回事；日志脱敏**无条件生效**，不受 `privacyMode` 影响。

## 3. 日志门面

### 3.1 类型与并发

新增 `Core/Diagnostics/AppLog.swift`。

调用点横跨三种并发域：`@MainActor`（`AppState`、`UsageService`）、`nonisolated final class ... @unchecked Sendable`（`PricingCatalogStore`）、`actor`（`QuotaPersistenceCoordinator`）。因此门面必须是 `nonisolated` 且线程安全，且**调用侧同步返回**（不能 `await`，否则要改所有调用点的上下文）。

沿用 `PricingCatalogStore` 已有的先例：

```swift
nonisolated final class AppLog: @unchecked Sendable {
    static let shared = AppLog()
    // NSLock 保护内存缓冲；真正写盘在私有串行 DispatchQueue 上
}
```

调用侧是静态便捷函数，同步、不抛错、失败静默：

```swift
AppLog.info(.quota, "codex snapshot source=remote plan=plus primary=87%")
AppLog.warn(.pricing, "decode failed, kept old cache: \(Redact.error(error))")
```

### 3.2 级别

| 级别 | 用途 | 默认是否落盘 |
|---|---|---|
| `debug` | 逐文件扫描明细、每轮调度决策 | 否（需打开「详细日志」） |
| `info` | 状态快照、刷新结果、生命周期事件 | 是 |
| `warn` | 降级但有兜底（保留旧缓存、回退全量扫描、限流退避） | 是 |
| `error` | 功能失败（拉取失败、写盘失败、解析失败） | 是 |

### 3.3 分类

对应现有 `print` 前缀，收敛为固定枚举，用作 OSLog category 与文件行中的字段：

`app`（生命周期、调度、更新检查）、`credentials`、`quota`、`usage`、`pricing`、`persistence`、`network`。

现有前缀映射：`[Credentials 凭据]` → `credentials`；`[Quota 额度]` → `quota`；`[UsageScan 用量扫描]`、`[CycleUsage 周期用量]`、`[UsageLogWatcher 日志监听]`、`[Usage 用量]` → `usage`；`[PricingCatalog 价格目录]` → `pricing`；`[quota-persistence]` → `persistence`；`[service-status]`、`[update-check]` → `app`；`[imported-codex]`、`[claude-cli-fallback]` → `credentials`。

### 3.4 双输出端

1. **文件**：`~/Library/Logs/CCBar/ccbar.log`，导出包的唯一来源。
2. **unified log**：继续用 `os.Logger(subsystem: "com.cc-bar", category: 分类)`，让开发者在自己机器上能实时 `log stream`。写入时**统一显式标注 `privacy: .public`**——消息在进入门面前已经脱敏过，OSLog 再打一次码只会让日志失去价值。

这条是关键决定：**脱敏责任在门面入口，不在 OSLog 的 privacy 标注**。

### 3.5 行格式

```
2026-09-13T10:22:31.412+0800  INFO  quota        codex snapshot source=remote plan=plus primary=87% weekly=64%
2026-09-13T10:22:31.480+0800  ERROR credentials  claude load failed: keychain item not found (errSecItemNotFound/-25300)
```

固定宽度的级别与分类列，便于 `grep`。时间戳带毫秒与时区偏移（用户与开发者不同时区时必须能对齐）。

## 4. 脱敏

### 4.1 两道防线

**第一道：调用点只写结构化安全字段。** 禁止把任意对象、`Error`、URL、响应体直接插值进日志。需要写敏感字段时必须过 `Redact`。

**第二道：门面出口的正则清洗（scrubber）。** 每条消息在写入前统一跑一遍模式匹配，命中即替换为 `<redacted:类型>`。这是兜底，防止将来新增调用点时漏掉第一道。

### 4.2 Redact 工具

新增 `Core/Diagnostics/Redact.swift`。

| 输入 | 输出 | 说明 |
|---|---|---|
| `Redact.account("a@b.com")` | `acct#3f9a2c11` | HMAC-SHA256(值, 本机 salt) 取前 8 位 hex。同一账号跨行、跨日一致，可用于判断「是不是同一个账号」和「账号有没有切换」，但不可反推 |
| `Redact.account(accountId)` / `(userID)` | 同上 | 与 email 用同一函数，同一账号的 email 与 id 会得到不同哈希，这是预期的 |
| `Redact.path(url)` | `~/.claude/projects/proj#8a1f/xxx.jsonl` | 家目录替换 `~`；`projects/` 下一级目录名（= 用户的仓库/项目名，可能是公司内部名）哈希；文件名保留后缀不保留主体 |
| `Redact.url(url)` | `https://api.openai.com/v1/xxx`（去 query 与 fragment） | query 里常带 token、account id |
| `Redact.error(error)` | `domain/code: localizedDescription`，再过 scrubber | 不打 `NSError.userInfo`（可能含 URL、失败请求体） |
| token / API key | 不提供函数 | 任何形态都不允许进日志。只允许写 `hasAccessToken=true/false` 这类布尔值；**不写长度、不写前缀、不写后四位** |

salt：首次运行生成 16 字节随机数存 UserDefaults（`ccbar.diagnostics.redactionSalt`），仅本机使用。用户重置后哈希会变，跨版本比对会断，可接受。

### 4.3 Scrubber 模式表

| 模式 | 替换为 |
|---|---|
| JWT：`eyJ[A-Za-z0-9_\-]{8,}\.[A-Za-z0-9_\-]+\.[A-Za-z0-9_\-]+` | `<redacted:jwt>` |
| Anthropic key：`sk-ant-[A-Za-z0-9_\-]{8,}` | `<redacted:key>` |
| OpenAI key：`sk-[A-Za-z0-9_\-]{16,}` | `<redacted:key>` |
| Codex 个人访问令牌：`at-[A-Za-z0-9_\-]{8,}` | `<redacted:key>` |
| `(?i)(authorization|bearer|api[-_]?key|token|secret|password)\s*[:=]\s*\S+` | `键=<redacted>` |
| 邮箱：`[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}` | `<redacted:email>` |
| 绝对家目录：`/Users/<name>` | `~` |
| UUID：`[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-…` | `<redacted:uuid>` |
| 长 hex / base64：`[A-Za-z0-9+/=_\-]{40,}` | `<redacted:blob>` |

最后一条最激进，会误伤一些正常长字符串；这是有意的取舍——**日志可读性让位于不泄露**。若误伤影响定位，再针对具体字段在调用点显式写成短字段。

正则集中在一处，配单元测试（见 §9）。

### 4.4 现有快照的改造

`logCredentialSummary` / `logQuotaSummary` 的信息结构保留，只替换敏感字段：

```
credentials  codex account=acct#3f9a2c11 plan=plus expiredGuess=false hasAccess=true hasRefresh=true
credentials  cursor account=acct#77b04e5a expiresAt=2026-10-01T00:00:00Z hasAccess=true
```

`email`、`account_id`、`userID` 全部换成 `Redact.account(...)`。plan、来源、过期时间、布尔标记保留明文——这些是定位问题的主要依据，且不是 PII。

## 5. 落盘与轮转

| 项 | 取值 | 理由 |
|---|---|---|
| 目录 | `~/Library/Logs/CCBar/` | macOS 惯例，Console.app 侧栏能直接看到，非沙盒可写 |
| 当前文件 | `ccbar.log` | |
| 轮转阈值 | 单文件 2 MB | |
| 保留份数 | `ccbar.log.1` ~ `ccbar.log.3` | 总上限约 8 MB |
| 写入时机 | 内存缓冲，满 64 条或距上次 flush 超过 5 秒时后台批量写；`applicationWillTerminate` 与导出前强制 flush | 避免每条一次 I/O，和 `docs/草案-性能与功耗等价优化方案.md` 已落地的写盘节流取向一致 |
| 写入线程 | 私有串行 `DispatchQueue(qos: .utility)` | 绝不在主线程做文件 I/O |

容量估算与落地结论：额度刷新最快 1 分钟档、每轮 `logQuotaSummary` 5~7 行、每行约 170 字节 → 无去重时约 1.7 MB/天，2 MB × 4 份只够覆盖 4 天出头。

但真正的问题不是体积而是**信噪比**：稳态下这些行 99% 完全重复，一天几千行相同内容会把真正的 error 埋掉。因此这条预留方案已经落地为正式约束（见 `技术实现.md` §15.1a）：按 Provider 缓存上一轮行文本，内容不变就不写，另加 1 小时心跳；同时未启用的 Provider 不再记失败行；重置时间从"还剩几分钟"改为绝对时间戳，否则相对值每轮都变会让去重完全失效。改完后稳态下几乎不写盘，8 MB 能覆盖的时间跨度远超原估算。

## 6. 导出诊断包

### 6.1 产物

`CCBar-diagnostics-yyyyMMdd-HHmmss.zip`，写入临时目录，然后 `NSWorkspace.shared.activateFileViewerSelecting([url])` 在 Finder 中选中。不弹 `NSSavePanel`（多一步选路径，对「快速发给开发者」这个场景是负担）。

打包用 `Process` 调 `/usr/bin/ditto -c -k --sequesterRsrc --keepParent`。

包内：

```
CCBar-diagnostics-20260913-102231/
├── summary.txt        环境与状态摘要
├── ccbar.log          当前日志
├── ccbar.log.1        轮转日志
├── ccbar.log.2
└── ccbar.log.3
```

### 6.2 summary.txt 内容

同样过一遍脱敏与 scrubber。

- **App**：版本（`MARKETING_VERSION`）、build、安装路径是否在 `/Applications`、是否 ad-hoc 签名。
- **系统**：macOS 版本、机型标识（`hw.model`）、架构、系统语言、当前时区。
- **配置**：`appLanguage`、`quotaInterval`、`usageInterval`、`menuBarWindow`、`floatingEnabled`、`privacyMode`、`autoCheckForUpdates`、各 Provider 启用 / 菜单栏 / 悬浮窗开关、各统计服务可见性。
- **账号**：每个 Provider 的凭据来源、`Redact.account(...)`、plan、过期猜测、最后一次错误（脱敏）。不含 email 明文。
- **额度**：每个 Provider 最近快照的来源、各窗口剩余百分比、重置时间、最后错误、当前是否处于 429 退避。
- **本地日志源**：`~/.codex`、`~/.claude/projects`、`~/.pi`、`~/.local/share/opencode/opencode.db` 是否存在、文件数量级（不列文件名）、最近修改时间。
- **缓存健康度**：`~/Library/Application Support/CCBar/` 下各 JSON 的存在性、字节数、修改时间、能否解码。不含内容。
- **最近一次扫描**：文件数、行数、新增条目数、不可读文件数、耗时。

### 6.3 导出前的确认

按钮点击后先弹 `NSAlert`（或 SwiftUI `.confirmationDialog`），中英文说明：

- 诊断包包含什么（版本、系统、设置、各服务的状态与错误、本地日志扫描统计）。
- 不包含什么（登录令牌、明文邮箱、对话内容、文件内容、项目名）。
- 提示用户发送前可以自己打开 `summary.txt` 看一眼。

这一步不能省。用户对「把日志发给开发者」的顾虑，只能靠明确告知消解。

## 9. 验收

**脱敏（单元测试，`CCBarTests`）**

- 给定含 JWT、`sk-ant-`、`at-`、`Bearer xxx`、邮箱、`/Users/nanvon/`、UUID、64 位 hex 的字符串，scrubber 输出**不含**任何原始片段。
- `Redact.account` 对同一输入稳定、对不同输入不碰撞（抽样）、输出不含原文任意 4 字符连续子串。
- `Redact.url` 去掉 query 与 fragment。
- `Redact.error` 对带 `userInfo` 的 `NSError` 不输出 `userInfo` 内容。

**落盘**

- 连续写入超过 2 MB 后发生轮转，`ccbar.log.3` 之后的旧文件被删除，目录总大小不超过约 8 MB。
- 关闭「详细日志」时 `debug` 行不落盘。

**导出**

- 点击导出后 Finder 选中 zip；解压得到 `summary.txt` + 至少 1 个日志文件。
- 用 `grep` 在整个解压目录中搜索本机真实邮箱、真实 access token 前 12 字符、真实项目名：**零命中**。这是最终验收项，必须人工执行一次。

**性能**

- 主线程无文件 I/O（Instruments 或代码审阅确认写入全在 utility 队列）。
- 1 分钟刷新档运行 1 小时，日志增量在预估量级（约 60 KB/小时）。

## 10. 分批

| 批次 | 内容 | 可独立交付 |
|---|---|---|
| A | `AppLog` + `Redact` + 落盘轮转 + 迁移全部 `print` 与现有 `Logger` + 脱敏单元测试 | 是。此时日志已可用，开发者可指导用户手动去 `~/Library/Logs/CCBar/` 取文件 |
| B | `DiagnosticsBundle` + 设置页 Diagnostics 组 + 导出前确认弹窗 | 是。这是面向用户的完整能力 |
| C | `verboseLogging` 开关 + 文档回写（技术实现 / 界面布局 / 产品需求 / README） | 是 |

## 11. 风险

- **脱敏漏网**：最大风险。缓解靠两道防线 + §9 的人工 grep 验收 + 「调用点禁止直接插值任意对象」的评审规则。新增日志调用点时，评审必须检查是否有裸 `\(error)`、裸 URL、裸路径。
- **哈希可关联性**：`acct#xxxx` 能让开发者判断「是否同一账号」，也意味着如果开发者另有渠道拿到同一 salt 下的映射就能反查。salt 只存本机、不随包导出，已阻断这条路径；但 salt 不导出也意味着**不同用户的哈希不可互相比对**，这是有意的。
- **日志写盘功耗**：缓冲 + 批量写已经把 I/O 降到约每 5 秒一次；若实测仍有影响，退化为只在 `warn`/`error` 与快照变化时写。
- **用户误发**：确认弹窗 + `summary.txt` 放在包的第一位、纯文本可读，用户能自查。
- **文件数量膨胀**：新增 3 个源文件需手工改 `project.pbxproj` 4 处，漏改会出现「本地 Xcode 能编译、CI 报 undefined symbol」之类的错位，改完需要一次 Debug 构建确认。
