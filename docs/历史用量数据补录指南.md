# 历史用量数据补录指南

给同样踩到「Claude Code 自动清理导致 cc-bar 用量缺一段」这个坑、且本机还装着 **cc-switch** 的用户（或帮他们操作的 AI）参考。不是产品功能，是一次性数据修复的操作手册。

## 1. 背景：为什么会缺数据

Claude Code 默认开启 `cleanupPeriodDays`（默认 30 天）本地清理策略，启动时自动删除 `~/.claude/projects/**/*.jsonl` 里超过这个天数的会话文件。cc-bar 的用量统计（`Core/Usage/ClaudeJSONLScanner.swift`）依赖重新扫描这些 jsonl，源文件一旦被删，对应日期的用量就再也算不出来——cc-bar 自己的缓存（`usage-rollup.json`）本质也只是这份扫描结果的持久化，不是独立备份，一样救不回来。

如果同一台机器上还装了 **cc-switch**（一个多客户端代理/切换工具，`~/.cc-switch/cc-switch.db`），它可能因为落盘更早、或本身就有独立的用量记录机制，保留了 cc-bar 已经丢失的那部分数据。这份指南就是怎么把 cc-switch 里的备份，转换成 cc-bar 认识的格式补回去。

## 2. 前提检查

开始之前先确认这几件事，任何一条不满足就不要往下做：

1. 用户确实装了 cc-switch，且 `~/.cc-switch/cc-switch.db` 存在（`sqlite3 ~/.cc-switch/cc-switch.db ".tables"` 能看到 `usage_daily_rollups` / `proxy_request_logs` 这类表）。
2. 已经跟用户确认过要不要做这件事、范围有多大——**不要**看到这份指南就自己判断"用户可能需要"然后擅自执行,数据来源、过滤规则、覆盖范围都应该和用户过一遍再动手（本项目协作规则里"改动前先确认"同样适用于数据变更,不只是代码变更）。
3. cc-bar 本体没有正在跑的扫描/写盘操作（避免和它自己的 `usage-rollup.json` 写入撞车）。

## 3. cc-bar 认的导入格式

补录文件只有**一个固定路径**，cc-bar 启动时和每轮用量扫描时都会自动按天去重合并，不需要额外配置（每轮扫描都合并是必需的：结构版本或 generationID 失效时会清空聚合器再全量重建，若只在启动时合并，重建后落盘的快照就会丢掉补录数据，详见《技术实现》§7.8）：

```
~/Library/Application Support/CCBar/imported-usage-claude-2026H1-gapfill.json
```

⚠️ 这个文件名是硬编码在 [ImportedUsageBackfill.swift](../Core/Storage/ImportedUsageBackfill.swift) 里的，**当前只支持这一个文件**。如果以后还要再补一批（比如又发现一段新缺口），做法是把新旧数据合并进同一份 JSON 里重新写一次，而不是新建第二个文件——除非先去改 `ImportedUsageBackfill.swift` 让它支持多文件。

文件内容是一个 JSON 数组，每一项对应 cc-bar 内部的 `UsageBucket` 结构（[UsageModels.swift](../Core/Usage/UsageModels.swift)），字段和编码规则必须精确匹配，否则 `JSONDecoder` 会静默解码失败（`ImportedUsageBackfill` 出于设计故意不报错，失败等同于文件不存在）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `app` | 字符串 | 固定 `"claude"`（这套机制目前只服务 Claude；Codex 同理需要类似东西时得单独设计） |
| `model` | 字符串 | Anthropic 官方模型 id,如 `claude-opus-4-7`；**不要**把中转商跑的第三方模型（deepseek / mimo / gpt 之类）混进来,即使它们在源数据里被标成了同一个 app_type |
| `speed` | 字符串 | 没有可靠速度档位信息时一律填 `"unknown"`，不要瞎猜 standard/fast |
| `day` | 数字 | **Apple 参考时间纪元秒数**（2001-01-01 00:00:00 UTC 为 0），代表用户本地时区那一天的 00:00。不是 Unix 时间戳，换算见下方脚本 |
| `inputTokens` / `outputTokens` / `cacheReadTokens` / `cacheCreationTokens` | 整数 | 原始 token 数，不要预先做任何倍率换算 |
| `costUSD` | **字符串** | 十进制字符串，如 `"5.531000"`；不是 JSON number,因为 cc-bar 用 `Decimal` 避免浮点精度问题 |
| `requestCount` | 整数 | 请求数 |
| `hasUnpricedUsage` | 布尔 | 只要源头有真实、可信的花费数字就填 `false`；如果这批数据的价格本身就不可靠/缺失，才填 `true` |

## 4. 具体步骤

### 4.1 确定 cc-bar 当前已经有哪些天的数据

不要凭感觉猜一个"分界日期"——实测中会出现零散的孤立幸存日（个别文件因为被后续访问刷新了 mtime 侥幸躲过清理），缺口不是一整段连续区间。必须逐天精确比对：

```python
import json, datetime

TZ = datetime.timezone(datetime.timedelta(hours=8))  # 换成用户实际时区
ref = datetime.datetime(2001,1,1, tzinfo=datetime.timezone.utc)

p = "~/Library/Application Support/CCBar/usage-rollup.json"  # 展开成绝对路径
d = json.load(open(p))
ccbar_days = set()
for b in d["buckets"]:
    if b.get("app") != "claude":
        continue
    utc_dt = ref + datetime.timedelta(seconds=b["day"])
    ccbar_days.add(utc_dt.astimezone(TZ).date().isoformat())
```

### 4.2 从 cc-switch 提取数据

cc-switch 的具体表结构可能随版本变化，先 `sqlite3 ~/.cc-switch/cc-switch.db ".schema"` 现查一遍，不要直接照抄下面的表名。截至本文撰写时（2026-07），用得上的两张表：

- `usage_daily_rollups`：按天 + 模型的聚合表,字段里已经有现成的 `date` / `model` / `request_count` / `input_tokens` / `output_tokens` / `cache_read_tokens` / `cache_creation_tokens` / `total_cost_usd`。
- `proxy_request_logs`：逐请求明细表,`created_at` 是 Unix 时间戳（秒），需要按用户本地时区转成日历日之后再聚合，不要直接用 SQLite 的 `date()`（那是 UTC 日期,容易和本地时区的 `usage-rollup.json` 对不上,产生一天的偏差）。

两张表通常是新旧两套统计机制的接续（比如老表在某天停止更新，新表接着往后记），先看两边各自的最大/最小日期,确认有没有断档或重叠。

**先看 `app_type='claude'` 下实际出现了哪些 `model`**，把真正的 Anthropic 模型和中转商跑的第三方模型（deepseek / mimo / gpt 等，虽然协议走的是 Claude 端点、被标成了同一个 app_type，但不是 Claude 用量）分清楚，逐一确认后再决定保留哪些、过滤哪些——这份名单必须和用户核对，不能自己瞎猜。

### 4.3 求缺口 = cc-switch 有的日期 − cc-bar 已有的日期

对每个 `(date, model)`，只在 `date not in ccbar_days` 时才纳入导入范围；`ccbar_days` 里已有的日期，哪怕只有一条孤立记录，也整天跳过、不覆盖、不合并、不叠加。

### 4.4 转换成 §3 的 JSON 格式并写盘

`day` 字段换算：

```python
local_midnight = datetime.datetime.strptime(date_str, "%Y-%m-%d").replace(tzinfo=TZ)
day_epoch = (local_midnight - ref).total_seconds()
```

`costUSD` 写成保留 6 位小数的字符串，其余字段直接照抄源数据整数值。写到 §3 那个固定路径。

### 4.5 配一份同目录的说明文件

文件名建议 `imported-usage-claude-2026H1-gapfill.README.md`（跟数据文件同名前缀），写清楚：数据来源（哪个工具、哪几张表）、导出时间、过滤规则（保留了哪些模型、剔除了哪些）、覆盖的具体日期范围、汇总数字（总请求数、总花费）。这份文件不是给程序读的，是给人（未来的你、或者接手的人）看的，务必写。本机可以直接参考同目录下已有的 `imported-usage-claude-2026H1-gapfill.README.md`（`~/Library/Application Support/CCBar/` 下，不在 git 仓库里，仅供参考格式，§6 是它的内容摘要）。

## 5. 边界：这套机制补不回来什么

- **只有用量和花费数字**（token 数、请求数、cost），**没有对话正文、工具调用明细、推理过程**。cc-switch 的这两张表本身就不存这些内容,巧妇难为无米之炊。
- 只覆盖 cc-switch 自己有记录的时间范围。cc-switch 数据库创建之前（`ls -la ~/.cc-switch/cc-switch.db` 看 birth time）的任何数据,这条路也补不回来,只能寄希望于 Time Machine / APFS 快照之类的系统级备份。
- 当前实现是**一次性、单文件**的，不是持续同步 cc-switch 的通用功能。如果用户想要"以后一直自动同步 cc-switch 数据"这种持续联动，那是完全不同的技术方案（要长期耦合 cc-switch 的私有表结构，并给它建一套独立的增量 watermark 和失效规则），跟这份一次性补录不是一回事，不要混着做。

## 6. 一次真实案例

2026-07-16，本机（见 [ImportedUsageBackfill.swift](../Core/Storage/ImportedUsageBackfill.swift) 头部注释）实际执行过一次：缺口是 2026-05-02 ~ 2026-06-16 之间的 38 个不连续日期，74 条（天+模型）记录，过滤掉了 deepseek / mimo 系列非 Claude 模型后，总请求数 9098，总花费 $853.83。可以直接读那份 `.README.md` 当模板抄。
