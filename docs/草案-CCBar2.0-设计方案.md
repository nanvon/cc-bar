# CCBar 2.0 设计方案

> 状态：待评审、未实施。保存本方案不代表已确认全部功能范围或授权实施。  
> 编写日期：2026-09-08。  
> 分析基线：仓库 v1.0.55 当前代码与文档；本次分析未运行构建、测试或真机功耗测量。  
> 定位：可靠保存历史用量，按项目分析成本，并让后台开销随新增数据量增长。

用户能直接感受到三个变化：工具清理日志后历史仍可查看；可以知道一个项目在不同工具上消耗了多少；历史积累越来越多时，扫描与统计页面仍保持轻快。

本文是一份可继续拆成设计文档和实施任务的方案。新增部分均为建议设计，实际产品现状仍以 [产品需求.md](产品需求.md)、[技术实现.md](技术实现.md) 和当前代码为准。

## 一、版本目标与范围

建议将 2.0 收敛为四项核心交付：

| 核心交付 | 用户得到什么 | 主要技术工作 |
|---|---|---|
| 可靠的历史存储 | 升级、重算、日志清理后，已有历史不会轻易消失 | SQLite、迁移、事务、恢复机制 |
| 项目分析 | 跨工具查看同一项目的用量与费用构成 | 项目映射、聚合查询、详情下钻 |
| 可解释的费用 | 分清实际扣费、估算、未定价和历史汇总 | 费用来源、价格版本、覆盖范围 |
| 大数据量与低功耗优化 | 后台减少无关扫描，统计页减少重复计算 | 分来源采集、局部更新、查询分页 |

小时趋势作为数据层支持后的扩展功能，可以纳入 2.0 后半程。预算提醒、额度通知和多设备同步暂不成为首发依赖，避免拉长基础升级的验证周期。

成功标准应优先看：

- 升级前后的历史汇总能够对账。
- 原始日志删除后，已保存历史仍可查询。
- 重算失败时，仍能展示此前的有效结果。
- 一个来源新增日志，不再必然扫描其他全部来源。
- 单页查询不需要加载全部历史明细。

## 二、产品设计：保持轻量入口，把分析能力放到主窗口

菜单栏、Popover 和悬浮窗继续负责快速查看额度与今日／本周用量。新能力主要进入主窗口，避免常用入口变复杂。

建议主窗口保留现有页面，并新增“项目”：

| 页面 | 职责 | 2.0 变化 |
|---|---|---|
| 概览 | 所选范围的总体用量 | 统一查询快照、费用依据、模型筛选 |
| 项目 | 跨工具的项目用量分析 | 新增 |
| 对话 | 定位高消耗会话 | 真正分页、关联项目、可选用量事件详情 |
| 额度时间线 | 官方额度变化 | 首版保持既有范围 |
| 周期 | 当前真实额度周期的用量 | 使用新查询层，保持当前统计口径 |

### 项目页的具体形态

左侧显示项目列表，支持按最近活跃、费用和 Tokens 排序，以及项目名称搜索。每项展示项目名、最近活跃时间、工具构成和范围内费用。

右侧项目详情包括：

1. 所选范围的 Tokens、费用、请求数估算和活跃天数。
2. 用量趋势，支持 Tokens／费用切换。
3. 按工具、模型、Standard／Fast 的费用构成。
4. 缓存读取与写入 Token、缓存命中比例。
5. 范围内费用最高的对话。
6. 导出当前范围数据。

图表点击某天后，可以查看对应对话；点击对话进入现有对话详情，避免重复开发两套详情。

### 项目归属规则

不能仅凭目录名相同就合并项目。建议区分：

- 原始项目：日志中识别到的路径和项目线索。
- 展示项目：用户在 CCBar 中看到的项目实体。
- 映射关系：一个展示项目可以关联多个原始路径。

这样可以处理 worktree、项目迁移和不同工具使用不同路径的情况。

自动识别先提供合并建议，用户确认后建立映射。取消映射时恢复原有归属，不修改原始用量记录。继续遵循当前受保护目录策略，不为确认项目存在而遍历可能触发系统授权的目录。

Cursor 当前缺少可靠的本机会话关联依据，先进入总体统计，不强行分摊到项目。

## 三、数据设计：保存可追溯用量，再生成展示结果

当前 `UsageEntry` 只在内存中流转，落盘主要保留日、对话和周期聚合。2.0 建议增加持久化的“用量事实”。

这里的事实是来源能够可靠提供的用量记录，不保证每条都对应一次完整请求。

建议的数据关系如下：

| 数据实体 | 主要内容 | 设计重点 |
|---|---|---|
| 数据源与身份 | 工具、来源位置、已知账号或未知身份 | 未知账号不能默认归到当前登录账号 |
| 扫描进度 | 文件身份、偏移、解析上下文、解析器版本 | 与本轮数据更新一起提交 |
| 用量事实 | 来源标识、时间、会话、模型、速度、Token 拆分 | 可去重、可更正、可追溯 |
| 会话档案 | 标题、来源路径、项目线索、开始结束时间 | 不保存对话正文 |
| 项目与映射 | 展示项目、路径别名、人工归属 | 可撤销，不改原始事实 |
| 费用评估 | 费用依据、价格版本、分项金额、缺价状态 | 与用量事实分离 |
| 历史汇总 | 旧版本迁入的日桶、对话桶等 | 明确其粒度和覆盖范围 |
| 查询聚合 | 小时、日、项目、对话、周期统计 | 可从事实重建的派生数据 |

实际建表时可以根据访问模式合并部分实体，不必机械地一项对应一张表。

### 身份、时间与金额的约束

- 用量来源工具、模型厂商、计费账号是不同维度，分别建模。
- 日志没有可靠账号信息时保留“未知”，不依据当前登录状态补写历史。
- 新记录保存真实时间戳，按用户所选时区生成日期分组。
- 旧日桶只有日期信息时，保留原分桶语义，不能伪造小时级时间。
- 金额沿用精确十进制语义；数据库表示方式需要明确精度、舍入与溢出规则，不能直接转成普通浮点数。
- Cursor 官方计量与本地模型估算分别保存来源依据。

### 去重与更正

当前跨文件去重集合存在保留数量上限。新设计采用持久化事件键，但事件键必须由各解析器分别定义。

需要覆盖：

| 场景 | 预期行为 |
|---|---|
| 相同日志再次扫描 | 不增加用量 |
| 文件移动到归档目录 | 不重复计费 |
| fork／clone 重放父会话记录 | 按当前来源语义去重 |
| 文件截断后重写 | 重新解析，但已存在事实不重复累计 |
| 相同事件出现更完整的数据 | 更正原事实，并更新受影响聚合 |
| 来源缺少稳定 ID | 使用来源专属规则，记录识别局限 |

数据库唯一约束负责兜底，解析器仍负责判断哪些记录代表同一事实。

对于更正，不能只做“忽略重复插入”。应比较新旧内容，将受影响日期、会话和项目标记为需要重算，或应用可靠的差量更新。

## 四、SQLite 升级：优先替换用量存储

建议首轮把以下内容纳入数据库：

- 扫描进度与去重信息。
- 本地用量事实。
- 日、对话和周期用量聚合。
- 历史汇总与项目映射。
- 费用评估版本。

凭据继续使用现有凭据体系；简单设置继续使用 UserDefaults。额度快照等小型 JSON 可以暂时保留，避免同时迁移全部状态。

### 写入方式

采用单一数据库写入服务，一批扫描结果对应一次受控事务：

```text
读取新增日志
→ 解析和规范化
→ 开启事务
→ 插入或更正用量事实
→ 更新受影响聚合
→ 更新去重信息和扫描进度
→ 提交事务
→ 通知界面刷新
```

事务提交失败时，不推进持久化扫描进度。下轮可以重新读取相同数据，由事件键保证幂等。

全量扫描采用有界批次，避免把全部解析结果积存在内存中；批次边界必须与安全的扫描进度对应。

SQLite 同时只允许一个写事务，采用单写入服务比多个模块自行抢写更容易控制。参见 [SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)。

### 读取方式

查询层提供面向界面的接口，例如：

- 查询某范围的概览。
- 查询项目列表的一页。
- 查询某项目的趋势与构成。
- 查询某对话的完整生命周期统计。
- 查询指定时间范围的用量事件。

UI 不直接拼 SQL，也不持有全部历史数据。

索引按实际查询设计，优先覆盖时间、会话、项目映射和来源事件键。不要为所有字段建立索引，否则每次采集都会增加写入成本。

WAL、checkpoint、缓存大小等参数在代表性数据集上确定，不先套固定“性能最佳参数”。参见 [SQLite WAL 文档](https://www.sqlite.org/wal.html)。

## 五、迁移方案：旧历史必须先保住

这是整个大版本风险最高的部分，应单独验收。

### 迁移步骤

| 步骤 | 行为 | 失败处理 |
|---|---|---|
| 预检 | 检查旧文件版本、代次关系、可读性和磁盘空间 | 保留旧版本数据，给出可操作错误 |
| 创建新库 | 在独立位置创建数据库并记录迁移状态 | 不影响现有文件 |
| 导入旧汇总 | 按原有粒度导入日／对话／周期数据 | 事务回滚，可重试 |
| 导入扫描上下文 | 只复用经验证兼容的进度和解析状态 | 不兼容部分进入受控重建 |
| 核对 | 按来源、日期、模型、速度比较 Tokens 与费用 | 不一致时不切换 |
| 切换 | 新库标记为可用，下次启动恢复该状态 | 保留旧文件供回退 |
| 补充明细 | 对仍存在的日志按范围补建事实 | 不把新明细重复加到旧汇总 |

### 旧汇总与新明细共存

不能把迁入的日桶与重新扫描的事件直接相加。

建议建立覆盖记录：某个范围当前由旧汇总提供，还是已由完整明细替代。范围需要足够细，具体由来源和现有聚合键决定。

只有确认该范围扫描完整、结果通过核对，才能切换读取来源。若只能找到部分旧日志，继续保留原汇总；局部明细可以用于查看，但不能宣称覆盖了整段历史。

日聚合、对话聚合和周期聚合属于不同投影，不能相互相加。

### 迁移后的重算

将“重新计算用量”拆成内部不同操作：

- 重新生成查询聚合：从已保存事实计算，不访问原始日志。
- 重新计算估算费用：依据指定价格版本计算。
- 重新解析来源：仅在解析规则修正等场景使用原始日志。

界面可以继续保持简洁，但操作结果应明确说明影响范围。

重算在新代次中进行，完整成功后替换当前有效结果。日志缺失或读取失败时保留原结果，并标记无法更新的范围，避免先清空再尝试恢复。

## 六、费用设计：保存原依据，允许明确地重新评估

建议费用模型区分四种情况：

| 类型 | 展示方式 | 重算规则 |
|---|---|---|
| 官方计量金额 | 官方扣费／计量 | 仅由该来源的新结果更正 |
| 模型价格估算 | API 等值估算 | 可按选定价格版本重新计算 |
| 未定价用量 | 展示已知金额，并说明部分未定价 | 获得可靠价格后可补算 |
| 旧汇总金额 | 历史汇总 | 缺少明细时保留原值 |

同时保留两个概念：

- **原记录费用**：当时采集或估算得到的值。
- **重新评估费用**：用户选择某个价格版本后得到的新结果。

默认使用哪个作为主展示口径，需要在详细交互设计时确定；建议默认延续原记录费用，避免更新价格目录后历史数字静默变化。

Overview 不必增加很多字段。金额旁提供紧凑提示，详情页再显示来源、价格版本、未定价范围。

预算功能应在这套口径稳定后加入，否则“项目超预算”可能实际只是 API 等值估算超过阈值。

## 七、性能与功耗方案

建议分成三条独立验证的工作线，并补充系统电源状态策略。

### 后台采集

第一步把全局变化标记改为分来源标记：

```text
Claude 有变化 → 扫描 Claude
Codex 有变化 → 扫描 Codex
Pi 有变化 → 扫描 Pi
OpenCode 有变化 → 查询 OpenCode 增量
```

首轮先做到来源级别。文件级候选队列放到后续，避免同时引入事件丢失、文件移动、根目录重建等复杂性。

必须保留：

- 事件监听失败时的扫描兜底。
- 定期完整核对。
- 新来源目录出现后的发现机制。
- 扫描期间新变化的下一轮处理。
- 手动刷新与强制重建的明确语义。

统计服务的显示开关继续只影响展示，不自动停止历史采集。

### 数据处理与写盘

- 每批仅更新发生变化的事实和聚合。
- 避免为每次新增记录复制全部历史数组。
- 聚合计算移到后台服务。
- 批量提交，控制事务大小与频率。
- 无变化时不发布新的数据版本，减少 SwiftUI 更新。
- 全量导入使用有界缓冲和可恢复进度。

数据库本身也会产生额外索引和日志写入，最终应比较实际写入字节和 CPU 时间，不能只比较 JSON 文件数量。

### 前台查询

Overview 一次查询生成共享结果，KPI、模型构成、趋势等使用同一份快照。缓存键包含：

- 数据版本。
- 日期范围和粒度。
- 服务、项目、模型筛选。
- 费用口径。
- 影响日期分组的时区等条件。

对话列表改为查询分页，不再先生成全部排序结果再截取前 200 条。

异步查询增加取消或版本检查。用户快速切换范围时，旧结果不能覆盖新选择。

### 系统电源状态

在当前锁屏降频基础上增加自动策略：

| 状态 | 建议行为 |
|---|---|
| 正常使用 | 按现有设置刷新 |
| 低电量模式 | 延后非紧急历史补拉，减少扫描并发 |
| 温度压力较高 | 暂缓全量重建等重任务 |
| 用户主动查看或刷新 | 优先完成当前可见范围，仍遵守限流 |
| 恢复正常状态 | 合并恢复任务，避免积压任务同时启动 |

Apple 提供电源和温度状态通知，适合据此调整后台工作。参见 [Apple 电源状态文档](https://developer.apple.com/documentation/xcode/responding-to-power-notifications)。

有限并发刷新 Provider 可以缩短等待，但要单独评估。它主要改善响应速度，不自动视为功耗优化。

## 八、架构拆分方式

建议保持单进程，围绕职责逐步拆分：

| 模块 | 负责 | 不应承担 |
|---|---|---|
| 额度服务 | 账号刷新、快照、限流和错误状态 | 用量历史查询 |
| 采集协调器 | 来源变化、扫描调度、批次提交 | SwiftUI 展示逻辑 |
| 来源解析器 | 将日志转成规范化记录 | 直接修改 UI 或跨来源推断 |
| 数据库存储 | 事务、迁移、进度、事实保存 | 产品筛选规则 |
| 统计查询服务 | 聚合、分页、查询缓存 | 凭据读取和网络续期 |
| 界面状态 | 当前页面数据、选择和加载状态 | 全历史数据处理 |

`AppState` 继续作为应用入口的协调对象，逐步减少业务执行职责。无需先完成一次大规模“拆文件重构”才能开始功能开发。

新增接口应通过替换一个真实调用链验证价值，避免先搭一套暂时没有消费者的通用框架。

## 九、验收方案

数据库升级应同时验证正确性、恢复能力和性能。

| 类别 | 必须覆盖的场景 |
|---|---|
| 迁移对账 | 多来源、多模型、Fast、缺价、历史补录、不同旧缓存版本 |
| 幂等 | 同一批数据重复导入、文件归档移动、fork 重放 |
| 更正 | 相同事件字段更新、解析规则修正 |
| 历史保护 | 原始日志部分或全部删除后升级、重算 |
| 故障恢复 | 事务失败、迁移中断、重算中断、磁盘空间不足 |
| 时间边界 | 跨日、跨月、夏令时、时区变化、额度重置边界 |
| 身份隔离 | 账号切换、未知身份、项目映射变化 |
| UI 一致性 | 快速切换筛选、翻页期间数据更新、旧查询晚到 |

性能使用同一份日志快照、相同设置和相同设备比较：

- 空闲常驻。
- 单工具连续追加。
- 多工具同时追加。
- 大历史库冷启动。
- 首次导入与全量重建。
- 概览切范围、项目搜索、对话翻页。

记录 CPU 时间、内存峰值、磁盘读写、唤醒次数、查询延迟和界面卡顿。具体数值目标在基线测量后制定；先设结构性要求，例如“查询一页不读取全表”“单来源变化不启动其他正常来源扫描”。

现有等价测试可以复用，但迁移与崩溃恢复必须增加专门用例。

## 十、实施顺序与发布控制

建议按依赖拆成以下批次，每批都能独立审阅：

| 批次 | 工作 | 进入下一批的条件 |
|---|---|---|
| A：基线与查询优化 | 性能指标、Overview 共享查询结果 | 现有结果等价，收益可测 |
| B：分来源采集 | 来源变化标记、独立扫描计划 | 不漏扫、不重计，兜底有效 |
| C：数据库基础 | 表结构、事务写入、事件身份、迁移原型 | fixture 对账和中断恢复通过 |
| D：历史迁移与切换 | 旧汇总导入、覆盖管理、回退 | 有缺失日志的真实规模样本也能迁移 |
| E：查询接入 | Overview、对话、周期切到新查询层 | 与旧口径对账，分页和性能达标 |
| F：项目功能 | 项目映射、详情、下钻、CSV | 跨工具统计准确，映射可撤销 |
| G：费用解释与收尾 | 费用依据、安全重算、诊断、文档 | 历史保护与用户操作链完整 |

A、B 可以先通过 1.x 小版本发布，降低 2.0 同时引入的变化数量。数据库切换应先做小范围试用，重点收集迁移失败、数据差异和性能退化。

**2.0 首发取舍：优先完成可靠迁移、安全重算、项目分析和费用解释。** 小时趋势在数据基础稳定后加入；提醒、预算、多设备同步放到后续，避免它们阻塞核心版本交付。
