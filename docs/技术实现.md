## 1. 技术栈

| 层 | 选择 | 备注 |
|---|---|---|
| 语言 | Swift（`SWIFT_VERSION = 5.0` 语言模式 + `SWIFT_APPROACHABLE_CONCURRENCY`、`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`） | 默认 MainActor 隔离，跨隔离域的类型显式标 `nonisolated` / `Sendable` |
| 工程 | Xcode `ccbar.xcodeproj` | 单 target，标准 macOS App |
| UI | SwiftUI 主、AppKit 辅 | 菜单栏 label / 悬浮窗 panel 走 AppKit |
| 最低系统 | macOS 14 Sonoma+ | 依赖 `MenuBarExtra(.window)`、`@Observable`、`SMAppService` |
| 存储 | UserDefaults + JSON 文件 | 自身不建库；只读打开 Cursor / OpenCode 的 SQLite（系统自带 `SQLite3`） |
| 网络 | `URLSession` async/await | 标准库，无第三方依赖 |
| 图表 | `Charts`（SwiftUI） | 统计 tab 的日 / 周 / 月柱状图与 Timeline 折线 |

整个工程零第三方依赖；钥匙串通过命令行 `security` 访问，避免 Keychain Services API 的多次授权弹窗。

## 3. 应用入口与窗口组合

`CCBarApp.swift` 组装三个 Scene：

1. `MenuBarExtra(.window)`：label 是自绘 NSImage 包装；content 是 `PopoverRootView`。`.task` 内执行 `appState.bootstrap()` 并把 `FloatingPanelController` 与 AppState 绑定，再根据设置同步显示。
2. `Window("CCBar", id: "main")`：主窗口，内部 `MainWindowRootView` 用 TabView 切「统计 / 设置」。
3. `Window("Welcome", id: "onboarding")`：引导窗口，`fixedSize` 禁缩放。

`AppCommands` 通过 `CommandGroup` 注入全局快捷键：

- `⌘,` → 打开主窗口并切到设置 tab。
- `⌘1` → 打开主窗口并切到统计 tab。
- `⌘R` → 调用 `appState.refreshNow()`。

`AppDelegate` 启动时设 `NSApp.setActivationPolicy(.accessory)`，让进程默认不出现在 Dock。冷启动（含 `SMAppService` 开机自启、Dock / 应用程序 / Launchpad / Raycast 手动启动）一律静默，只驻留菜单栏，不自动打开主窗口；用户点 Dock 图标触发 `applicationShouldHandleReopen` 时，通过安装在 `MenuBarLabelRoot` 的 SwiftUI handler 调用 `openWindow(id: "main")`，并先把 `mainTab` 设为 `.stats`；handler 未安装时先记录 pending，避免丢失事件。首次启动由 Onboarding 接管。`MainWindowRootView` 在 `onAppear` / `onDisappear` 里把策略切到 `.regular` / 切回 `.accessory`：只有主窗口（统计 / 设置）打开期间才显示 Dock 图标，Popover 不受影响。

## 4. 全局状态：`AppState`

`@Observable @MainActor`，单例方式由 `CCBarApp` 持有并通过 `.environment` 注入。核心字段：

- 凭据 / 身份：`codexAccount` / `claudeAccount`。
- 额度：主服务统一存于 `primaryQuotaStates[QuotaApp]`，Codex / Claude 计算属性保留为兼容入口；来源为 `api` / `local` / `cache` / `cliFallback`。
- 刷新状态：`QuotaRefreshState`（`lastSuccessAt`、`lastAttemptAt`、`backoffUntil`、`lastError`、`inFlight`、`source`）。
- 显示设置：`SettingsStore.providerDisplaySettings[QuotaApp]` 统一保存全局 / 菜单栏 / 悬浮窗开关；首次读取时迁移旧 Codex / Claude UserDefaults key。统计页服务开关走独立的 `SettingsStore.usageServiceVisibility[UsageApp]`（本地服务默认全开，Cursor 默认关闭，JSON 持久化到 `ccbar.settings.usageServiceVisibility.v1`）：过滤只发生在展示层（`StatsView.filteredBuckets` 等），扫描 / 聚合 / 入库仍全量，重新开启后历史照常出现。

  展示层读的是 `isUsageServiceEffectivelyVisible(_:)` = 用户偏好 && 运行时账号可用性，而不是偏好原值。Cursor 没有本地日志，账号消失（卸载 / 退出登录）后远端缓存不再更新，继续展示只会留下一条空服务行；`SettingsStore.cursorAccountDetected` 由 `AppState.cursorAccount` 的 `didSet` 同步（运行时字段，不持久化，乐观初值 `true` 以避开启动瞬间的空窗闪烁），账号恢复后统计行自动回来，**偏好本身始终不被改写**。设置页的 Toggle 与 `AppState.refreshQuotas` 的刷新计划刻意仍读偏好原值 `isUsageServiceVisible(_:)`——前者要让用户看到自己真实的勾选状态，后者若改读 effective 会在账号丢失时把刷新链路一并关掉，导致账号再也检测不回来。
- 今日花费：`codexTodayCost` / `claudeTodayCost` / `piTodayCost` / `opencodeTodayCost`，由 `UsageService.publishTotals()` 写入（Pi / OpenCode 无订阅额度，仅用于 Popover 今日花费合计）。
- UI 协调：`mainTab`（统计 / 设置）、`shouldShowOnboarding`。
- 子系统：`usageService`、`scheduler`、`quotaCache` 内存副本、Claude CLI 兜底冷却 `claudeFallbackBackoffUntil`。

关键方法：

- `bootstrap()`：只执行一次；按顺序加载 quota 缓存 → `UsageService.bootstrap` → 读 Codex 凭据 → 必要时弹 Keychain 引导 → 读 Claude 凭据 → 决定是否展示引导 → 启动 Scheduler → 触发首次 JSONL 扫描（异步不阻塞）→ 启动 7 秒后触发一次额度刷新（异步不阻塞）。
- `refreshQuotas(reason:)`：每次刷新(手动 / Scheduler 定时)按 `QuotaRefreshPlan`（由当前 Provider 开关与可见导入账号一次性构造）只刷新已启用的主 Provider 与可见导入账号；关闭 Codex / Claude 后不再进入对应凭据、token 与额度链路。`loadCodex` / `loadClaude` / `loadAntigravity` / `loadCommandCode` 内部比较 `accountId` / `email` / `token`，发现身份变化(例如 cc-switch 外部切换了账号)时清掉旧的额度快照与磁盘缓存，避免出现"新账号 + 旧额度"的错配；对于本地无邮箱但由服务端回填身份的凭据（如 Codex PAT、Command Code、Antigravity jetski），同一令牌未变时沿用上次回填的身份，避免误判账号切换导致清空旧快照与 UI 闪烁。可见导入 Codex 账号仍按自身设置独立调度，且只有主 Codex 启用时才可能与主账号镜像。
- `applySettingsChange()`：设置项变化后立即把新间隔灌进 Scheduler。

刷新前置校验在 `beginCodexRefresh` / `beginClaudeRefresh` 中：检查 `inFlight`、`backoffUntil`、周期性触发的 60s 最小间隔。成功后 `storeXxx` 只更新内存快照并标脏持久化文件；`refreshQuotas` / `bootstrap` / 设置操作末尾把标脏文件以不可变 snapshot 一次性提交给 `QuotaPersistenceCoordinator`（actor），编码与原子写移出 MainActor，同一文件一轮最多写一次；coordinator 串行执行并合并写入期间到达的新快照，保证后发的新版本不被较晚完成的旧写入覆盖。失败走 `markXxxFailure`，遇 429 设置 10 分钟退避。

## 5. 凭据读取

### 5.1 Codex

`CodexAuth.load()` 优先读 `$CODEX_HOME/auth.json`（未设置 `CODEX_HOME` 时回落 `~/.codex/auth.json`），解析 `tokens.access_token` / `refresh_token`，再用 `JWT.decode` 解 `id_token` 的 payload 拿邮箱、`chatgpt_plan_type`、`account_id`。

**personal access token 形态**：当 auth.json 没有可用 `tokens.access_token`、但有顶层 `personal_access_token`（形如 `{"OPENAI_API_KEY": null, "personal_access_token": "at-..."}`，即在 ChatGPT Team/Enterprise 后台「访问令牌」创建的 Codex 工作区访问令牌）时，`CodexAuth.load()` 把它当 access_token 返回，并置 `CodexAccount.isPersonalAccessToken = true`。该令牌是不透明字符串、无 JWT、无 `exp` / `refresh_token`：

- 取数时跳过 `CodexTokenRefresher`，直接拿令牌当 Bearer 打 `wham/usage`，不发 `ChatGPT-Account-Id` header（令牌已绑定账号）。
- 身份（`email` / `plan_type` / `account_id` / `user_id`）本地解不出，由 `wham/usage` 响应回填到 `codexAccount`；重读 auth.json 时令牌不变则沿用上次回填，`codexIdentityChanged` 对 PAT 改用 access_token 本身判定账号切换。

`CodexTokenRefresher.ensureFreshAccessToken`：当 JWT `exp` 剩余 < 300s 时 POST 到 OpenAI OAuth token 端点（grant_type=refresh_token，client_id 用 Codex CLI 公开 ID），成功后原子写回 `auth.json`。（PAT 账号不走此路径。）

**Codex 侧保留刷新，但装了三道防撞。** OpenAI 同样对 refresh_token 做重用检测（`refresh_token_reused`），并发刷新会把有效登录搞掉：

1. **进程内串行 + 去重**：`Coordinator` actor 按 `WriteBack.coordinationKey`（`auth.json` / `imported:<id>`）分键维护 `inFlight` Task。AppState 有 4 个入口会调 `ensureFresh*`，合并成一次请求；不同导入账号各自独立，不会互相合流。
2. **发请求前重读存储**：`peekStored(writeBack:)` 再读一次 `auth.json` / `ImportedCodexStore`。若 `codex` CLI 已自行轮换过且新 access_token 还新鲜，直接采用不发请求；即便仍过期，也用盘上最新的 refresh_token 去刷，不拿陈腐副本撞重用检测。
3. **写回失败不吞掉**：此时服务端已经轮换、旧 token 作废，写回失败就意味着盘上留着废票、下次启动登录失效。`persist` 重试一次，仍失败则记 `error` 级日志（category `codex-refresh`）并继续返回本次刷到的 token——它这次会话仍可用，不该因落盘失败让整次取数失败。

`WriteBack.importedAccount(id:)` 指向 cc-bar 自己的 Keychain 条目（`com.cc-bar.codex.imported`），不与任何 CLI 共享，这条路径的刷新本身就没有竞争。

### 5.2 Claude

`ClaudeAuth.load()` 优先读 `~/.claude/.credentials.json`；不存在再调 `security find-generic-password -s "Claude Code-credentials" -w` 读 Keychain。邮箱兜底来自 `~/.claude.json` 顶层 `oauthAccount.emailAddress`。

`ClaudeTokenRefresher.ensureFreshAccessToken`：**只读，不刷新、不回写。**

- 手上的 access_token 未过期（`refreshSkew=30s`）→ 直接用。
- 已过期 → 重读一次凭据存储，期待 Claude Code 已经自己刷过：读到的 access_token 还够用（`adoptSkew=5s`）就采用并更新 `claudeAccount`。
- 重读仍拿不到有效 token → 返回 `QuotaError.credentialsExpired`，文案「Claude 凭据已过期，请打开 Claude Code（或在终端运行 `claude`）刷新登录后再回来」。

#### 为什么不自己刷新

Claude 的 OAuth `refresh_token` 是 *一次性* 的：刷新即轮换，旧值立即作废，并且服务端带重用检测。同一个 `client_id` 下不存在「两份同时有效的 refresh_token」——cc-bar 每成功刷新一次，Claude Code CLI / Desktop 内存里那份就立刻变成废票，它们下次刷新拿到 `invalid_grant`，整条 token family 被撤销，**用户被迫重新登录**。

这不是靠「小心一点」能消除的：compare-and-swap 之类的写前比对保护的是磁盘状态，保护不了另一个进程内存里的副本。

关键权衡是收益侧：**cc-bar 需要刷新的时刻，恰好是数据不会变的时刻**。access_token 过期意味着用户已经很久没用 Claude Code，额度本来就没消耗，刷新换来的「新鲜数据」和快照里的旧数据是同一份。为一个不变的数字赌上用户主力工具的登录态，不划算。

同类工具的选择佐证了这一点：OpenChamber 与 cc-switch 对 Claude 完全只读（OpenChamber 的 quota 文档把理由写进了注释）；CodexBar 会刷新但只写自己的缓存条目，从不回写 `Claude Code-credentials`，且 0.47.0 起一度彻底停止读取该条目，原因是 Claude Code 每次刷新都会重写它的 ACL。

#### 过期后的降级链路

1. **保留快照**：`markClaudeFailure` 不清空 `claudeQuota`，上一次的额度条继续展示，只是标记错误。
2. **本地用量不受影响**：`Core/Usage/` 的 JSONL 统计不碰凭据，今日 / 本周 token 数、费用、模型分布照常工作。
3. **CLI 兜底取数**：用户手动刷新（`reason == .userInitiated`）且错误是 `credentialsExpired` 时，走 `ClaudeCLIFallbackQuotaClient`。`claude` CLI 用自己的会话身份，刷新对它是安全的，顺带把凭据刷新了，下一轮 cc-bar 重读就能直接采用。

#### 仍保留的两项协作机制

- **进程内去重**：`Coordinator` actor 合并菜单栏 / 悬浮窗 / Popover 几乎同时触发的重读——keychain 读要过一次 ACL，不便宜。
- **礼让窗口后重读**：存储在最近 `politeMtimeWindow=10s` 内被改过，认为 Claude Code 正在刷新的半途，sleep `adoptDelay=1s` 再读一次。两个源都支持：文件源看 mtime，keychain 源看条目属性里的 `mdat`（`security find-generic-password` 不带 `-w` 读属性不碰密文，不会触发钥匙串授权弹窗）。

> 删除的实现：`performNetworkRefresh` / `writeBackToFile` / `writeBackToKeychain` / `invalid_grant` 软恢复 / `ClaudeDelegatedRefresh`（PTY 唤起 `claude` CLI 代刷）。`QuotaError.tokenRevoked` 随之改名为 `credentialsExpired`，语义从「服务端拒绝了 refresh_token」变为「本地凭据已过期且我们不去刷」。
>
> 连带影响：`Helpers/CCBarClaudeWatchdog`（为委托刷新做 TCC 归因隔离的套娃小二进制）随之失去唯一调用方，已连同工程里的 `Embed CCBarClaudeWatchdog` 构建阶段一并删除。现在只剩 `ClaudeCLIFallbackQuotaClient` 这一处会起 `claude` CLI，它直接 `Process` 启动，不做 TCC 隔离，也不设受控 cwd。

### 5.3 Cursor

`CursorAuth.load()` 只读打开 `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`（`SQLITE_OPEN_READONLY`，busy timeout 250ms），取 `cursorAuth/accessToken` 一项。

- token 是 JWT，只解 payload 取 `sub`（`userID::subject` 形态）、email 与 `exp`，用于识别账号与判断过期（`expirationLeeway = 60s`）。
- 请求侧不发 Bearer，而是把它拼成 Cookie：`WorkosCursorSessionToken=<userID>%3A%3A<accessToken>`（`CursorAuthSession.cookieHeader`）。
- **不读 refresh token、不调 OAuth、不写 Cursor 的 SQLite，也不把 Cursor 凭据存进 cc-bar 的 Keychain / UserDefaults / `quota-cache.json`。** token 过期后只能等 Cursor.app 自己续，cc-bar 重读即可。
- 额度或用量请求收到 401 时，`AppState` 只允许重读一次本地 SQLite（`loadCursor()`）再重试一次，不做第二轮（见 `loadCursorQuota` / `refreshCursorRemoteUsage` / `loadCursorUsageHistory`）。
- 账号身份用 `belongsToSameAccount(as:)` 比对（先比 `userID`，都为空才退回规范化邮箱），身份变化时清掉 Cursor 的额度快照与远端用量缓存。

### 5.4 Command Code

`CommandCodeAuth.load(homeDirectory:preference:)` 返回 `CommandCodeAuthSession { accessToken, source, login, name, email, orgID, planType }`，`source` 记录命中的来源，用于设置页与 Onboarding 展示。

- `preference == .automatic`（默认）时按顺序取第一个命中的：`~/.commandcode/auth.json` → `~/.pi/agent/auth.json`（读 `commandcode` / `command-code` provider 项）→ `~/.local/share/opencode/auth.json`（同上）→ 环境变量 `COMMAND_CODE_API_KEY` / `COMMANDCODE_API_KEY` → cc-bar 自己的 Keychain 条目（`service = com.nanvon.ccbar.command-code`，`account = primary`）。
- `preference == .manual` 时**只**读 Keychain，不扫描任何本地文件；偏好持久化在 `ccbar.settings.commandCodeCredentialPreference`，由设置页的 `CommandCodeCredentialSheet` 切换。
- 令牌是不透明 API Key，没有 JWT / `exp` / refresh：不做续期，身份（`login` / `name` / `email` / `orgID` / `planType`）由 `/alpha/whoami` 与 `/alpha/billing/subscriptions` 回填；账号键 `accountKey` 优先 `org:<orgID>:<login|email>`，退化到 `user:<login>` / `email:<email>`，都没有时用 token 首尾片段拼出的占位键（不落盘明文 token）。

### 5.5 Antigravity

`AntigravityCredentials.load()` 优先读 `~/.gemini/jetski-standalone-oauth-token`（Antigravity 生态真源：agy CLI / IDE 插件登录即写此文件），读不到才退回 `~/.gemini/oauth_creds.json`（旧版 Gemini CLI 遗留）。`AntigravityAccount.source` 记录命中的文件，供刷新后原样写回。

- 过期时间来自 jetski 的 `expiry`（ISO8601）或 oauth_creds 的 `expiry_date`（毫秒）；临期 `refreshSkew = 300s` 时 POST `https://oauth2.googleapis.com/token` 用 `refresh_token` 续期并写回原文件。
- OAuth client 有两个候选：Gemini CLI 的公开 client 与 Antigravity 原生 client，client_id 直接写在源码里（公开标识），**client_secret 不硬编码**——刷新时按需从本机已安装的官方组件里提取（Gemini CLI 的 npm bundle `*.js`、Antigravity 的 `~/.gemini/bin/agy` 二进制），因此永远与官方客户端同步，也不会让开源仓库或分发的二进制携带官方密钥。
- 账号身份（email / plan）本地解不出完整信息时由云端 `loadCodeAssist` 响应回填；同一 token 未变时沿用上次回填的身份，避免误判账号切换。

## 6. 额度查询

### 6.1 接口

| 服务 | 请求 | 关键 Header |
|---|---|---|
| Codex | `GET https://chatgpt.com/backend-api/wham/usage` | `Authorization: Bearer …`、`ChatGPT-Account-Id`、`User-Agent: codex-cli` |
| Claude | `GET https://api.anthropic.com/api/oauth/usage` | `Authorization: Bearer …`、`anthropic-beta: oauth-2025-04-20`、`User-Agent: claude-code/2.1.0` |
| Antigravity | `POST https://daily-cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` + `:retrieveUserQuotaSummary` + `:fetchAvailableModels` + `:retrieveUserQuota`（主域 `cloudcode-pa.googleapis.com` 仅作失败回退） | `Authorization: Bearer …` |
| Cursor | `GET https://cursor.com/api/usage-summary` | `Cookie: WorkosCursorSessionToken=…`（无 Bearer） |
| Command Code | `GET https://api.commandcode.ai/alpha/whoami` + `/alpha/billing/credits` + `/alpha/billing/subscriptions` | `Authorization: Bearer <API Key>` |

响应统一映射为 `QuotaSnapshot { primaryLimit, secondaryLimit, auxiliaryLimits, modelLimits, geminiWindow, geminiWeekly, isUnlimited, ... }`，每条 `QuotaLimit` 带 `fiveHour / weekly / modelWeekly / unknown` 语义。

- **Codex**：根据 `limit_window_seconds` 识别 5H 与 WK，并保留服务端主次顺序。
- **Claude**：合并旧的 `five_hour` / `seven_day` 与新 `limits` 数组，Fable 等 `weekly_scoped` 项进入 `modelLimits`。
- **Antigravity**：`retrieveUserQuotaSummary` 的分组是权威源（`gemini-5h` / `gemini-weekly` 属 Gemini 组，`3p-5h` / `3p-weekly` 属 Claude and GPT 组）——primary = Gemini 5h、secondary = Gemini weekly、`auxiliaryLimits` = Claude 5h / weekly，同时把 Gemini 两窗口另存进 `geminiWindow` / `geminiWeekly`；拿不到分组源时退化为「5h 主条 + weekly 副条」。重置时间只用服务端 `resetTime`，缺失就显示未知，不按窗口长度推。
- **Cursor**：`individualUsage.plan.totalPercentUsed`（`limitType == "team"` 时改用 `teamUsage.pooled` 比例）映射为 `cursor-total` 主额度，`autoPercentUsed` 作为副条 `cursor-auto`、`apiPercentUsed` 作为辅助条 `cursor-api`；窗口长度由 `billingCycleStart` / `billingCycleEnd` 推出，`isUnlimited` 时不渲染百分比或进度条。
- **Command Code**：`windowLimits.fiveHour` / `.weekly` 的 `cap` 与 `used` 由服务端返回（本地不写死上限），换算成百分比；`cap <= 0` 的窗口整条丢弃。`usedPercent == 0` 且没有有效未来 `resetAt` 时，按窗口长度（5h = 18000s / 周 = 604800s）预估一个重置时间，与 Codex / Claude 对齐。GOAT 套餐额外把 `credits.monthlyCredits` 按月总额 70 换算成一条 `MONTHLY` 辅助额度（`windowSeconds = 30 天`，重置时间取订阅的 `currentPeriodEnd`）；非 GOAT 套餐不生成月度条目。

### 6.2 调用策略

- 启动读 `quota-cache.json` 灌进 AppState，不立刻打网络；bootstrap 后 7 秒补一次额度请求（`.periodic`，受 60s 最小间隔与 429 退避约束），让 Popover 不必等首个调度周期。
- 周期循环按设置间隔触发（额度默认 2 分钟，可设 1 / 2 / 3 / 5 / 10 分钟；代码层保留对 nil / 0 的兜底，设置 UI 无「关闭」入口）；任意一家上次成功 < 60s 时跳过。
- 收到 429 后该服务进入 10 分钟退避，期间所有触发短路。
- 手动刷新绕过 60s 节流，但仍遵守 429 退避。
- 401 / 403 不会自动停止循环（保持简单），但错误会显示在 Popover。
- 网络、本地服务或解析失败均保留旧快照，错误写入 `lastError`，下一 tick 重试。

### 6.3 Claude CLI 兜底

`ClaudeCLIFallbackQuotaClient` 只由 `refreshNow`（`reason == .userInitiated`）触发，且自身有 10 分钟独立冷却。两种进入条件：

- **API 取数失败** 且 `claudeQuota == nil`（手上一份快照都没有，需要救急）；
- **凭据已过期**（`QuotaError.credentialsExpired`）——cc-bar 不自己刷新，改由 CLI 用它自己的会话身份取数，顺带完成刷新。

行为细节：

- 候选可执行：`/opt/homebrew/bin/claude` → `/usr/local/bin/claude` → `/usr/bin/claude` → `env claude`。
- 用 `/usr/bin/script -q /dev/null <claude>` 包一层伪 PTY 拿到 ANSI 输出；失败再裸跑一次直接执行。
- 通过 stdin 写入 `/usage\n\n/status\n/exit\n` 驱动 CLI。
- 输出 strip ANSI，按 `Current session` / `Current week (all models)` / `Current week (Sonnet only)` / `Current week (Opus)` 标签抓百分比与 `Resets …` 文本。
- 错误关键词识别：`rate_limit_error` / `authentication_error` / `failed to load usage data`，转成对应 `QuotaError`。

CLI 兜底拿到的 snapshot 用 `QuotaSnapshotSource.cliFallback` 标记，仅用于救急展示。

### 6.4 持久化

`QuotaCache` 写 `~/Library/Application Support/CCBar/quota-cache.json`。当前结构版本 v4，用 `providers[QuotaApp]` 保存语义化主次额度；读取 v2 快照时按窗口长度重新归类 Codex，旧 Claude Opus/Sonnet 转为模型专项额度，读取 v1 时继续迁移顶层 `codex` / `claude` 字段。

三个额度文件的写入统一走 `QuotaPersistenceCoordinator`（批次 C）：刷新 / bootstrap / 设置操作只更新内存并标脏（`QuotaFile` 集合），末尾构造不可变 snapshot 提交；coordinator 在 utility 任务里编码 + 原子写，同一文件一轮最多一次，串行提交 + pending 合并防止旧写入覆盖新版本。每次 flush 由 AppState 在 MainActor 上分配单调递增 `sequence`，coordinator 丢弃序列号不高于已写入的提交——`Task.detached` 的执行顺序无语言保证，序列号用于裁决乱序到达的过期快照。写盘失败只记日志，不回滚内存快照与 UI，下轮成功刷新会重新生成完整 payload 覆盖。周期边界滚动触发的受限重建仍按内存中的最新 `quotaCycles` 判断，不等写盘完成。

`quota-history` 单独设最短写盘间隔 `quotaHistoryWriteInterval`（15 分钟）。每次采样 `sampledAt` 都会前进，快照必然不等于上一份，因此它会跟着额度刷新频率被整份重写——本机实测 220KB，2 分钟一次就是每小时 6.6MB。它只承载历史曲线，当前额度由 `quota-cache`（数 KB）承载，丢几个采样点对用户没有实质影响。未到期时脏标记保留到下一轮 flush，不会丢失；`cache` / `cycles` 体量小或本就不常变（后者已由 `scheduledEndJitterTolerance` 挡掉抖动重写），不受此限制。三者都不脏或只有未到期的 history 脏时，本轮不提交任何快照。

`QuotaHistoryStore` 写 `~/Library/Application Support/CCBar/quota-history-today.json`，保留最近 15 个自然日（含今天）的本机额度采样：

- **窗口系列**：每个账号的 5 小时 / 每周两个标准窗口各自独立成一条系列（key = `seriesKey(accountKey, limitKind)`），本次刷新同时记录 `primaryLimit` 与 `secondaryLimit` 中 kind 为 `fiveHour` / `weekly` 的窗口；两条窗口的 `lastSamples`、`events` 与窗口边界互不影响。
- `lastSamples`：每个系列最近一次成功采样的窗口类型与剩余整数百分比。同一系列的类型 / ID 改变时清理该系列旧基准和事件，避免跨窗口产生虚假涨跌；其他系列不受影响。
- `events`：只有同一系列剩余整数百分比发生变化时才新增事件，字段包含账号 key、应用、账号类型、额度 ID/类型、采样时间、变动前 / 后剩余、delta 和重置时间。
- 启动和每次写入都按本地 `Calendar.current.startOfDay` 清理更早于「今天 − 14 天」的事件与样本，保证当前滚动周窗口（7 天）与上一轮周窗口对比始终有数据。
- **时间线投影**：`timelinePeriods` 不改变持久化格式。5H 过滤为本地自然日 `00:00–24:00`（仅用于筛选数据，图表 X 轴按实际采样范围自适应）；每周以最新 `resetsAt` 划出当前周期（不是自然周），上一周期的边界取事件自身 `resetsAt` 里早于当前窗口的最近一个（窗口重新起算后新旧周期未必正好相差 7 天，硬按「当前起点」推导会把整段真实数据判空），没有可用旧窗口时才退回 7 天推导。每个周期显示真实变动事件，当前周期额外并入 `lastSamples` 的最新成功采样；因此 Codex 跨周期重置后即使不生成 delta 事件，界面也会显示新周期的当前值和刷新时间。
- **周期归属与折线分段**：事件带 `resetsAt` 时按同窗容差归属，缺失时才退回时间范围并用半开区间，避免边界事件同时落进两个周期；当前周期先认领，上一周期不重复计入。`QuotaTimelineEntry.windowIndex` 按 `resetsAt` 给相邻点分段，图表据此断线——5H 的一天横跨约 5 个窗口，而跨窗重置本就不产生变动事件，不分段会把上一窗口低点与新窗口高点直连成「额度自己涨回去」的假斜线。
- 历史格式 v3：v2（只记主额度、只存当天）在载入时把 `lastSamples` 键按样本内的 `limitKind` 迁移为窗口系列键；v1 无法判型的当天记录不迁移。
- Codex 主账号、Claude 主账号、每个导入 Codex 账号分别使用独立 key；镜像主 Codex 的导入账号只在主账号来源为 API 成功快照时记录。

### 6.5 服务状态（`ServiceStatusClient`）

OpenAI / Anthropic / Cursor 各自的 Statuspage.io 公开接口,无需鉴权,用于在 Popover 中显示一个状态圆点：

| 服务 | 端点 |
|---|---|
| OpenAI | `https://status.openai.com/api/v2/status.json` |
| Anthropic | `https://status.claude.com/api/v2/status.json` |
| Cursor | `https://status.cursor.com/api/v2/status.json` |

Antigravity 与 Command Code 没有可用状态源：Google 未提供 Antigravity 状态页（`status.cloud.google.com` 是全 GCP 事件流，不覆盖 `cloudcode-pa.googleapis.com`）；Command Code 的 `status.commandcode.ai` 是 Upptime 静态站，无 JSON 接口，其数据等价于外部 ping `api.commandcode.ai`，与 App 自身的额度请求结果重复。

响应中 `status.indicator` 取值 `none / minor / major / critical / maintenance`，未识别值归并为 `unknown`。`ServiceStatusClient.fetch` 解析为 `ServiceStatus { indicator, description, updatedAt, fetchedAt }`，10s 超时。

调用策略：

- `AppState.refreshServiceStatus()` 并发拉三家，单边失败不影响其他；网络/解析失败保留上一份快照，不清空。
- 由 `Scheduler` 固定 5 分钟一次驱动；启动后立即拉一次；`refreshNow()` 也会顺带刷新。
- 仅做展示，不缓存到磁盘。

### 6.6 更新检查（`UpdateChecker`）

两级降级数据源，均为公开仓库匿名访问、10s 超时：

1. **主路 · 静态版本清单**：`https://github.com/nanvon/cc-bar/releases/latest/download/version.json`（`Accept: application/json`，`cachePolicy = .reloadIgnoringLocalCacheData` 避免读到 CDN/本地缓存的旧清单）。该文件由 [release.yml](../.github/workflows/release.yml) 在构建后生成、随 DMG 一起挂到 Release，内容为 `{"tag","version","page"}`。`releases/latest/download/<asset>` 是 GitHub 的稳定端点，走 302 + CDN，**不占用 API 额度**。
2. **兜底 · Releases API**：`https://api.github.com/repos/nanvon/cc-bar/releases/latest`（`Accept: application/vnd.github+json`），解析 `tag_name`。仅在清单不可用（如该 release 未附带 version.json、或网络抖动）时使用。匿名 API 限 60 次/小时**/IP**，共享出口 IP 下容易被其他程序耗光，因此不作主路。

拿到 tag（`vX.Y.Z`）后与当前 `CFBundleShortVersionString`（即 `MARKETING_VERSION`）做数值比较：

- `UpdateChecker.isNewer(tag:than:)`：去 `v` 前缀、按 major/minor/patch 逐段数值比较，长度不足的段视为 0；tag 或当前版本任一侧格式无法解析时按「不更新」处理，避免误报。
- 状态机 `AppState.updateStatus`（`idle / checking / upToDate / updateAvailable / failed / rateLimited`），`checking` 期间重复调用直接返回（去重）。
- 触发：设置页「检查更新」手动触发；`autoCheckForUpdates` 开启（默认关）时 bootstrap 后延迟 5s 自动查一次。只做按需检查，不做定时轮询。
- 发现新版本时按钮变为「前往下载」，经 `NSWorkspace.shared.open` 打开 `https://github.com/nanvon/cc-bar/releases/latest`，由用户手动下载。**不做自动下载/安装**：工程为 ad-hoc 签名、未公证，自动替换会被 Gatekeeper 拦截，且目录策略约定不覆盖 `/Applications` 中的运行安装。
- 失败区分两档，均可重试、无其他副作用：兜底 API 返回 403 + `x-ratelimit-remaining: 0` 或 429 时（`UpdateChecker.isRateLimited`）置 `.rateLimited`，设置页显示「GitHub 暂时限流，请稍后再试」；其余失败置 `.failed`，显示「检查失败」。

## 7. 本地 JSONL 扫描

`JSONLDirectoryEnumerator` 在递归枚举时一次取得 URL、mtime 与 size，Claude / Codex / Pi Scanner 复用这份 descriptor，不再逐文件二次查询属性。Codex 仍保留最多 4 路的变化文件并发解析，但未变化文件在创建 Task 前即被过滤，只用已有 `ScanFileState` 补会话 seed；扫描目录、存活文件判定、archive 去重、watermark 与统计口径不变。

**逐行解析的内存约束**（全量重扫的峰值主因，改动前实测 1.8GB / 稳态 190MB）：

- 文件读取走 `JSONLLineReader.streamLines`：每次读 4MB 块，块内按整行切分、每 256 行回调一批，跨块残行留到下一块拼接。单文件常驻内存与文件大小无关（本机最大 jsonl 达 59MB），不再出现「整份 Data + 整份 String + 全部行数组」三重驻留。消费语义与旧的 `readOutcome` 完全一致：只消费到最后一个 `\n`，末尾残行不推进 offset，整段没有换行时 `newOffset == offset`。`readOutcome` / `read` 保留给单测与只需一次性取全部行的调用方。
- **块内切行按字节，不按 Character**：用 `Data.firstIndex(of:)` 定位 `\n`、逐段 `String(data:encoding:)`，不再先整段转 `String` 再 `split(separator: "\n")`。后者按 Character 切分要逐位判定 grapheme cluster 边界，本机 `sample` 实测该步采样数（1361）高于逐行 `JSONSerialization` 本身（855），是扫描的头号 CPU 开销。换行符是 ASCII，「整段可解码」与「每行都可解码」互为充要，因此「任一行解码失败即整段作废」与旧实现逐字节等价；空行跳过、末段保留的语义同样不变。
- **每块读取与每批解析都包 `autoreleasepool`**。逐行 `JSONSerialization` 会产出大量 Objective-C 临时对象，`FileHandle.read` 每块返回的也是 autoreleased NSData 支撑的 `Data`；Swift 并发只在 job 结束时排空池，而全量扫描是一个数分钟、无挂起点的长 job，不显式排空就会把整轮解析的临时对象全部堆在池里。OpenCode（SQLite 行循环）与 `ConversationTitleIndex`（索引文件逐行解析）同样按 256 行一批排空。
- 实测（1729 个 codex 文件 / 1.8GB / 43.6 万行，独立复现程序）：不排空池 400MB 日志即达 790MB 峰值；只加池 124MB；分块流式 + 块级池后全量 1.8GB 仅 148MB，且峰值不随日志体量线性增长。
- 相应地，`UsageEntry` 批量驻留不是峰值来源：本机全量约 11 万条、单条约 200–250B，合计仅数十 MB。

### 7.1 Claude（`ClaudeJSONLScanner`）

- 入口路径 `~/.claude/projects`，遍历所有 `.jsonl`。
- 每条 `type=assistant` 行解析 `message.id` / `message.model` / `message.usage`（`input_tokens` 不含 cache_read）/ `stop_reason`。缓存写入 Tokens 对外仍使用 `cache_creation_input_tokens` 合计；计价时额外拆出 `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`。明细缺失时合计全部按 5m，明细与合计不一致时保留合计、1h 不超过合计、剩余按 5m。
- 本批次内按 `message.id` 取唯一，优先选 `stop_reason != nil` 或更高 output_tokens 的一条；最后与全局 `seen` 集合比对，避免 sidechain / subagent 文件中重复计数。
- 每条记录同时提取 `sessionId` / `cwd` / `gitBranch`；相同 `sessionId` 的主文件与 `subagents/` 文件合并为一个对话，档案标记是否包含子任务。
- 标题优先从 `~/.claude/history.jsonl` 按 sessionId 关联；未命中时取主会话第一条非注入 user 文本并清洗为最多 80 字摘要。
- 项目先收集同一 session 的全部 cwd 候选，再按 history project、唯一 Git 根目录、非 sidechain cwd、顶层项目容器匹配的顺序解析；无法可靠消除多个项目冲突时归为“无明确项目”，不依赖文件枚举顺序。
- 全局 seen 列表持久化在 `scan-state.json`，上限 20000，超出截尾。
- 流式 assistant 行只有在 `stop_reason != nil` 时才代表一次完整调用；半成品不入账，也不写入 seen，等待后续完整行由下一次增量扫描接收。永远没有结束行的中断请求不统计。

### 7.2 Codex（`CodexJSONLScanner`）

- 入口路径 `~/.codex/sessions` + `~/.codex/archived_sessions`。
- rollout 用文件名 / `session_meta.id` 的稳定 UUID 作为扫描状态 key；文件移入 `archived_sessions` 后继续沿用原 offset，避免重扫叠加。
- 标题优先从 `~/.codex/session_index.jsonl` 关联真实 thread name，未命中时取首条 `user_message` 摘要。
- `session_meta.cwd` 经 `ConversationProjectResolver` 形成项目身份（存在性检查与 Git 根识别按 §7.5a 的隐私分级执行）；检查过的已不存在路径仍保留为历史项目。
- `turn_context` 行更新当前模型（写入 `ScanFileState.lastModel`）。
- `thread_settings_applied.thread_settings.service_tier` 更新当前速度档位：`priority` / `fast` → Fast，`default` → Standard，其他值 → Unknown；写入 `ScanFileState.lastServiceTier`，增量续扫继承该状态。
- `event_msg` 且 `payload.type == "token_count"` 行，从 `payload.info.last_token_usage` 直接累计（不是累计 delta），`info == nil` 跳过。
- 每条 `token_count` 同时对 `total_token_usage` 的稳定字段生成签名并写入 `ScanFileState.lastCodexTotalUsageSignature`；设置切换后若累计签名没有变化，说明只是回显上一请求，跳过而不把它错归到新档位。
- Codex 的 `input_tokens` 含 cache_read；若 `last_token_usage.cache_write_tokens`（或 `input_tokens_details` / `prompt_tokens_details` / `token_details` 内同名字段）存在，`billable_input = input_tokens − cached_input_tokens − cache_write_tokens`。当前本地日志缺该字段时按 0，不推测缓存写入。
- **fork 会话的历史重放去重**：Codex 从某个会话 fork（`session_meta.payload.forked_from_id`）时，会把父会话已有的整段历史**逐字节重放**进新文件（只改写 `timestamp` 为 fork 时刻），其中包含父会话全部 `token_count`，同一份用量因此同时出现在父子两个 JSONL 里。重放段没有任何事件级标记，也无法用「`session_meta.id` 与文件自身不符」判定——fork 之后的新调用不会再写自己的 `session_meta`，同样落在父会话 id 之下（本机 1752 个会话实测，该判据会多删 8487 万真实 Token）；`forked_from_id` 本身也不是判据：存在带该字段却没有重放的 fork，而带 `parent_thread_id` 的子代理会话完全没有重放。
  - 解析时区分两个会话 ID：`ownSessionID` 只由**首条** `session_meta`（或文件名 UUID）决定，用量与会话种子一律归到它；`emittingSessionID` 跟随每条 `session_meta` 变化，重放段里指向父会话，只用于生成去重键。
  - 跨文件去重键为 `emittingSessionID#累计用量签名`（`total_token_usage` 的六个稳定字段，同 `lastCodexTotalUsageSignature`），持久化在 `ScanState.codexSeenTokenIds`（做法同 Pi 的 `/fork` `/clone` 去重）。重放行与父文件里的原始行天然同键；fork 之后的新调用累计值更高、键不同，正常入账。累计用量缺失时不参与去重（宁可重复也不误删）。回显重复由 `lastCodexTotalUsageSignature` 在解析阶段先滤掉，去重键才不会把它们误判成重放。
  - 文件按会话 UUID 升序解析（Codex 会话 ID 是 UUIDv7，前 48 位即创建时刻毫秒，字典序等于创建序），保证父会话先于它的 fork 被扫到。去重只保留首次出现的记录，顺序不确定时会改成留下重放副本——后者 `timestamp` 已被改写成 fork 时刻，用量会归错天。
  - 去重发生在并发解析结果的**合并阶段**（单文件解析无共享状态），`cacheCreationKeys` 同样在此收集，只有真正入账的记录才给会话补标。

### 7.3 Pi（`PiJSONLScanner`）

- 入口路径 `~/.pi/agent/sessions/**/*.jsonl`（按工作目录分子目录，递归枚举）。
- pi 会话文件是 append-only JSONL，assistant 消息自带 `message.usage`（`input` / `output` / `cacheRead` / `cacheWrite` / `totalTokens`）与可选的 `message.cost`（USD 费用四类 + `total`）；`cost.total > 0` 时日志价格优先，缺失或为 0 且有 Token 时由统一 Pricing 按在线目录 → 本地价格表补算，仍无价才让 `costUSD` 为 nil。缺价条目会进入 `hasUnpricedUsage` 路径并触发远端价格刷新。
- 模型标签为 `provider/model`（如 `deepseek/deepseek-v4-flash`），避免不同 provider 模型重名；速度档位恒为 Standard（pi 无档位概念）。
- Pi 的四项日志费用与 `total` 只有 JSON 浮点尾差时，保留官方分项并把差额对齐到总价；明显不一致的分项不作为可靠构成。
- 解析 `type=message` 的 assistant 消息计入用量；`type=compaction` / `type=branch_summary` 带 `usage` 时也计入（对齐 pi `/session` 的 token/cost 合计口径，模型标签沿用文件内最近一条 assistant 的）；toolResult 嵌套 usage、label、model_change 等不参与。
- 会话标题取会话内首条 user 消息文本（清洗为最多 80 字）；项目身份由 `type=session` 的 `cwd` 经 `ConversationProjectResolver` 解析。
- 增量沿用 mtime + byte offset；跨文件按 `entryID@ISO timestamp` 全局去重（覆盖 `/fork` `/clone` 复制旧行到新文件导致的重复计费），全局 seen 上限 20000 截尾（同 Claude）。

### 7.4 OpenCode（`OpencodeScanner`）

- 入口 `~/.local/share/opencode/opencode.db`（OpenCode Desktop / CLI 共用同一 SQLite 库）；只读打开（`SQLITE_OPEN_READONLY`），与 OpenCode 运行中的写入通过 WAL 并发安全。库缺失 / 打开失败 / 表结构不符时本轮 no-op、保留原 watermark，不阻塞其他服务扫描。
- 解析 `message` 表每行 `data` JSON：user 消息带嵌套 `model{providerID, modelID, variant}`，assistant 消息自身带顶层 `providerID` / `modelID`；模型标签格式 `providerID/modelID`（对齐 Pi），variant 不拼入。增量扫描只追加 assistant 时模型标签可能丢失，回退到会话内最近 user 消息继承的模型兜底。
- assistant 消息自带 `cost`（USD）与 `tokens{input, output, reasoning, cache{read, write}}`；reasoning 并入 output（对齐 Claude / Codex 的 output 含 thinking 口径）。`total <= 0` 且无 cost（或 cost 为 0）的消息（工具调用收尾等）不计入。
- 费用：有效官方 `cost > 0` 时总额直接采用，价格链只用于估算四项费用占比并按官方总额缩放，不会覆盖官方总费用；缺失或为 0 且有 Token 时调用统一 `Pricing.resolveCostBreakdown`，按在线目录 → 本地价格表补算。最终 `UsageEntry.costUSD` 与 `costBreakdown.total` 始终一致，本地与远端都无价时按 `$0` 展示。`Pricing.normalize` 对 `opencode-go/` / `commandcode/` / `command-code/` 前缀剥除（Command Code 为双层标签，循环剥内层 `deepseek/` 后与本地表 / 远端目录对齐）。
- 会话信息：`session` 表提供 title / directory，`workspace` 表提供 branch；空标题用该会话首条 text part 兜底。项目身份由 directory 经 `ConversationProjectResolver` 解析。速度档位恒为 Standard（无档位概念）。
- 增量：watermark 为 `max(message.time_created)`（Unix 毫秒），查询 `>= watermark` 并按 `message.id` 全局去重兜底 compaction / 时间戳回跳，seen 上限 20000 截尾；被删除的会话不回扫（与 JSONL append-only 假设一致）。
- **无订阅额度**：定位与 Pi 一致——不进入额度轮询、Popover 额度区、菜单栏、悬浮窗与 Timeline；仅在主窗口用量统计与对话页展示（`opencodeTodayCost` 供 Popover 今日花费合计使用）。

### 7.5 增量与持久化（`ScanCache`）

- 每个文件维护 `ScanFileState { mtime, offset, lastModel?, lastServiceTier?, lastCodexTotalUsageSignature?, lastCodexEmittingSessionID?, conversationID?, conversationCwd?, conversationGitBranch?, conversationIsSidechain?, fallbackTitle? }`；Claude 按路径保存轻量会话摘要，让未变化文件也能重新判断项目可用状态，Codex 按稳定 conversationID 维护（该字段存的是文件**自身**的会话 ID，不会被 fork 重放进来的父会话 `session_meta` 覆盖）。Codex 文件截断时 offset、模型、速度、累计签名和 `lastCodexEmittingSessionID` 一起重置。
- 调度逻辑：`mtime == prev && offset == size` → 跳过；`offset > size` → 文件被截断，归零重扫（去重靠 seen 集合）；否则从 `offset` 处续读到末尾。
- **时间戳解析走手写快路径**：`JSONLTimestamp.parse` 先按 UTF-8 字节解析 `YYYY-MM-DDTHH:MM:SS[.fff…][Z|±HH[:]MM]`，形状不符再回退到复用的 `ISO8601DateFormatter`。除实例创建外，`date(from:)` 单次调用本身也很贵（内部走 CFDateFormatter 的通用格式状态机），实测占整轮日志扫描 CPU 的一半以上。快路径同样要求必须带时区、且必须完整消费整个字符串，与 `.withInternetDateTime` 的接受范围严格一致，不放宽也不收窄，避免把原本解析失败的行变成有效条目。
- 已不存在的文件 watermark 在每次扫描末尾清理。
- **跨文件去重集合走 `SeenIDSet`**（Claude message.id / Codex `会话 id#累计用量签名` / Pi entryID / OpenCode message.id 四处共用，上限 `defaultLimit = 20000`）。它显式维护插入顺序，`capped(to:)` 保留的是真正的最近 N 条。旧实现是 `Array(Set(...)).suffix(n)`：`Array(Set)` 给出哈希桶顺序、与插入顺序无关，因此截断保留的是**随机** N 条，可能把刚插入的新 ID 丢掉（文件被截断触发 `offset = 0` 重扫时就会重复计费）；而且集合扩容 rehash 后整个数组顺序重排，会让内容等价的 `ScanState` 每轮都被判为已变化，白白重写数 MB 的 scan-state.json（本机实测该文件 2.57MB，其中三个 seen 数组占 1.36MB）。改用有序结构后，没有新 ID 的轮次输出数组与输入逐元素相同，`ScanState` 判等即可跳过写盘。Pi 在文件读取失败时要回滚本文件本轮记下的 key，用批量 `remove(contentsOf:)` 合并成一次线性扫描。
- **scan-state 常驻内存**：`scan-state.json` 只在冷启动且日聚合、对话两份主 rollup 恢复成功后的首轮扫描中读盘解码；周期 rollup 若存在也必须同代，否则仅丢弃周期缓存并重建。此后每轮复用 `UsageService` 内存中上一轮已提交的 `ScanState`，内存路径执行与读盘路径相同的 generationID 结构校验；价格指纹只随缓存写盘记录、不参与失效判定（价格变化不自动重算，历史保持旧价，由设置页「重新计算用量」手动对齐）；持久化失败时清空内存副本并标记失效，下轮直接全量重建。
- **标题索引缓存**：`ConversationTitleIndex` 对 `~/.claude/history.jsonl` / `~/.codex/session_index.jsonl` 按 (mtime, size) 缓存解析结果，索引文件未变化的轮次不重读不重解析。
- 四份扫描缓存（scan-state / usage-rollup / conversation-rollup / cycle-usage-rollup）均为机器读文件，JSON 编码不使用 sortedKeys，省掉每轮写盘的全量键排序。
- 顶层结构 `ScanState { version, generationID, pricingFingerprint, claude, codex, claudeSeenMessageIds, codexSeenTokenIds, pi, piSeenEntryIds, opencodeLastMessageTime, opencodeSeenMessageIds }`，版本号 v14（v10 新增 pi 扫描 watermark，v11 新增 opencode watermark，v12 统一 Pi/OpenCode 费用解析口径，v13 项目归属隐私分级，v14 Codex fork 重放去重与会话归属修正，各自触发一次全量重建把对应历史数据扫入）。`UsageRollupPayload` 为 v9，`ConversationRollupPayload` 为 v7；三者共享同一 `generationID`，任一缺失或错代都触发全量重扫，避免部分写入后让 watermark 越过尚未持久化的聚合数据。
- **失效条件有两类**：`version` 管结构变更，`generationID` 管四份扫描相关缓存的提交一致性。任一不满足即整份丢弃；`UsageService` 会先清空内存聚合器，再全量重扫重算历史桶，绝不把全量结果叠加到旧桶。`pricingFingerprint`（`Pricing.fingerprint(knownUsage:)`，价格内容的 SHA-256）只随缓存写盘记录、不再参与失效判定：价格变化（本地价格表调整或远端调价）后自动扫描继续按现价计新条目，历史桶保持旧价，直到用户在设置页「重新计算用量」手动全量重算对齐——避免每次调价都自动重扫 GB 级日志造成能耗尖峰。`knownUsage` 由当前桶的 `(app, model, speed)` 推导。详见 §7.6。

### 7.5 聚合（`UsageAggregator`）

- `@Observable @MainActor`，内存 `[BucketKey: UsageBucket]`，BucketKey = (day, app, model, speed)。
- 本地 `ingestLocal(entries)` 累加 token 与 cost 并写 `usage-rollup`；Cursor Dashboard 远端桶只经 `replaceRemote(app:dayRange:buckets:)` 按自然日替换并写独立 `cursor-usage-rollup`。`snapshot()` / `totals(app:from:to:)` 才合并两区供统计 UI 读取，Cursor 不进入本地价格指纹、扫描缓存、对话或周期聚合。
- 由于是 `@Observable`，Popover 和统计 tab 在 body 读 `aggregator.totals(...)` 时自动建立依赖，新扫描完写回 buckets 后 UI 自动刷新。
- **Token 展示口径**：`UsageTotals.inputWithCacheTokens = input + cache_read + cache_creation`，`totalTokens = inputWithCacheTokens + output`。Stats 页的"总令牌 / By service tokens / By model 入"统一使用此口径，与 cc-switch / ccusage 对齐；其中 Claude 的 `input_tokens` 本身不含 cache_read，Codex 的 `inputTokens` 在解析时已扣过 `cached_input_tokens`，因此三项相加不会重叠。
- `UsageSpeedBreakdown` 分别汇总 Standard / Fast / Unknown。原始 Tokens 不乘倍率；只有 Fast 桶另算 `fastBillingEquivalentTokens`。未收录倍率时等效 Tokens 按 0；聚合范围只要混入任一未收录倍率的 Fast 模型，倍率统一显示 `—`，不能只显示已知模型的倍率而让它与总 Fast Tokens 不一致。未收录档位费率时金额按 `$0` 展示。

### 7.5a 对话聚合（`ConversationAggregator`）

- 与日聚合并行维护 `ConversationInfo` 和 `(conversationKey, day, model, speed)` 桶；列表可按时间范围汇总，右侧详情聚合对话完整生命周期。
- 档案只保存 ID、最多 80 字标题摘要、项目 key / 名称 / 规范路径 / 状态 / 来源、分支、源文件路径和起止时间，不保存完整消息正文。
- `ConversationProjectResolver` 对扫描中的唯一原始路径做 memoized 项目解析，并按隐私分级决定是否触碰文件系统：只有家目录以内、且不在 TCC 保护目录（桌面/文稿/下载/音乐/图片/影片）之下的路径才做文件系统检查——存在时解析 symlink 和最近 Git 根目录，已删除路径标记 unavailable；其余路径（含可移动卷、网络宗卷、其他用户目录）不发起任何文件系统访问，只按字符串归组并标记 unverified。分级判定 `allowsFileSystemCheck` 大小写不敏感、按路径组件匹配，拿不准一律不查，避免非沙盒 App 触发系统「文件与文件夹」授权弹窗。`/` / 用户主目录归为无明确项目，CCBar wakeup / probe 归为系统任务。同名路径不合并。
- 项目状态新增 `unverified`（与 available / unavailable 同为路径身份，`isPathBased` 参与重名分组）；项目菜单里 unverified 与可用项目同组展示，不显示「已不存在」徽标。Info.plist 里的 `NSDesktopFolderUsageDescription` 等六个用途声明只是保险层：按上述分级，正常路径不会再触碰保护目录。
- `ConversationQueryRequest / ConversationQueryResult` 把 app、projectKey、时间、搜索与排序合并为一次查询：单次遍历同时生成对话行、项目选项、项目 key 和重名集合。聚合器以 `revision` 标记 load / ingest 后的数据版本，并 memoize 最近一次查询；SwiftUI 重绘复用快照，不重复聚合。
- 详情按 `(conversationKey, revision)` 缓存，只有切换对话或扫描数据变化时重新聚合完整生命周期；seed 的标题、项目、路径等字段与现有档案完全一致时不递增 revision。无 Token 桶的 seed 不进入持久化档案，避免产生无效起止时间。`isEmpty` 直接读取桶状态，不通过 `snapshot()` 复制全量数据。秒级“上次更新”文字由独立视图刷新，不使列表查询失效。
- `ConversationUsageBucket` 同时保存速度档位、请求数、四项 Token、四项成本及内部缺价标记；查询层生成 Standard / Fast / Unknown 明细以及 standard / fast / mixed / unknown 状态。缺价部分金额按 0 汇总，UI 只展示最终数值，不追加缺价文案。
- `ConversationRollupCache` 写入 Application Support 下的 `conversation-rollup.json`，失效条件与日聚合一致（结构版本 / generationID）。

### 7.5b Cursor 远端计量（`CursorUsageFetcher` + `CursorUsageCache`）

Cursor 没有本地会话日志，它的用量来自账号级 Dashboard 接口，因此**不进入 JSONL 扫描链路**：不写 `scan-state.json`，不参与价格指纹、对话聚合和周期聚合。

- 取数：`POST https://cursor.com/api/dashboard/get-filtered-usage-events`，同样只带 `CursorAuthSession.cookieHeader`。按时间窗口分页，`pageSize = 1000`、单窗口最多 `maxPages = 200`；分页期间总数变化、页数不足或单日事件超过页上限时抛出对应的 `CursorUsageError`，本轮放弃而不写入半截数据。
- 费用口径：直接用事件的 `chargedCents` 汇总，**不套本地价格表**。字段缺失或异常时置 `UsageBucket.costIncomplete`，它与本地缺价标记 `hasUnpricedUsage` 语义不同，只作诊断，界面仍显示已知合计。
- 入库：`UsageAggregator.replaceRemote(app:dayRange:buckets:)` 按自然日**整段替换**远端区，不是累加；本地区与远端区在 `snapshot()` / `totals(app:from:to:)` 时才合并给统计 UI。
- 持久化：独立文件 `cursor-usage-rollup.json`（`CursorUsageCache`，结构版本 v1），记录日桶与 `coveredDayRanges`（已完整覆盖的自然日区间）。缓存按账号隔离，`cursorRemoteAccountID` 不匹配时不采用。
- 补拉策略：统计页选中有限范围且覆盖有缺口时按月串行静默补拉；`All` 只用现有缓存，不做无界回溯。已有任意相交快照就先展示已知金额，不因覆盖不全把数值清成占位。

### 7.5c 厂商归并（`ModelProvider`）

纯展示层推导，只服务统计页的「按提供商」面板，不参与定价与存储。

- `ModelProvider.resolve(app:model:)` 顺序：前缀匹配（`openai-codex/` / `openai/` → OpenAI，`anthropic/` → Anthropic，`deepseek/` → DeepSeek，`opencode-go/` → OpenCode-Go，`commandcode/` / `command-code/` → Command Code）→ 裸模型名关键词（`claude-` / `gpt-` / `o1` / `o3` / `o4` / `chatgpt-` / `codex-` / `deepseek-`）→ 按 app 兜底（codex → OpenAI，claude → Anthropic）→ `other`。
- Cursor / Pi / OpenCode 的模型若不匹配上述规则，一律归 `other`；`other` 组在任何排序下固定排最后。

### 7.6 价格（`Pricing` + `PricingCatalogStore`）

**统一解析**：扫描器统一调用 `Pricing.resolveCostBreakdown`。Pi / OpenCode 日志中的有效总价（`cost > 0`）直接采用，不会被价格表改写；Pi 保留浮点尾差范围内的官方分项，OpenCode 则用价格表估算分项占比并按官方总价缩放。日志价格缺失或为 0 且有 Token 时，再按 Standard API 价格链查在线目录 → 本地价格表。最终 `UsageEntry.costUSD` 与 `costBreakdown.total` 始终相同，统计页和对话页只消费这个最终结果。Codex / Claude 既有的 A/B 价格来源规则保持不变。

- **A 类**（`Pricing.localOverrideKeys` = `contextPriceTiers.keys ∪ timedOverrides.keys ∪ fixedLocalOverrideKeys`）：受本地特殊规则管辖，远端价格目录**零参与**。
  - GPT-5.6 Standard 使用 OpenAI Standard API 官方费率，覆盖 `gpt-5.6`（Sol 别名）、Sol、Terra、Luna；`gpt-5.6-pro` 不存在，Pro 为 reasoning.mode。每个模型用 `ContextPriceTiers { longContextThreshold, shortContext, longContext }` 表达两个完整费率，完整输入 `>272_000` 时输入、缓存读、缓存写和输出均切到长上下文价。未实现 Batch / Flex 费率选择。
  - GPT-5.5 Standard 同样在完整输入 `>272_000` 时切换长上下文价：输入 `$10`、缓存读取 `$1`、输出 `$45` / MTok；`<=272_000` 使用 `$5 / $0.50 / $30`。GPT-5.5 Pro 是独立模型，固定使用输入 `$30`、缓存读取 `$30`、输出 `$180` / MTok；官方没有缓存折扣，因此它列入 `fixedLocalOverrideKeys`，不接受远端目录覆盖。
  - `timedOverrides`：按历史日期分段生效价，取用量记录发生时间对应的分段。当前无模型使用（Claude Sonnet 5 原定 2026-09-01 换新价 $3/$15 已取消，官方确认 $2/$10 为固定标准价，改列 `fixedLocalOverrideKeys`）。
  - GPT-5.6 的 `cache_write_tokens` 按独立 cache-write 费率计入；Codex 当前本地日志未记录该字段，因此缺失时按 0，展示的是基于本地日志可得字段的官方 API 价格折算估算，而非账单对账。
- **B 类**（其余扁平价模型）：`PricingCatalogStore.shared.rate(for:app:speed:)` 的 Standard 价格优先（LiteLLM 优先于 models.dev），命中不到才回落内置 `table`；两者都没有时 `Pricing.cost()` 内部返回 `nil`，聚合与 UI 按 `$0` 处理。
  - **已知边界**：远端只提供「当前单一价」，没有历史分段，B 类模型一律用当前合并价重算全部历史。如果某个 B 类模型实际曾经调过价、需要精确历史计价，做法是把它升级为 A 类、手工加进 `timedOverrides`（发版维护）。

**`PricingCatalogStore`**（`Core/Pricing/`）：内存快照 + v2 磁盘缓存 + 后台刷新，用锁（`OSAllocatedUnfairLock`）保护而非 `actor`，因为 `rate(for:app:speed:)` 必须保持同步调用（两个 Scanner 同步调用 `Pricing.cost()`）。v1 缓存启动时迁移为 Standard rates，Fast rates 初始为空；迁移会清除旧 ETag / 刷新时间以强制一次完整拉取，既保留离线数据，也避免 304 让 Fast 永久空缺。

- 远端源：LiteLLM `model_prices_and_context_window.json`、models.dev `api.json`，各自独立 ETag / 24h 刷新间隔 / 失败 30min 退避。
- 匹配规则：LiteLLM 只取不含 `/` 的裸键，且 `litellm_provider ∈ {anthropic, openai, deepseek}`；Standard 解析基础字段，Fast 仅把 OpenAI `*_priority` 字段映射为 Codex Fast，不混淆 Anthropic Priority Tier。models.dev 只取 `anthropic`/`openai`/`deepseek` 三个官方 provider 下的 `models`，Standard 解析 `cost`，Fast 解析 `experimental.modes.fast.cost` 并按 provider 分入 Codex/Claude 两张表；转售商同名条目继续过滤。两侧都对 key 跑 `Pricing.normalize()`，裸名优先，日期后缀变体仅在裸名缺失时兜底填坑。
- 刷新触发有三条：App 启动和每次 `scanNow()` 开头用 `refreshIfNeeded()` 做 24h 常规检查；**只有手动重算（`forceRescan()`）**在扫描结束发现 Standard/Fast 缺价时调用 `refreshForMissing()` 绕过 24h，同一 app/model/speed 的尝试时间持久化且 30 分钟内不重复；设置页“价格目录”按钮调用 `forceRefresh()` 手动绕过 24h。Unknown 档位、已有可靠价格但请求级不支持的场景，以及明确不计价的 `codex-auto-review` 不触发缺价刷新。**自动扫描不做缺价刷新**：上游永远不会收录的模型（如 opencode 的隐身模型）会让缺价集合永不为空，挂在自动扫描上等于每 30 分钟强制拉两份远端目录，还会因指纹漂移连锁触发 GB 级日志全量重扫，是常驻能耗的主要来源。
- 快照一致性：刷新结果先进入 pending，只在扫描开始或一批扫描结束后的安全边界原子提交为 active；一整批扫描、缓存校验和最终 fingerprint 都只读取同一份 active 价格表。自动扫描不做缺价刷新、也不因指纹变化重算；缺价补齐与历史重算只发生在设置页「重新计算用量」。
- 保护链：网络失败 / 非 2xx / JSON 解析失败 / 解析结果为空、或相较已有 20 条以上缓存异常缩水超过一半时，一律保留旧快照并进入 30 分钟退避，不覆盖已有好缓存。可疑内容会清除该源 ETag，确保下次完整拉取重新验证；磁盘缓存 `pricing-catalog.json` 损坏或不存在时回退空 payload（= 纯内置表兜底，不影响现有计价能力）。
- 只请求两个公开 JSON URL，不上传任何本地用量 / 账号信息。

**通用**：

- **Fast 分流**：`Pricing.costBreakdown(app:model:speed:...)` 先按档位选择价格。Standard 继续走 A/B 价格链；Unknown 内部返回 nil、金额按 0；Fast 只接受带明确档位语义的在线 rates，models.dev 官方 provider 优先、LiteLLM OpenAI Priority 兜底，命中不到再回落 `codexFastPrices` / `claudeFastPrices`。完整输入 `>272_000` 的 Codex Fast 仍按 0；GPT-5.5 因上游曾存在旧 Priority 价而使用已审计本地固定覆盖，Opus 4.6/4.7 使用固定本地历史价。远端 Fast 条目消失时不删除 last-known rate，避免历史日志突然归零。`billingEquivalentMultiplier` 中 Codex ChatGPT credit 倍率仍只走本地表；Claude 仅在 Standard/Fast 四项非零比例完全一致时允许在线推导。
- **Claude 缓存 TTL**：`Pricing.costBreakdown` 的 `cacheCreation` 表示普通/5m 写入，继续使用模型表中的 1.25× cache-write 费率；新增 `cacheCreation1h` 使用当前 Standard / Fast 基础输入价的 2×，两部分只在 `CostBreakdown.cacheCreation` 汇总，不增加 UI 字段。1h 倍率规则加入价格指纹；Pi/OpenCode 费用口径改变则通过 v12/v9/v6 结构版本自动全量重扫回算历史费用。
- Fast 规则来源（2026-07-16 口径）：[Codex Fast mode](https://learn.chatgpt.com/docs/agent-configuration/speed#fast-mode)、[OpenAI Priority Processing](https://openai.com/api-priority-processing/)、[Claude Fast mode](https://platform.claude.com/docs/en/build-with-claude/fast-mode)。这些规则可能调价，因此价格和倍率都纳入本地指纹。

- 归一化（`Pricing.normalize`）：循环剥 `openai-codex/`、`openai/`、`anthropic/`、`deepseek/`、`opencode-go/`、`commandcode/`、`command-code/` 前缀（Command Code 日志标签为 `commandcode/deepseek/...` 双层，循环剥除直到无前缀）；Vertex 风格 `name@YYYYMMDD` 截断 `@` 前；Anthropic 风格 `-YYYY-MM-DD` 或 `-YYYYMMDD` 后缀剥掉；最后 `lowercased()`；远端目录 key 归一化复用同一套规则。
- 金额用 `Decimal`（`Foundation.Decimal`），单位 USD / 百万 token。`Pricing.cost()` 返回 `Decimal?`：`nil` 表示没有可靠费率，`UsageAggregator.ingest` 聚合时按 0 处理；内部缺价标记继续保留给诊断使用，但 UI 不展示。
- `Pricing.costBreakdown()` 与 `cost()` 使用同一费率选择，返回输入 / 输出 / 缓存读取 / 缓存写入四项 Decimal；返回 nil 时四项费用在 UI 中均按 0 展示。
- `Pricing.fingerprint(knownUsage:)`：哈希内容 = 本地 `table` + `contextPriceTiers` + `timedOverrides` + Standard/Fast 固定本地覆盖 + Fast 本地价格/倍率 + Claude 缓存 TTL 倍率 + 当前用量中实际出现过且远端命中的 app/model/speed 合并价。只算已使用子集，远端新增无关模型无影响。指纹随四份扫描相关缓存写盘，但不再触发自动失效/重算：相关价格变化后历史保持旧价，由用户在设置页「重新计算用量」手动全量重算对齐。

### 7.7 协调（`UsageService`）

- `bootstrap` 同时读取 `usage-rollup.json`、`conversation-rollup.json` 与 `cycle-usage-rollup.json`，立即恢复现有统计、对话列表和周期统计。三个 rollup 的磁盘读取 + JSON 解码（conversation-rollup 实测可达数 MB）放在后台线程执行，不阻塞启动主线程；周期 rollup 与主 rollup 代次一致即恢复，其中 cycleID 已不存在于清理后周期记录的**孤儿桶**单独丢弃，其余桶与 provider 初始重建标记原样保留。孤儿桶来自 `cleaningUpLegacyPayload` 的残片剔除与重叠合并，按 cycleID 末段（该周期 `endAt` 的 epoch 秒，见 `QuotaCycleStore.resetInstant(fromCycleID:)`）定位到时间轴：落在受限重建窗口内的置位 `hasPendingOrphanCycleRebuild`，由 bootstrap 末尾一次受限重建补回；落在窗口外或反解不出时刻的置位 `cycleUsageNeedsManualRecalculation`，在设置页提示用户手动重算，不再自动全量重扫。旧实现把孤儿桶当作整份 rollup 失效，清空聚合器并触发一次不带窗口的全历史重建（实测 2.4GB、约 100 秒 CPU），而每次启动的清理几乎必然产生孤儿桶，等于每次启动都全量重扫。周期 rollup v4 修复受限重建重复累加；载入 v3 或更旧派生数据时丢弃旧 rollup 并自动完整重建一次，`quota-cycle-history.json` 的周期边界与账号段不受影响。
- `scanNow()` 中 Claude / Codex / Pi / OpenCode 并行增量扫描，一批 entries 同时写入 `UsageAggregator`、`ConversationAggregator` 与符合主账号周期条件的 `CycleUsageAggregator`；只有对应聚合结果真实变化时才重新编码 rollup，watermark 变化时才写 scan-state，完全无变化的轮次不写盘。
- **周期扫描的日志变化门控（`UsageLogWatcher`）**：`Scheduler` 走 `scanPeriodically()`，先问 FSEvents 门控要不要扫。原本每轮都会递归枚举全部日志目录并逐文件取 mtime/size——本机实测 2535 个 jsonl / 314 个目录，5 分钟一轮约合每天 180 万次 stat，而绝大多数轮次一个字节都没变。watcher 监听四个 provider 的顶层目录（`~/.claude`、`~/.codex`、`~/.pi`、`~/.local/share/opencode`）而非精确的 sessions 子目录：子目录可能尚未创建，而 FSEvents 只监听建流时已存在的路径，多收无关事件只会多放行一轮，代价远小于漏扫。事件合并窗口 2 秒（门控本身不需要低延迟）。**任何异常都退化成「每轮都扫」**：建流失败、路径全不存在、启动前已发生的写入，一律置位放行；此外无论有没有事件，超过 30 分钟必定强制扫一次兜底 FSEvents 漏报。标记在扫描**开始前**清零，扫描期间产生的新事件由下一轮接手。手动刷新（`refreshNow`）与强制重算（`forceRescan`）直接走 `scanNow` / 全量路径，不受门控影响——用户点了就一定扫。
- **rollup 写盘节流**：三份 rollup 都是全量快照（本机实测 conversation-rollup 3.4MB、scan-state 2.6MB、usage-rollup 139KB、cycle-usage-rollup 47KB），活跃编码时按 5 分钟扫描周期写等于每小时约 74MB、整天 1～2GB 的 SSD 写入，外加每轮 3.4MB 的 JSON 编码 CPU。因此距上次成功落盘不足 `rollupWriteInterval`（15 分钟）时，本轮只更新内存聚合，不重写磁盘快照。UI 实时性不受影响——`publishTotals()` 每轮照常执行，节流的只是写盘。**关键约束：未落盘期间 watermark 必须一并压住**。若只提交 scan-state，重启后会拿到「新 watermark + 旧 rollup」的同代组合，中间那段用量永久丢失；cycle rollup 若单独领先，则会在下轮增量扫描时被重复灌入。因此 `commitsThisRound` 统一裁决三份 rollup 与 watermark 同进同退，盘上永远是「同代同进度」。尚未建立代次（`loadedRollupGeneration == nil`）时必须立刻落盘。节流只作用于常规周期扫描（`allowDeferredWrite: true`）；强制重算与周期重建前的 drain 立即提交，否则后续步骤会基于未落盘状态继续推进。
- **不做退出时 flush**：意外退出或 ⌘Q 的代价只是下次启动多重扫最多一个节流窗口的增量日志（秒级完成），数据不会丢，因此不引入 `terminateLater` 与一份重复的落盘逻辑。
- Claude / Codex 扫描结果会显式上报 JSONL 读取失败。根目录从未存在表示该 Provider 尚无本地会话，是可成功重建为空的正常状态；只有目录存在但无法打开、或 JSONL 实际读取失败才算失败。文件在枚举后、读取前被归档或清理时，`JSONLLineReader` 会复查路径并将其归为正常消失：不增加失败数、不显示警告，本轮保留旧 watermark；Codex 下轮可凭同一会话 ID 在 `archived_sessions` 从原 offset 续扫，避免归档后从 0 重复计入，真正删除的状态则由下轮 alive 集清理。常规增量扫描保留成功文件的结果，失败文件不推进 watermark，并写入 `lastError` 等待下轮重试；初始/受限周期重建按 Provider 隔离，失败侧保留原周期桶，成功侧仍可清桶重灌，避免 Claude 的问题阻塞 Codex（反之亦然）。`lastError` 会在统计页显示可见警告，并提供直达设置页“重新计算用量”的入口。
- 持久化先原子写 `usage-rollup.json`、`conversation-rollup.json` 与 `cycle-usage-rollup.json`，最后提交 `scan-state.json` watermark；四份文件共享 generationID。任一保存失败都会删除 scan-state、设置 `lastError` 并让下次扫描强制全量重建，不能把部分写入当成成功刷新。
- `QuotaCycleStore` 只记录功能启用后主账号 primary / secondary 中实际观察到的 `.weekly` 与 `.fiveHour`；不反推启用前周期，模型专项额度和导入 Codex 账号也不进入周期统计。采样**不按 `is_active` 过滤**：`is_active` 只表示「当前哪个限制在起约束作用」，非当前约束的窗口（如 5 小时未满时的 weekly）同样返回有效 percent / resets_at，过滤会导致周期记录停更、页面停留在旧值。精确 `(accountKey, limitID, resetsAt)` 与 60 秒内抖动优先命中原记录；若 resetAt 发生更大漂移，但同账号 / 同周期类型的旧记录仍有效且已用比例没有明显回落，也只在新旧边界相差不超过 30 分钟时继续更新原周期并保留最早起点，避免无变化的分钟级漂移产生伪周期，也避免低用量提前重置被串入旧周期。命中原记录后，`scheduledEndAt` / `endAt` 只在新旧边界相差 ≥5 秒（`scheduledEndJitterTolerance`）时才改写，避免 `quota-cycle-history.json` 每轮刷新都被无谓重写。**但该容差不足以稳住重建触发**：Codex 的 five-hour `resets_at` 不是固定边界而是持续滚动，实测 39 分钟内后移 2279 秒（与墙钟近 1:1），任何有限容差都会被周期性击穿——实测曾让受限重建退化成每个额度刷新周期一次，每次重解析 194MB、约 24 秒 CPU、瞬时 70~190% 占用。因此 `cycleUsagePartition` **不把活跃周期的 `endAt` 计入指纹**（统一记为 `active`），只有周期结束后固定下来的边界才参与比较：活跃周期的右边界只决定它还能容纳多少后续用量，不改变已归集用量的切分方式，新条目本来就由常规增量扫描持续灌入。`startAt`、`allowanceSegments` 与 cycleID 集合照旧参与指纹，它们变化才是真需要重灌的信号。只有已用比例真实回落或旧周期到期才新建周期；新旧周期只有重叠超过 60 秒才会收口旧周期，秒级重叠视为同源边界抖动。相同 `resetsAt` 下的明显回落则在周期内新建 allowance segment，保留重置前后的独立基线。载入 v2～v4 数据时幂等删除秒级残片、合并重叠记录，并按相同回落规则接回相邻漂移片段；只有较 `scheduledEndAt` 提前截断超过 60 秒的相邻片段才是漂移合并候选，且这些片段必须满足**同窗对齐**——与所属周期的恢复时刻差不超过 30 分钟（`windowAlignmentTolerance`）。服务端窗口制式换档（实测 Codex 出现过周四 11:34 → 周一 09:01 对齐切换）会让相邻片段恢复时刻差出数天，合并这类跨窗片段（旧实现）会把整段历史吞成伪长周期（实测 11.4 天），聚合因此多算数千万 Tokens——护栏拒绝后换档片段保留为独立周期。合并结果（漂移合并与重叠去重）的 `scheduledEndAt` 取各片段最早恢复时刻、`startAt` 恒为「恢复时刻 − 窗口长度」，避免漂移链路把起点越拉越偏。去重要求重叠**超过 60 秒**（`overlapDeduplicationMinimum`）且同时满足同窗对齐才算重复记录：相邻的两个真实周期，边界分别由各自采样时刻的 `resets_at` 推出，两侧抖动叠加会让后一周期起点比前一周期终点早亚秒到数秒，这只是边界毛刺；真正的重复来自同一周期的 resetAt 漂移，重叠接近整个窗口（≥5 小时）。此处误判的代价不可逆——`merging` 只保留 base 的 `startAt` / `endAt`，被吞记录覆盖的整段周期历史会永久丢失且无法从日志重建。载入与每次采样末尾执行**超长自检**：周期时长超过「窗口长度 × 1.15」即回写 `startAt = scheduledEndAt − 窗口长度`（正常 7 天窗口只有秒/分钟级抖动，绝不误伤），并让调用方按 partition 变化触发受限重建；load 中发生修复时 `QuotaCycleStore.load()` 会返回修复的 cycle 集合，`AppState` 在 bootstrap 的初始重建之后追加一次 `rebuildCycleUsageForRecentChanges()`——修复只改了内存起点，旧 rollup 桶仍按污染窗口切分，必须重灌受影响周期。服务缺失窗口长度、只能按已知 5H / 7D 长度确定起点时边界为 inferred。
- 同一服务的主账号切换会持久化为半开区间账号时间段；精确请求先按时间段确定账号，再进入对应周期，保证全量重建不串号、环比不跨账号。Claude 主账号键使用规范化 email 的 SHA-256，不落盘明文邮箱；旧版常量键 `claude:primary` 无法还原真实账号，升级后一次性归入当前识别到的 Claude 账号，保留原 cycleID 以继续关联已有 rollup。邮箱缺失时暂退化到旧常量键，待身份可用时再迁移。
- `CycleUsageAggregator` 用请求 `timestamp` 按 `[startAt,endAt)` 同时归入对应周周期与 5H 周期，再按额度段半开区间归桶。首个账号时间段从 `QuotaCyclePayload.trackingStartedAt` 开始；周期重建即使读取空 watermark JSONL，也会排除该时间之前的请求，不读取日聚合残差或 Claude 补录数据。用满预估只使用当前额度段的本机用量和 `maximumUsedPercent - baselineUsedPercent`：观察变化与 Tokens 大于 0 即输出 Token 预估，观察变化与已知费用大于 0 即输出费用预估，`incomplete` 和部分未定价只影响标注；发生重置时用“此前额度段实际用量 + 当前额度段满额预估”，避免把累计费用除以清零后的比例。当前额度段 observed 为 0 时保留本机实际用量，但不生成用满预估或可信度；不能把首次采样的官方快照比例回退成观察增量。
- **周期用量重建分两条路径**：① 冷启动且 cycle rollup 无效（版本升级 / generationID 错代 / 首次启用）时，`rebuildCycleUsageIfNeeded()` 按待完成 Provider 全量重扫对应历史日志。**孤儿桶不再走这条路径**（见 §7 bootstrap 说明），因此它只在真正的代次错配 / 版本升级下触发；v4 rollup 除全局 `initialRebuildCompletedAt` 外还持久化 `initialRebuildCompletedApps`。成功侧独立置位，失败侧保持待重试，因此下次启动只扫描失败侧，不会因一个永久不可读文件让健康 Provider 反复全量重扫；旧 v4 没有该字段时，全局完成时间非空会兼容视为 Codex / Claude 均已完成。② 周期窗口滚动 / 账号段变化时（`recordQuotaCycles` 检测到 partition 变化），`rebuildCycleUsageForRecentChanges()` 做**受限重建**。受限重建先用当前 watermark 跑一次常规增量扫描并正常提交，避免窗口重扫已灌入的新日志被下次增量扫描再计一次。重建基准窗口是最近 8 天，但扫描下限会向前扩展到受影响周期中最早的 `startAt`，保证清桶后灌回跨窗口周期的全部用量，不会逐日削减周期开头。Claude 和 Codex 均按文件 mtime 过滤（Codex 递归扫 `sessions` / `archived_sessions` 两个根目录，因此包含平铺归档和旧日期目录里近期续用的会话），且跳过标题索引构建。`CycleUsageAggregator.rebuildRange` 先清除受影响周期的旧桶，并且只允许扫描条目重新归入同一组周期；空集合直接 no-op，因此相同扫描结果重复执行保持幂等，窗口外历史桶不会被重复追加。受限重建与冷启动全量共用 `commitCycleAggregation` 收尾（聚合 → 落盘 rollup → 更新内存状态）；只有初始重建会更新 Provider 完成集合，受限重建不会把待重试侧误标完成。
- `CodexJSONLScanner` 文件间并行解析（`maxConcurrentFiles = 4` 路 TaskGroup，按会话 UUID 升序合并结果），全量重扫 / 强制重算是主要耗时场景（codex 历史日志可到 GB 级），多核并行显著缩短耗时；跨文件去重与 `cacheCreationKeys` 都在合并阶段完成，单文件解析无共享可变状态。claude / pi / opencode 保持串行（claude 有跨文件 message.id 去重，并行化风险高、收益低）。
- 扫描中再次调用 `scanNow()` 不并发启动第二批，而是登记一次 queued scan；当前批完成后自动补跑，避免刷新点击时恰好有日志追加而漏到下一周期。

### 7.8 个人历史用量补录（`ImportedUsageBackfill`）

- 起因：Claude Code 默认 30 天自动清理本地 `~/.claude/projects` jsonl，早于 cc-bar 扫描到就被删除的日期永久无法重新计算。`bootstrap()` 在常规 rollup 恢复之后，额外读取 `~/Library/Application Support/CCBar/imported-usage-claude-2026H1-gapfill.json`（若存在），按 `existingDays` 过滤掉 cc-bar 已有的日期后 `ingest` 进聚合器；文件不存在时是纯 no-op，不影响其他安装。
- 合并发生在两处，规则相同（按天去重）：`bootstrap()` 合并一次保证首轮扫描前即可展示；`runScan()` 每轮在扫描 entries ingest 之后、快照落盘之前再合并一次。后者仍然必需——结构失效路径会清空聚合器再全量重建，若只在 bootstrap 合并，重建后落盘的快照将丢失补录数据；每轮重新合并保证任何一次落盘都包含补录用量。
- 当前实现只认一个固定文件名，不是通用的多批次导入机制；后续如需支持其他数据源或多个批次，需要先扩展这里再动手补数据。
- 数据来源、过滤规则、如何用 AI 从其他工具（如 cc-switch）里生成同样格式的补录文件，见 [历史用量数据补录指南.md](历史用量数据补录指南.md)。

## 8. 调度（`Scheduler`）

`@MainActor`，持有 AppState 弱引用。三件周期任务共用**单一时基**，不再各起一条 `Task.sleep` 循环：

- **额度**：`quotaInterval` 秒触发一次 `appState.refreshQuotas(reason: .periodic)`。设置项可选 `1 / 2 / 3 / 5 / 10` 分钟，默认 2 分钟；`nil` / 0 表示不排期。
- **用量**：`usageInterval` 秒触发一次 `appState.usageService.scanPeriodically()`（带日志变化门控的周期入口，见 §7.7）。设置项可选 `1 / 2 / 3 / 5 / 10` 分钟，新安装默认 5 分钟；启动时仍立即扫描一次，用户手动刷新也会立即触发。已写入 UserDefaults 的旧选择不迁移、不覆盖。
- **服务状态**：固定 5 分钟触发一次 `appState.refreshServiceStatus()`，与额度/用量解耦（statuspage 变化慢，无需跟随用户的额度刷新间隔）。

`setQuotaInterval` / `setUsageInterval` 在间隔变化时重排该任务并重启循环，对应设置变更的实时生效。

**单一时基与唤醒合并**：循环每次只睡到「最近一个到期任务」，醒来后把落在 `coalescingWindow`（5 秒）内的任务一并执行。2 分钟与 5 分钟的任务因此在 10 分钟处合并成一次唤醒，而不是各自独立唤醒；三条独立循环原本每小时约 72 次唤醒，合并后约 36 次。macOS 的能耗计分里 wakeups/sec 权重很高，这是常驻菜单栏 App 的主要计分项之一。任务顺序执行而非并发——三者都要碰 `@MainActor` 状态，并发只会互相排队并拉长唤醒期。

**系统状态感知**（`NSWorkspace` + 分布式通知，均在主线程投递）：

- **系统睡眠停表**：`willSleepNotification` 取消循环，`didWakeNotification` 以唤醒时刻为新起点重排并立即补跑一次全部任务。`Task.sleep` 走连续时钟，不停表的话合盖数小时后唤醒瞬间会把整段睡眠期积压的周期一次性打出去。
- **不可见降频**：屏幕休眠（`screensDidSleep/Wake`）或锁屏（`com.apple.screenIsLocked` / `...Unlocked`，无公开常量）期间所有间隔 × `powerSavingFactor`（4）。此时菜单栏、Popover、悬浮窗都不可见，高频刷新纯属浪费——尤其额度刷新是网络请求，会反复唤醒 Wi-Fi 无线电，电池上通常比 CPU 更耗电。恢复可见时立即补一次全量刷新，用户解锁看到的第一眼就是新数据。
- **启动时主动探一次锁屏状态**（`CGSessionCopyCurrentDictionary` 的 `CGSSessionScreenIsLocked` / `kCGSessionOnConsoleKey`）：开机自启常发生在锁屏状态下，此时收不到 `screenIsLocked` 通知，不探测就会一路全速跑到用户解锁。

降频倍数与合并窗口都是写死的常量，没有做成设置项。

### 9.2 Popover (`PopoverRootView`)

- 宽 340pt；header（标题 + 副标题 + 状态点 + 刷新/统计/设置/⋯）+ 已启用 Provider 的 `ServiceBlockView`，中间 Divider。
- 状态点 (`headerState`)：取所有已启用主服务的 `lastSuccessAt.max()`，按当前刷新间隔 ×1.5 / ×3 阈值判 live / stale / offline。
- `ServiceBlockView`：主要额度大字百分比 + 固定短标签 + reset 倒计时；五小时显示 `5HOUR`，周额度显示 `WEEKLY`，不随 App 语言切换。存在且不重复时再显示次要额度；Claude 全部模型显示 `ALL`，Fable 专项额度显示 `Fable`。Cursor 把 `cursor-total` 作为主额度，按稳定 ID 追加 Auto / API 两条；`isUnlimited` 显示明确文本而不伪造百分比或进度条。Command Code 主额度为 5 小时（`5HOUR`），次要额度为周额度（`WEEKLY`），辅助额度包含 GOAT 月度额度；Command Code 不展示用量 cost。Codex、Claude、Cursor 共用既有 today/week cost 展示位；Cursor 有任意相交的远端快照时显示已知金额，覆盖缺口由后台补齐，完全没有远端快照才显示占位，不增加专属 tooltip。

- `MenuBarQuotaSelection` 对 Cursor 无论选择主要 / 周 / 两者均只取 `cursor-total`；Auto / API 不是周窗口，避免错误映射和菜单栏拥挤。Unlimited 在视觉上为 `∞`，辅助功能文本为 `Unlimited`。Command Code 支持菜单栏（主要 5H / 周额度 / 两者）与悬浮窗展示。

### 9.3 主窗口

- `MainWindowRootView` 是 TabView，`@Bindable` 绑到 `appState.mainTab`，所以 ⌘1 / ⌘, 切换是把 AppState 的字段改了；`minWidth 1040 / minHeight 520`，`onAppear` 切 `.regular` 激活策略、`onDisappear` 切回 `.accessory`。

## 12. 并发与线程

- AppState / UsageAggregator / UsageService / Scheduler / UsageLogWatcher / FloatingPanelController 全部 `@MainActor`。
- 凭据读取、token 续期、网络请求、JSONL 扫描全部走 `Task.detached(priority: .utility)`，结果回到 MainActor 写入状态。
- `Quota` 系列 client 全部 `nonisolated static`，不依赖 actor 隔离。
- 唯一的 GCD 用法是 `UsageLogWatcher` 的 FSEvents 派发队列（`qos: .utility` 串行队列）——`FSEventStreamSetDispatchQueue` 只接受 `DispatchQueue`。回调是 C 函数指针、不能捕获上下文，因此变化标记放在顶层的 `UsageLogChangeFlag`（`OSAllocatedUnfairLock` 保护，`Sendable`）里，用 `Unmanaged` 指针经 `FSEventStreamContext.info` 传入；刻意不嵌套进 `UsageLogWatcher`，因为嵌套类型会继承外层的 `@MainActor` 隔离，而这个盒子必须能在后台回调里直接访问。
- `Scheduler` 的系统通知回调用值型 `SystemEvent` 而不是闭包传递动作，避免把非 `Sendable` 闭包捕获进 `addObserver` 的 `@Sendable` block。

## 13. 已知技术债 / 持续关注

- **Claude CLI 兜底依赖外部进程**：用户没装 CLI 时会失败，目前只在 API 失败且无缓存的手动刷新触发，影响面有限。
- **B 类模型历史精度**：远端价格目录（LiteLLM / models.dev）只提供「当前单一价」，没有历史分段，B 类模型的历史用量一律按当前合并价重算。若某个 B 类模型实际曾经调过价、需要精确历史计价，需升级为 A 类、手工加进 `Pricing.swift` 的 `timedOverrides`（发版维护）。A 类模型（GPT-5.6 / GPT-5.5 阶梯价、Claude Sonnet 5 固定价）不受此限，远端零参与。
- **特殊规则仍需手维护**：`contextPriceTiers` / `timedOverrides` / Fast 历史固定覆盖以及 Codex ChatGPT credit 倍率仍需同步 `Pricing.swift`；改表后由 `Pricing.fingerprint(knownUsage:)` 自动失效缓存触发重扫。其余 Standard/Fast 扁平价可由 `PricingCatalogStore` 后台补齐。
- **seen ID 上限 20000**：极端长时间使用 + 大量 sidechain 引用可能导致环形丢失；目前足以覆盖正常使用。对 Codex fork 去重的含义是：若父会话的记录已被挤出 seen 集合（本机实测约相当于两个月的 `token_count` 量），此后才 fork 它，重放段会重新计入一次。
- **受限周期重建不做 fork 去重**：`rebuildCycleUsage` 走 `previous: [:]` + `minimumMtime` 只扫窗口内文件，seen 集合从空开始。若 fork 会话的父文件 mtime 落在窗口外没被扫到，其重放段会重复计入该周期桶。主界面的日用量与费用走全量增量路径，不受影响；要修需要在枚举后沿 `forked_from_id` 把祖先文件补进扫描集（只用于灌 seen、entries 丢弃）。
- **没有自动更新通道**：`UpdateChecker` 只做版本比对与跳转 Release 页，不下载也不替换安装（ad-hoc 签名未公证，自动替换会被 Gatekeeper 拦）。出包由 tag 触发的 GitHub Actions 完成，用户仍需手动下载覆盖；若要做静默更新需另接 Sparkle 并配套 Developer ID 与公证。

## 14. 导入账号（其他 Codex 账号）

用户可在设置页手动粘贴 `~/.codex/auth.json` 内容，为 cc-bar 添加任意多个 Codex 副账号（仅查看配额，不影响 CLI 的当前登录状态）。

### 14.1 设计原则

- **凭据与默认账号解耦**：默认账号始终来自实时读取 `~/.codex/auth.json`（cc-switch 切号也跟着变）；导入账号是独立副本，各自维护 token，绝不写回 `~/.codex/auth.json`。主 Codex 启用且导入账号与当前默认账号身份相同时，额度展示与刷新状态复用默认账号快照，不再读取导入 token 或重复请求官方接口；同时把当前默认账号 token 同步到该导入账号的 Keychain 副本，修复导入凭据长期未更新导致的后续刷新失败。主 Codex 关闭时不做镜像，可见导入账号使用自身 Keychain 凭据独立刷新。
- **允许重复（仅存储 / 管理界面）**：同一账号 ID 可以同时出现在默认槽和导入列表，语义不同（「当前 CLI 登录」vs「已导入的持久监控副本」）。存储层与设置页作为管理界面保留双份、不去重；刷新时镜像默认账号数据。**纯展示界面（Popover、统计页）则按身份去重**，同一账号只显示一次（见 §14.8）。
- **同 ID 覆盖**：再次粘贴相同账号时静默覆盖 token（保留 alias / visible 设置），避免悬空旧 token。
- **Team 账号区分用户**：账号身份用 `{chatgpt_account_id}:{chatgpt_user_id}` 复合键，同一 Team account 下不同 user 视为独立条目；缺失 `chatgpt_user_id` 时退化为单段 `chatgpt_account_id`（老数据兼容）。HTTP 请求里的 `ChatGPT-Account-Id` header 仍只取前半段。

### 14.2 存储

| 数据 | 位置 | 说明 |
|---|---|---|
| 元数据（id / alias / email / planType / visibleInPopover / addedAt） | `Application Support/CCBar/imported_codex_accounts.json` | 原子写，JSON version = 1。`id` 为 `{account_id}:{user_id}` 复合键 |
| Token 三件套（access / refresh / id） | macOS Keychain，`service = com.cc-bar.codex.imported`，`account = ImportedCodexAccount.id`（复合键） | SecItem 直接读写，不弹用户授权 |
| 额度快照缓存 | `quota-cache.json` 的 `importedCodex` 字段（`[String: QuotaCacheRecord]`） | 重启时立即显示上次数据 |

### 14.3 Token 续期回写隔离

`CodexTokenRefresher.ensureFreshAccessToken` 新增 `writeBack: WriteBack` 参数：
- `.codexAuthJSON`（默认）：续期后覆盖写回 `~/.codex/auth.json`，与现有行为一致。
- `.importedAccount(id:)`：续期后仅更新 Keychain 对应条目，不碰 `~/.codex/auth.json`。

### 14.4 刷新调度

`AppState.loadAllImportedCodexQuotas(reason:canMirrorPrimary:)` 在 `refreshQuotas` 中调用，对所有 `visibleInPopover = true` 的导入账号：
- 分批并发，每批最多 3 个同时 in-flight（chunked TaskGroup）。
- 每个账号独立维护 `QuotaRefreshState`（backoff / inFlight / lastSuccessAt），互不影响。
- 主 Codex 启用、且导入账号与当前默认 Codex 账号匹配时（优先 `{chatgpt_account_id}:{chatgpt_user_id}`，任一侧缺 user_id 时退回纯 account_id），直接镜像 `codexQuota / codexQuotaError / codexRefreshState`，不续期、不请求第二次 `wham/usage`；若默认账号有 `access_token`，先比较导入账号现有 token，只有 access / refresh / id 任一变化时才写 Keychain。主 Codex 关闭时跳过镜像，导入账号按独立账号链路刷新。

### 14.5 排序

- 列表顺序即 `imported_codex_accounts.json` 中 `accounts` 数组顺序,Popover「其他账号」按相同顺序展示。
- 设置页支持拖动排序:每行 `.draggable(account.id)` + `.dropDestination(for: String.self)`,放下后调 `AppState.reorderImportedCodexAccounts(orderedIds:)` 写回 `ImportedCodexStore.saveAll`,再触发 `reloadImportedCodexAccounts` 同步运行时。
- 新增的账号追加到列表末尾;`reorderImportedCodexAccounts` 对未在传入 ids 中的条目自动追加到末尾,避免丢失。

### 14.6 Paste 解析（ImportedCodexPaste）

支持三种粘贴形态：
1. **完整 auth.json**（`{OPENAI_API_KEY, tokens: {...}, ...}`）
2. **裸 tokens 子对象**（`{access_token, refresh_token, ...}`）
3. **personal access token**（`{"OPENAI_API_KEY": null, "personal_access_token": "at-..."}` 或裸 `{"personal_access_token": "..."}`）

形态 1/2 解析优先级：`tokens.account_id` → `access_token` JWT payload → `id_token` JWT payload。
email / planType 从 `id_token` 解，缺 id_token 时再从 `access_token` 的 JWT 里找。

形态 3（PAT）由 `ImportedCodexPaste.personalAccessToken(in:)` 识别（仅在无 OAuth tokens 时命中）。PAT 不透明、本地解不出 `account_id`，因此走独立路径：保存时由 `AppState.importCodexPersonalAccessToken(token:visibleInPopover:)` 联网发一次 `wham/usage` 验证令牌并拿回 `account_id` / `user_id` / `email` / `plan_type`，组出复合 id `{account_id}:{user_id}` 落库，并置 `ImportedCodexAccount.isPersonalAccessToken = true`。该字段为可空 Bool（兼容旧数据，nil 视为 false）；刷新时（`loadImportedCodexQuota`）PAT 账号跳过续期、直接用令牌、不带 `ChatGPT-Account-Id` header。

### 14.7 额外重置 credit（懒加载，主账号 + 导入账号）

`CodexResetCreditsClient.swift` 独立封装 `GET wham/rate-limit-reset-credits`，与 `wham/usage`（额度快照）完全解耦：不参与 `QuotaSnapshot`、不写入 `quota-cache.json`、不接入 `Scheduler` 定时刷新。

- 入口：设置页「账号」组的 Codex 主账号行、以及「其他 Codex 账号」每行都有一个 `gift` 图标按钮，点击打开「使用限额重置」弹窗（420 × 300pt Sheet），打开时按需拉取数据（不持久化）。
- 取数：
  - 导入账号：`AppState.fetchImportedCodexResetCredits(account:)`，token 处理与 `loadImportedCodexQuota` 一致（PAT 直接用令牌，OAuth 账号先 `CodexTokenRefresher.ensureFreshAccessToken(writeBack: .importedAccount(id:))` 续期）。
  - 主账号：`AppState.fetchCodexResetCredits()`，与前者对称，用主账号 token（PAT 直接用令牌，OAuth 账号 `writeBack: .codexAuthJSON` 续期），`accountId` 取 `codexAccount.accountId`（PAT 传 nil）。
  - 两者都不接入 backoff / inFlight 状态机，也不做「镜像默认账号」优化——每次打开都用对应账号自己的 token 独立请求。
- 展示：主账号行与导入行复用同一份 UI 组件 [`CodexResetCreditsSheet`](../Settings/CodexResetCreditsDetailView.swift)（`CodexResetCreditsState` 三态：loading / success / failure），顶部展示「总可用额度」浅绿胶囊标签 `可用 N 次` + 下方卡片列表逐条展示 credit 的 `title`（如「完全重置（每周 + 5 小时）」）与到期时间 `将于 yyyy-MM-dd HH:mm 到期`（本地时区，`DateFormatter` 默认 `.current` 时区自动换算）。

### 14.8 展示层去重

同一 Codex 账号同时是「当前 CLI 登录（默认槽）」和「已导入副本」时，纯展示界面按身份去重，只显示一次；设置页作为管理界面不去重（见 §14.1）。

- 判据：`AppState.importedCodexAccountMirrorsPrimary(_:)`（`internal`，供展示层共用）——`chatgpt_account_id` 相等，且 `chatgpt_user_id` 相等或有一方缺失。
- **Popover**（[PopoverRootView](../MenuBar/PopoverRootView.swift) + [OtherCodexAccountsSection](../MenuBar/OtherCodexAccountsSection.swift)）：主 Codex 卡片会展示时（`includesCodex`），「其他账号」分区传 `dedupPrimary: true` 隐藏镜像项；PopoverRootView 用去重后的计数决定分区与其前置 Divider 是否渲染，避免悬空分隔线。Codex 服务被关闭走 `!includesCodex` 分支时**不去重**，避免唯一账号整体消失。
- **统计页**（[StatsView.timelineSections](../Main/StatsView.swift)）：主账号时间线段标题为 `Codex`（不再出现「主账号」字样）；仅当主账号段已展示时，跳过与它同身份的镜像导入段。历史存储 key 不变，被隐藏项的历史仍在盘上，只是不展示（身份随 CLI 切号漂移）。
