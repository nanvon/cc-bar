# 草案 · 统计页改版与项目分析技术方案

> 状态：**已实施**（2026-09-28 编写，`589191e` 三期一次落地，随 v1.1.0 发布）。实施偏差：第 3 期周期桶加可选 `conversationKey`，未升 payload 版本（旧桶计入「其他」）；对话页项目筛选也改用统计页项目身份。以下为原方案。对应需求：[草案-统计页改版与项目分析-需求.md](草案-统计页改版与项目分析-需求.md)（下称「需求」）。本文详写第 1 期（概览改版），第 2、3 期只记录已核对的代码事实和实施前需要处理的点，开工前再补细节。
>
> 前置工作已合入：历史保护与安全恢复（`67ef704`）、性能与功耗等价优化批次 A–D（`StatsOverviewModel` 单次派生 + revision 缓存）。

## 1. 结论

- 第 1 期需要一个**按时间范围的项目汇总**。现有 `ConversationAggregator` 已经保存 `(对话, 天, 模型, 速度)` 桶和每个对话的项目身份，项目汇总直接从这些桶派生，**不改存储格式、不改扫描器、不触发重扫**。
- 「未归属」定义为**残差**：概览总量减去能归属到对话的用量。这样 P03（各项目 + 其余 + 未归属 = 概览总量）按构造成立，不依赖对所有来源逐一建模。
- 第 1 期不新增侧栏视图。「项目」视图随第 2 期上线，「额度」合并随第 3 期上线；第 1 期里指向项目页的入口改为跳转对话页并按项目筛选（§5 决策 3）。
- 第 2 期的分支与 worktree、第 3 期的周期按项目拆分都需要额外数据，见 §8。

## 3. 数据口径

### 3.1 过滤条件

项目汇总、高消耗对话与概览 KPI 使用**同一组过滤**，否则 P03 不成立：

- 时间：`StatsDateInterval current`，半开区间 `[from, to)`，按桶的 `day` 过滤。
- 服务：`visibleApps`（设置里开启且可用的统计服务）∩ 侧栏服务筛选。
- 金额：桶的 `costUSD`（即「API 等值」），无价桶按 0 计，`hasUnpricedUsage` 向上传递，与现有面板一致。

### 3.2 项目汇总

对范围内每个对话桶，按其 `ConversationInfo.projectKey` 累加 `UsageTotals` 与 `UsageSpeedBreakdown`，同时记录每个项目的 `lastAt`、对话数与服务构成。缺 info 的桶不计入任何项目。

`special:unassigned`（无明确项目）和 `special:ccbar-system`（CCBar 系统任务）照常汇总，但在「用量构成」里不参与前 4 排名，并入「其余 N 个项目」（§5 决策 2）。

### 3.3 未归属

```
未归属(app) = 概览日桶合计(app) − 项目汇总合计(app)      // 在同一组过滤下
```

逐服务计算后再求和，并对 Tokens 四类与金额分别计算。本地来源正常情况下残差来自补录数据、早于对话统计上线的历史日桶，以及缺 info 的对话桶；Cursor 全部进入残差。

残差只可能因为数据异常变成负数（对话桶多于日桶）。实现上逐项 `max(0, …)` 截断，同时用 `AppLog.debug(.usage, …)` 记录一次（不记项目名），不在界面上显示负值。测试覆盖这种情况，保证 P03 在正常数据下精确成立。

需求 §3.1 的说明文字是「未归属：Cursor 远端用量和补录数据没有项目信息」。残差里还包括早期历史，第 1 期文案改为「未归属：Cursor 远端用量、补录和早期历史数据没有项目信息」。第 2 期未归属详情再把本地残差拆成来源行（§8.1）。

## 4. 第 1 期设计

### 4.1 模型层

**`ConversationAggregator.overviewBreakdown(_:)`**（新增，放在 `ConversationAggregator.swift`）

```swift
nonisolated struct ConversationOverviewRequest: Hashable {
    var revision: UInt64          // 调用方传 aggregator.revision
    var from: Date
    var to: Date
    var apps: Set<UsageApp>       // visibleApps ∩ 服务筛选
    var topConversationLimit: Int // 5
}

nonisolated struct ProjectUsageRow: Sendable, Equatable, Identifiable {
    var key: String
    var name: String
    var path: String
    var status: ConversationProjectStatus
    var totals: UsageTotals
    var speed: UsageSpeedBreakdown
    var totalsByApp: [UsageApp: UsageTotals]
    var conversationCount: Int
    var lastAt: Date
    var id: String { key }
}

nonisolated struct ConversationOverviewResult: Sendable {
    var projects: [ProjectUsageRow]               // 按 API 等值降序，同值按名称
    var attributedByApp: [UsageApp: UsageTotals]  // 残差计算用
    var topConversations: [ConversationSummary]   // 按 API 等值取前 N
}
```

- 对范围内桶**只遍历一次**，同时得到项目行、按服务的已归属合计、每个对话的合计（取前 N 个）。
- 独立 memoize（`cachedOverview`），`markChanged()` 时一起清空。不复用 `query(_:)`：`query` 只缓存一份结果，概览与对话页交替请求会互相挤掉缓存。
- `ConversationSummary` 复用现有类型，高消耗对话行的标题、项目、分支、日期都从 `info` 取。

**`StatsOverviewModel` 扩展**

- `StatsOverviewInput` 增加 `conversationRevision: UInt64`。任一 revision 变化都重新派生，与现有缓存机制一致。
- `build` 增加参数 `conversationOverview: ConversationOverviewResult`。日桶遍历保持一次；构成面板的四个维度在遍历结束后由已有中间结果组装：
  - 服务：`totalsByApp` + `speedByApp`（已有）。
  - 提供商：`providerGroups`（已有），按 API 等值排序后取前 3，其余合并为「其他」。
  - 模型：跨服务合并 `modelRowsByApp`（同名模型跨服务合并，副标显示来源服务），取前 5，其余合并为「其余 N 个模型」。
  - 项目：`conversationOverview.projects` 取前 4（跳过 special 行），其余 + special 行合并为「其余 N 个项目」，另加「未归属」行（§3.3）。
- 新增值类型 `CompositionRow { id, kind(.item / .rest / .unattributed), title, subtitle, totals, speed, colorRole, action }` 和 `CompositionDimension { service, provider, model, project }`，面板只读结果。
- 删除 `ProviderSort` 的使用点（需求 §3.1：排序统一按 API 等值）；`ProviderGroup.sorted(_:by:)` 保留 `.cost` 分支或简化为只按金额，按实际引用情况决定，不留死代码。

- 日桶遍历次数不变（一次）。新增一次对话桶的范围遍历，由 `ConversationAggregator` 的 memoize 和 `StatsOverviewCache` 双层缓存，悬停、切换维度、展开提供商都不触发重算。
- 取前 N 个对话用一次线性扫描 + 小顶堆（或排序后截断，N = 5 时差异可忽略，按代码简洁选排序截断，但只对范围内对话排序）。
- 扫描轮次没有新数据时两个 revision 都不变，概览不重算，保持性能方案批次 D 的效果。

## 5. 实施决策（已定）

**决策 1：项目汇总放进第 1 期。** 需求第 1 期的「用量构成」包含项目维度和「未归属」行，P02、P03 都要验。汇总只在内存中从对话桶派生，风险和工作量可控，第 2 期项目页直接复用同一结果。

**决策 2：「无明确项目」和「CCBar 系统任务」在构成面板里并入「其余 N 个项目」。** 与需求 §4.1（项目列表里这两行固定排末尾）和 §5（周期拆分里并入「其他」）保持一致。它们是真实的本地用量，所以不算进「未归属」。

**决策 3：第 1 期指向项目页的入口改为跳转对话页。** 项目行点击：跳转对话页并按该项目筛选。「未归属」行：第 1 期无点击。「全部项目 ›」：第 1 期不显示。第 2 期上线项目页后改回需求 §3.1 的目标。

**决策 4：第 1 期侧栏保持 `概览 / 对话 / 时间线 / 周期`。** 「项目」随第 2 期加入，「时间线 + 周期 → 额度」随第 3 期合并。每期都能单独发版，不会出现空入口。

**决策 5：「API 等值」只替换概览 KPI 与新面板里的金额称呼。** 对话页、Popover 等其他位置的「费用」文案不在第 1 期改动范围内，避免一次改动波及多个界面；如需统一另行确认。

## 8. 第 2、3 期实施前需处理的点

### 8.1 第 2 期：项目页

- **worktree 归属**：worktree 目录下的 `.git` 是文件，内容 `gitdir: <主仓库>/.git/worktrees/<名称>`。在 `nearestGitRoot` 找到 `.git` 文件时读取这一行，沿 `commondir` 得到主仓库根；主仓库路径不在家目录或落在受保护目录时不读取，按独立项目显示（P07）。
- **不迁移已存身份**：已保存的 `ConversationInfo.projectKey` 保持不变，在查询层增加「worktree 路径 → 主仓库 key」映射（按唯一项目路径 memoize，文件系统检查次数等于唯一路径数）。这样不需要升级 `ConversationRollupPayload` 版本，也不需要重扫；worktree 本身的路径与分支供「仓库与 worktree」区块使用。
- **分支**：Codex 从 `session_meta.payload.git.branch` 读取，写入 `ConversationSeed.gitBranch` 与 `ScanFileState.conversationGitBranch`。已扫描过的旧 Codex 文件不会重新产生 seed，需要一次性只读每个文件首行补齐分支（只读 `session_meta`，不读正文）；Pi、DSH 日志暂未确认有分支字段，分支列显示「—」。
- **未归属详情的来源行**：Cursor 行取 Cursor 日桶合计（精确）；本地残差行按「补录与早期历史」合并显示，日期区间和服务从残差非零的日桶得到。补录与早期历史在日桶里无法区分，是否要单独标出补录需要产品确认。
- **首次整理状态**：项目页的「正在整理历史对话」复用 `UsageService.isScanning` 与 `ScanProgress`；判断「无缓存」用 `conversationAggregator.isEmpty`。

### 8.2 第 3 期：额度页

- **周期按项目拆分需要新数据**：`CycleUsageBucket` 没有对话维度，对话桶只有天粒度，无法映射到 5 小时窗口。需要给周期桶加 `projectKey`（或 `conversationKey`），`CycleUsageRollupPayload` 升到 v5 并触发一次周期重建。重建只能覆盖本机日志仍在的时间段，更早的周期按「其他」显示。
- 其余内容（周期卡与时间线同屏、`官方 N%` 状态色、变动明细折叠）是现有 `CycleStatsView` 与时间线视图的重排，不涉及数据变更。
