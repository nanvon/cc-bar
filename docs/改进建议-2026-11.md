## 1. 价格规则远端化

**现状**

- v1.1.0 到 v1.1.40 约 6 周发了 40 版，其中近 10 次提交与价格有关；v1.1.40 只为新增 Claude Fable 5.2 / Mythos 5.2 价格。
- `Core/Usage/Pricing.swift`（1110 行）里的基础价表、阶梯价（`contextPriceTiers`）、分段价（`timedOverrides` 等）、Fast 价与倍率都是代码常量。
- 远端目录（`PricingCatalogStore`，LiteLLM / models.dev）只能补 Standard / Fast 扁平价，阶梯、分段、倍率进不来。技术实现 §13 已把这点记为技术债。

**问题**

每次官方调价或出新模型都要发版，用户要升级后才有正确费用；升级前新模型费用显示为缺价。

**建议**

把规则表从代码常量改成数据文件：App 内置一份作为兜底，远端放一份（仓库 Release 资产或 raw 文件），用签名校验后热更新。现有的「规则指纹变化后自动重建历史」（§7.5d）可以直接复用，改动集中在「静态表 → 可加载数据」。

**待核实**

- Sparkle 的 ed25519 密钥是否适合复用来签价格文件，还是单独一把密钥更清楚。
- 规则文件的格式要能表达现有全部规则类型（阶梯、按日期分段、Fast 固定价、倍率、长上下文 Fast 价、Codex credit 倍率），需要逐项对照 `Pricing.swift`。
- 远端规则版本比 App 新、出现 App 不认识的规则类型时的降级行为。
- 远端规则回滚或被篡改时，历史不应被反复重建。

### 实施补充

**规则类型清单**（逐项核对 `Pricing.swift` 得出，数据文件要能表达前 11 类）

| # | 代码符号 | 内容 |
|---|---|---|
| 1 | `table` | 模型 → 四项基础价 |
| 2 | `contextPriceTiers` | 模型 → 阈值 + 短 / 长上下文两套完整价 |
| 3 | `timedContextPriceTiers` | 阶梯价的分段生效（`from` + 整套阶梯） |
| 4 | `timedOverrides` | 基础价的分段生效；`from` 有的是 UTC 日界，有的精确到小时（DeepSeek 用 `utcInstant`） |
| 5 | `fixedLocalOverrideKeys` | 禁止远端目录覆盖的固定价 key |
| 6 | `codexFastPrices` / `claudeFastPrices` | Fast 档价，按 App 分两张表 |
| 7 | `fixedFastLocalOverrideKeys` | Fast 档禁止远端覆盖的 key |
| 8 | `timedCodexFastPrices` | Codex Fast 的分段生效 |
| 9 | `codexFastLongContextPrices` / `timedCodexFastLongPrices` | Codex Fast 长上下文价及其分段 |
| 10 | `codexFastMultipliers` / `claudeFastMultipliers` | 计费等效倍率 |
| 11 | `claudeCacheCreation1hMultiplier` | 全局常量，当前为 2 |
| 12 | `ModelIdentity.aliases` / `variantTags` / `buildTagPattern` | 模型名解析规则，经 `ruleSignature` 进入价格指纹 |

建议第一版只把 1–11 做成数据。第 12 类和取价算法留在代码里，包括：`price()` 里写死的 `app == .codex, inputTotal > 272_000`（Fast 长上下文阈值）、按 App 的 `switch`、`codex-auto-review` 不计价、`derivedClaudeFastMultiplier`、`resolveCostBreakdown`。`normalize(model:)` 用的 `identityPrefixes` 是存储身份的一部分，代码注释写明不能改，不进数据文件。

**读代码后发现的必须处理的问题**

1. **`precondition` 会崩溃。** `localOverrideKeys` 初始化时有 5 个 `precondition`（分段价的 key 必须在基础表里有对应行等）。规则来自远端后，一份不满足约束的文件会让 App 启动即崩溃。要改成加载时校验，校验失败整份拒绝并继续用当前生效的规则；内置文件的约束用单测保证。
2. **指纹是进程内常量。** `cachedLocalPricingFingerprint` 是 `static let`，只算一次。规则可热更新后，指纹要跟随规则快照计算。
3. **规则切换时机。** `PricingCatalogStore` 用 `active` / `pending` 两份快照，只在扫描开始前 `commitPending()`，保证同一轮扫描的计价和最终指纹读同一份价格。规则文件必须用同样的机制，在同一个时机切换。`Pricing.cost()` 被各 Scanner 同步调用，规则读取要保持同步（`PricingCatalogStore` 用 `OSAllocatedUnfairLock`，可照做）。
4. **规则变化会立即触发完整重建。** `UsageRebuildBasis.rebuildReason` 对 `.localPricing` 没有最短间隔，指纹一变就重扫全部日志。远端化之后要防止反复重建：
   - 规则文件带单调递增的 `revision`，App 只采纳比本地已采纳值更大的文件，并把已采纳值持久化。这样远端回滚、CDN 返回旧缓存都不会触发重建。
   - App 升级后内置文件可能比缓存的远端文件新，启动时取 `revision` 较大的一份。
   - 是否给远端规则变化加 24 小时最短间隔（与现有 `.remotePricing` 一致，原来缺价的用量命中新价格时仍立即重建）：**待用户决定**。
5. **Decimal 精度（实测）。** 现有价格由浮点字面量构造，部分值不精确：`0.0028` 实际是 `0.002800000000000000512`，`0.044` 是 `0.04399999999999998976`，`0.56`、`0.28`、`0.07`、`1.11`、`0.014`、`0.003625` 同样有尾差；`0.435`、`0.175`、`1.32` 等是精确的。数据文件应把价格存成字符串、用 `Decimal(string:)` 解析，这样部分价格会和现在差 1e-19 量级。后果有两个：本地价格指纹必然变化，所有用户升级后重建一次历史（每次改价表发版本来也会这样，可接受）；对费用做精确相等断言的测试可能失败，失败时要逐个确认差异确实只是尾差，不要为了通过测试去改数据。
6. **等价验收。** 价格规则的测试集中在 `CCBarTests/QuotaParsingTests.swift`（约 56 处 `Pricing` 调用）和 `DshPricingTests.swift`，都经公开接口断言。改成数据文件后这些测试除第 5 点的尾差外应全部通过。另外加一个结构对照测试：改造前把 `localPriceBody()` 的输出按规则类型拆开存成 fixture，改造后逐项比较 key 集合和数值，用来发现漏迁的条目。
7. **测试隔离。** `PricingCatalogStore` 在单测里用空目录（`AppRuntime.isRunningUnitTests`）。规则存储也要这样：单测只读内置文件，不读用户目录，不联网。
8. **与远端目录的分工不变。** 有阶梯、分段或固定价的 key 仍属于 A 类，远端目录（LiteLLM / models.dev）不参与。`remoteRate(for:)` 里的三条排除规则必须和 `price()` 的取价顺序保持一致，否则 `remotePricingSignature` 会记错，引起多余重建或漏重建。
9. **未知规则类型。** 文件带 `schemaVersion`。App 遇到比自己高的版本整份拒绝，不做部分解析；发布新规则类型时先发支持它的 App 版本，过渡期内远端文件保持旧 `schemaVersion`。

**待用户决定**

- 签名密钥：复用 Sparkle 的 EdDSA 密钥（App 侧用 CryptoKit 的 `Curve25519.Signing.PublicKey` 和 Info.plist 里的 `SUPublicEDKey` 验证），还是另生成一把。复用可以少管理一把密钥。`sign_update` 能否直接签任意文件需核对。密钥操作按 `docs/打包发布.md` 由维护者执行。
- 规则文件放在哪里、谁来签。私钥在 CI secret 和维护者钥匙串里，签名只能在这两处做。可选做法：规则文件提交到 main 后由一个 workflow 签名并上传到固定 tag 的 Release 资产。这需要新增 CI workflow。

**建议步骤**

1. 把 1–11 类常量搬进内置数据文件，`Pricing` 改为从加载结果取价；行为等价，可独立发布。
2. 规则存储（`active` / `pending`、扫描前切换、指纹随快照计算、加载校验）。
3. 远端获取、验签、`revision` 采纳规则、本地缓存。
4. CI 签名流程和文档（`docs/技术实现.md` §7.6、§11、§13；`CLAUDE.md` 增加「只改价格不发版」的流程）。

**结论（2026-11-11）**

- 已按四步实施：价格数据在 `Resources/pricing-rules.json`（revision 1），`Core/Pricing/PricingRules.swift` 负责解码与整份校验，`PricingRulesStore.swift` 负责 active / pending 快照、远端验签、revision 采纳与缓存，`.github/workflows/pricing-rules.yml` 负责签名发布。单测 `PricingRulesTests`。
- 待用户决定的三项：签名复用 Sparkle EdDSA 密钥（`sign_update -p` 已用于签 `release-notes.md`，可签任意文件）；规则文件放固定 tag `pricing-rules` 的 prerelease，由 CI 签名；远端规则变化不加 24 小时最短间隔。
- 内置文件的选择：说明写在每条的 `note` 字段，不参与指纹；内置文件读不出来时记日志、按全部未定价运行，不崩溃。
- 等价核对：用改造前代码导出的本地价格体与新文件算出的价格体，按 1e-9 舍入后逐字一致；差别只在第 5 点列出的 10 个浮点尾差值，因此升级后所有用户会重建一次历史。
- 未验证：单元测试未运行；workflow 尚未在 GitHub 上跑过，首次推送规则文件到 main 后需要确认 prerelease 与两个资产生成正常。

## 2. 用量事实表（SQLite），并重写 2.0 草案

**现状**

- 本机 `usage-history/current.json` 为 13.7MB：对话汇总 6.5MB（5148 个对话）、扫描进度 3.0MB、周期桶 2.1MB、消息账本 1.7MB。
- 每次提交的开销：编码整份 → 读回旧 current 并完整解码校验 → 写 `previous.json` → 写 `current.json`（`Core/Storage/UsageSnapshotStore.swift` 的 `commit`）。常规扫描有 15 分钟写盘节流（`UsageService.rollupWriteInterval`）。
- 落盘的是日 / 对话 / 周期聚合，逐条用量（`UsageEntry`）只在内存里流转。
- `quota-history-today.json`（约 680KB）和 `quota-cycle-history.json`（约 430KB）是整份重写。更正：前者已有 15 分钟写盘限速（`AppState.quotaHistoryWriteInterval`），后者只在周期记录变化时写，都不是每次刷新都写。

**问题**

- 体积随对话数线性增长，整份驻留内存、整份重写。目前可接受，一两年后未必。
- 只存聚合意味着价格或统计规则一变就要回原始日志重算，而 Claude 日志会被自动清理；日志已删除的部分只能保留旧值。
- 小时级趋势、请求级缓存分析、「哪个对话用掉了这个 5H 窗口」这类功能缺少数据基础。

**建议**

认同 `草案-CCBar2.0-设计方案.md` 的方向（持久化用量事实、单写入服务、分页查询）。但该草案基线是 v1.0.55，其中「项目分析」已在 1.x 落地（见 `docs/README.md` 草案表），一致快照与安全重算也已实施。2.0 的范围可以收窄为「事实表 + 旧历史迁移 + 查询层」，草案需要按当前代码重写一遍再评审。

**待核实**

- 事实表的数据量：本机全量约 11 万条用量记录（技术实现 §7 的实测），估算体积和索引成本。
- 现有一致快照（current / previous / quarantine）的保护语义在 SQLite 下如何等价保留。
- 旧聚合与新事实并存期间的覆盖范围管理（草案 §5 已有设想，需对照现状）。
- 是否值得先只把额度历史两个文件改成追加写，作为低风险的第一步。第二轮结论：不值得。这两个文件已经限速或只在变化时写，改追加写要引入新的文件格式和压缩逻辑，收益小。

### 实施补充

这一条分成两个任务：先重写草案（只改文档），评审通过后再拆实现任务。不要在同一个任务里既写方案又写代码。

**草案里已经落地、重写时应删除或改写的部分**

- 项目分析（草案 §二、批次 F）：已在 1.x 落地。
- 一致快照、安全重算、恢复状态（草案 §五「迁移后的重算」、§九「历史保护」「故障恢复」）：已由 `UsageSnapshotStore` + `UsageHistoryConsistency` 实现，见 `docs/技术实现.md` §7.5d。
- 去重集合上限（草案 §三「去重与更正」的出发点）：已由 `UsageMessageLedger` 解决。
- 价格版本与重算依据（草案 §六的一部分）：已有 `UsageRebuildBasis`。
- 性能批次 A / B：`docs/README.md` 草案表记录「性能与功耗等价优化方案」批次 A–D 已落地，需核对与 2.0 草案批次 A / B 的对应关系。

**重写草案必须回答的问题**

1. **各来源的事件键。** 账本现在只存摘要（`SeenIDSet.digest`，SHA-256 前 8 字节）。Claude 用 `message.id`，Codex 用 `会话 id#累计用量签名`，Pi 用 `entryID@timestamp`。OpenCode、DSH 按会话整体替换，没有逐条稳定键，事实表对它们只能是「按会话替换一组行」。Antigravity 的做法需核对。8 字节摘要能否直接当主键（碰撞概率、能否反查）要评估。
2. **已删除日志的历史没有逐条事实。** 这部分只能以现有对话桶的粒度（会话、日、模型、速度）迁入，查询层要长期支持两种粒度并存，小时趋势对这部分数据不可用。覆盖范围的单位建议用「对话」：现有重建规则就是按对话记账（日志还在的以重扫为准，日志已删的保留原用量，`UsageRebuildMerge`），沿用它比草案 §五设想的日期范围覆盖更简单，也不会和现有语义冲突。
3. **事实表字段。** 要让改价后的重算不再依赖原始日志，事实必须保存 `Pricing.resolveCostBreakdown` 的全部输入：app、原始模型名、speed、input、output、cacheRead、cacheCreation、cacheCreation1h、totalTokens、inputTotal、时间、`reportedCost`、`reportedBreakdown`。现在被保留的已删除对话重算时是估算（缓存写入全按 5 分钟价、长上下文按桶内平均判断），原因就是缺这些字段。
4. **金额的存储。** SQLite 没有十进制类型。用 TEXT 还是定点整数要定下来，并保证迁移前后逐位相等。现有 JSON 里 `Decimal` 的编码方式需核对。
5. **一致性语义的对应。** 「一份文件 = 一笔提交」可以由事务代替。`previous.json`（整体回退到上一笔提交）和 `quarantine/`（保留故障证据）没有直接对应物，要给出做法，例如定期用备份 API 生成上一份完整库、用 `PRAGMA quick_check` 判定损坏。「版本不支持时只读、不覆盖」的规则要落到 `user_version` 上。现有故障注入测试（`UsageSnapshotStoreTests`、`UsageHistoryRecoveryTests`、`UsageSafeRebuildTests`）覆盖的每个场景，都要在新存储下有对应用例。
6. **依赖。** 工程的 SPM 依赖只有 Sparkle 和 zstd。`OpencodeScanner`、`AntigravityScanner`、`CursorAuth` 已经在用系统 `sqlite3` 读外部数据库。新存储建议直接用系统 `sqlite3`，不引入第三方库；现有三处的封装方式需核对是否可复用。
7. **降级。** 新库启用后，用户手动装回旧版时，旧版会继续读写旧 JSON，两边数据分叉。要定规则：新版是否继续维护旧 JSON、维护多久、再次升级时以哪边为准。
8. **数据量。** 本机约 12 万条用量记录，每行加索引粗估 150–200 字节，总量在 20MB 左右，比现在的 13.7MB 大，但改成增量写。需要用真实数据实测。

**建议的实现分期**（写进新草案）

1. 双写：事实表只写不读，JSON 仍是唯一事实来源；诊断里输出两边的对账结果。这一期出问题删库即可，不影响用户数据。
2. 选一个只读场景切到新查询层（例如对话明细），其余仍读 JSON。
3. 旧汇总迁入、全部查询切换、停写 JSON。只有这一期不可逆，应单独发版并保留旧文件。

## 3. Provider 抽象与并发刷新

**现状**

- `Core/AppState.swift`（3059 行）里每个额度服务各有一套 `beginXxxRefresh` / `storeXxx` / `markXxxFailure` / `loadXxx` / `loadXxxQuota`，六套代码几乎相同（约 2577–2800 行可直接对比）。
- 复制的代码里有细微差异，例如 `storeClaude` 只在来源为 API 时清除退避，其余服务无条件清除。这个差异应该是有意的，但放在复制代码里不容易被审查到。
- `refreshQuotas` 对各服务逐个串行 `await`（约 575–610 行）。Claude / Cursor 请求超时为 30 秒，前面的服务超时会推迟后面所有服务。
- 接入 Command Code 的提交（`b37860f`）改了 24 个文件。

**问题**

每加一个服务都要复制一套状态机并改多处 `switch`；复制越多，各服务行为不一致的风险越大。串行刷新让单个服务的网络问题影响全部服务的新鲜度。

**建议**

抽出 Provider 协议（凭据加载、取数、身份键）和通用的刷新状态机（inFlight、退避、最小间隔、成功 / 失败落状态、写缓存），各服务只保留真正不同的部分。服务之间并发刷新，仍遵守各自的 429 退避。2.0 草案 §8 认为「无需先完成拆分」；如果后续还会继续加服务，这一条的回报是明确的，可以独立于 2.0 做。

**待核实**

- 各服务之间真实存在的差异清单（Claude CLI 兜底、Desktop 借用、Cursor 远端用量联动、导入 Codex 账号镜像主账号、Antigravity 的 agy 优先）。抽象必须能容纳这些，不能为了统一而改行为。
- 并发刷新对 `QuotaPersistenceCoordinator` 的批次提交、额度通知去重是否有影响。
- 现有 `QuotaRefreshPlanTests`、`QuotaParsingTests`、`QuotaAlertTests` 对刷新流程的覆盖程度，重构前是否需要先补行为测试。

### 实施补充

**建议范围收窄。** 读完代码后，不建议做「Provider 协议 + 通用状态机」：

- 状态存储已经统一了。`PrimaryQuotaState` 和 `updatePrimaryState(_:_:)` 按 `QuotaApp` 存 snapshot / error / source / refresh，`codexQuota`、`claudeRefreshState` 这些只是访问器。
- 真正重复的是三组函数：`beginXxxRefresh`（7 份，含导入账号）、`storeXxx`（7 份）、`markXxxFailure`（7 份），以及 Cursor / Command Code / OpenCode Go 三份几乎相同的「401 后重读本地凭据，凭据变了才重试一次」。
- 各 `loadXxxQuota` 的主体差异很大，`loadAntigravityQuota` 尤其如此（agy CLI 优先、套餐查询、多处身份守卫），套进通用流程会把差异变成一堆开关。

建议做法：把三组函数改成按 `QuotaApp` 参数化的单一实现，加一张小的服务配置表；401 重读抽一个辅助函数；各 `loadXxxQuota` 保留为独立函数。这与 2.0 草案 §八「避免先搭一套暂时没有消费者的通用框架」一致。预计减少两三百行，主要收益是差异集中在一张表里，便于审查。

**各服务的真实差异**（v1.1.40 逐项核对，参数化后必须原样保留）

| 行为 | 差异 |
|---|---|
| 定时刷新的最短成功间隔 | Antigravity 是写死的 120 秒；其余用 `minSuccessInterval`（60 秒） |
| 成功后清除 429 退避 | Claude 只在 `source == .api` 时清除（CLI 兜底成功不清）；其余无条件清除 |
| 写额度历史（`recordQuotaHistory`） | Codex、Claude、Antigravity、导入账号写；Cursor、Command Code、OpenCode Go 不写 |
| 写周期记录（`recordQuotaCycles`） | 只有 Codex、Claude |
| 缓存记录的 `accountID` | Codex / Claude 用 `QuotaHistoryAccountKey`；Antigravity 用 email；Cursor 用 `userID`；Command Code / OpenCode Go 用 `accountKey`；导入账号不填 |
| 令牌续期 | Codex 用 `CodexTokenRefresher`（PAT 跳过）；Claude 用 `ClaudeTokenRefresher`，凭据过期且是手动刷新时走 CLI 兜底；Antigravity 自行续期，401 后强制续期重试一次；Cursor / Command Code / OpenCode Go 不续期 |
| 401 重读本地凭据 | Cursor 只认 401；Command Code、OpenCode Go 认 401 和 403；都排除代理拦截的响应（`looksLikeInterceptedResponse`） |
| 提醒版本号变化时 | Codex、导入账号：丢弃本次结果，不落状态。其余：照常落状态，只是不产生提醒 |
| 提醒版本号取样时机 | Codex 在令牌续期之前；Claude、Antigravity 在续期之后；其余在入口。Command Code、Antigravity 回填账号字段会递增版本号，必须在写回账号之前比较 |
| 不产生提醒的来源 | Claude CLI 兜底、Antigravity agy CLI（都没有可核实的账号身份） |
| 取数后的额外步骤 | Claude 查 profile；Antigravity 查套餐和邮箱；Cursor 无论额度成败都拉远端用量；Codex PAT 回填身份；Command Code 回填账号详情；导入账号可镜像主账号并同步令牌 |

**并发刷新**

- 这些函数都在 MainActor 上，并发后是在 `await` 处交错执行，没有数据竞争。`quotaCache`、`dirtyQuotaFiles`、`quotaHistory`、`quotaCycles` 都是在两个 `await` 之间同步修改的。
- 必须保留的顺序：
  - 导入账号在主 Codex 完成之后。`mirrorPrimaryCodexQuota` 复制的是主账号本轮刚取到的快照。
  - 每个服务内部先 `loadXxx()` 再 `loadXxxQuota()`。
  - Cursor 的四步顺序：`loadCursor` → `handleCursorAccessRequest` → `loadCursorQuota` → `refreshCursorRemoteUsage`。
- `quotaRefreshBatchDepth`、`logQuotaSummary()`、`scheduleQuotaPersistenceFlush()` 留在所有服务完成之后，Codex 和 Claude 同时滚动周期时仍只重建一次。
- 需核对：`handleClaudeDesktopAccessRequest` 和 `handleCursorAccessRequest` 可能弹出授权说明窗口，并发后两个窗口可能同时出现。可以把这两个调用挪到所有服务完成之后顺序执行，挪动前要读它们的实现确认没有依赖取数前的状态。
- 需核对：`loadCodex` 等在后台任务里启动 `/usr/bin/security` 子进程，并发后首次授权时可能同时出现多个钥匙串弹窗。
- `bootstrap()` 里的串行加载不在本条范围内。
- 各服务的请求超时：Claude、Cursor 30 秒，Antigravity 15 秒，Command Code、OpenCode Go 10 秒。串行时最坏情况是这些相加。

**测试现状**

`QuotaRefreshPlanTests`（15 个用例）只覆盖刷新计划的开关矩阵。各 `loadXxxQuota` 直接调用静态的 `XxxQuotaClient.fetch`，没有注入点，刷新状态机目前无法做单测。不建议为此引入网络 mock。可行的做法是把「是否开始刷新」的判断抽成纯函数（输入：当前 `QuotaRefreshState`、刷新原因、当前时间、服务配置；输出：是否开始和新状态），对纯函数写测试，覆盖 inFlight、退避中、最短间隔、手动刷新不受最短间隔限制这四种情况，以及上表前两行的差异。

**建议步骤**

1. 抽出刷新判断的纯函数并写测试；逐个服务把 `beginXxxRefresh` 换成调用它，每个服务一个提交。
2. `storeXxx` / `markXxxFailure` 参数化，同样逐个服务替换。
3. 抽出 401 重读凭据的辅助函数。
4. 并发刷新，单独提交、单独验收。

手动验收点：断网时各服务保留旧快照并显示网络错误；某个服务返回 429 后 10 分钟内不再请求，其他服务不受影响；切换账号后不出现「新账号 + 旧额度」；导入账号与主账号同身份时只请求一次；额度提醒不重复。

## 4. Developer ID 签名与公证

**现状**

`scripts/build.sh` 做 ad-hoc 签名，不公证。凭据读取统一走 `/usr/bin/security` 子进程，原因之一是避免 Keychain Services API 的授权弹窗。

**问题**

- 用户首次打开需要手动绕过 Gatekeeper。
- 做不了 WidgetKit 小组件、App Group、iCloud 同步等需要正式签名身份的能力。
- ad-hoc 签名每次构建身份不同，App 自己写入钥匙串的条目（导入 Codex 账号、手动 API Key）在更新后是否需要重新授权，**未验证**。

**决定（2026-11-11）**

用户确认不购买 Apple 开发者身份，本条不实施，继续用 ad-hoc 签名。由此确定的约束：

- 不做 WidgetKit 小组件、App Group、iCloud 同步。后续需求涉及这些能力时直接排除。
- 首次安装需要手动放行 Gatekeeper 的现状不变。
- 第 6 条的对外入口不能依赖签名身份（见该条补充）。

**仍需验证的一件事（与是否付费无关）**

App 自己写入钥匙串的条目有两处，都直接调用 `SecItem`：

- `ImportedCodexStore`：导入的 Codex 账号令牌，service 为 `com.cc-bar.codex.imported`。
- `AntigravityCredentials` 的续期缓存：service 为 `com.nanvon.ccbar.antigravity-refresh`。

ad-hoc 签名的身份随每次构建变化，新版本读取旧版本写入的条目时，系统可能弹出授权框或拒绝访问。Antigravity 那处读取时设置了 `interactionNotAllowed`，读不到会当作没有缓存，影响小。`ImportedCodexStore` 没有这个设置。本机的 `imported_codex_accounts.json` 只有 42 字节（空列表），所以维护者本机经历的 40 次升级没有覆盖到这条路径。

验证方法：安装版本 N，导入一个 Codex 账号并确认额度能刷新；通过应用内更新升级到 N+1；观察是否弹出钥匙串授权框、导入账号的额度是否还能刷新。如果会弹窗或失败，再决定处理方式（例如令牌改存到权限为 600 的文件）。这一步需要真机操作，模型无法代做。

## 5. 本地数据权限与临时文件清理

**现状**

- `~/Library/Application Support/CCBar/usage-history/current.json` 与 `~/Library/Logs/CCBar/ccbar.log` 权限为 644，`CCBar` 目录为 755。快照里有对话标题（来自用户输入的片段）和项目路径。
- 本机 `Application Support/CCBar/` 下留有 6 个 `*.sb-*` 文件和 1 个 `.bak-*` 文件，时间在 8–9 月。`.sb-*` 是原子写的临时文件，写入中途进程退出时留下，目前没有清理逻辑。

**问题**

单用户机器上风险低，但这些文件内容属于 `AI数据分析指南.md` 自己定义的敏感范围，权限应当与之相称。

**建议**

目录改 700、文件改 600（创建时设置，启动时对已有文件修正一次）；启动时清理超过一定时间的 `*.sb-*` 残留。

**待核实**

- `.sb-*` 的确切来源（哪条写入路径、什么情况下被中断）。
- 旧格式文件（`usage-rollup.json`、`conversation-rollup.json` 等，迁移后只读不写）是否可以在确认迁移成功后归档或删除，本机这几个文件合计约 5MB。

### 实施补充

**权限**

- 实测：`Data.write(to:options: .atomic)` 覆盖已有文件时保留原权限，把文件改成 600 后再原子写，仍是 600。所以已有文件在启动时修正一次就够，不需要改每个写入点。新建的文件按 umask 得到 644。
- 目录改成 700 后，其他用户无法进入目录，目录内的所有文件（包括新建的 644 文件和原子写的临时文件）都读不到。文件 600 是第二层保护。
- 写入点有十几处，各自 `createDirectory` 后 `write(.atomic)`：`QuotaCache`、`QuotaHistoryStore`、`QuotaCycleStore`、`QuotaAlertStore`、`ScanCache`（两处）、`ConversationRollupCache`、`CycleUsage`、`CursorUsageCache`、`DshContributionCache`、`PricingCatalogStore`、`ImportedCodexStore`、`UsageSnapshotStore`（三处）、`AppLog`。不要逐个修改。建议在启动早期加一个函数：以 700 创建或修正 `Application Support/CCBar`、其下的 `usage-history`、`usage-history/quarantine` 和 `Logs/CCBar`，再把这些目录里的普通文件改成 600。各写入点的 `createDirectory` 在目录已存在时不会改权限，不用动。
- 不在范围内：`CodexTokenRefresher` 和 `AntigravityCredentials` 里写的是其他工具自己的凭据文件，权限由那些工具决定，不要改。

**临时文件清理**

- `.sb-*` 的来源：文件名形如 `<目标文件名>.sb-<8 位十六进制>-<6 位字符>`，是 Foundation 原子写的临时文件，进程在写入过程中被终止时留下。本机残留对应 `quota-cache.json`、`quota-cycle-history.json`、`quota-history-today.json`、`usage-rollup.json`，日期在 8 月 13 日到 9 月 6 日之间，之后没有新增。
- 清理规则要保守：只处理 `CCBar` 和 `usage-history` 两个目录的直接子项，不递归；只删文件名匹配上述模式且修改时间早于 24 小时的文件。不认识的文件一律不动，包括 `.bak-*`、`imported-usage-*`（用户补录的历史数据）、`ClaudeProbe/`、`codex_wakeup_log.json`、`quarantine/` 里的全部内容。

**旧格式文件**

`usage-rollup.json`、`conversation-rollup.json`、`cycle-usage-rollup.json`、`dsh-contributions.json` 在 `usage-history/established` 标记存在后不会再被读取。它们是迁移前历史的最后一份旧副本，删除不可恢复，建议本条不处理。`cursor-usage-rollup.json` 仍在使用，不是旧文件。

**文档**：同步 `docs/技术实现.md` §11 持久化清单。

**结论（2026-11-11）**

- 临时文件清理已实施：`Core/Storage/AtomicWriteLeftoverCleaner.swift`，`AppState.bootstrap()` 开头在后台执行，规则同上；单测 `AtomicWriteLeftoverCleanerTests`。
- 权限部分不做：上一级 `~/Library/Application Support` 和 `~/Library/Logs` 在 macOS 默认就是 700，其他用户账号已经读不到；同一用户下的进程不受文件权限限制，改成 600 也挡不住。

## 6. 对 Agent 开放只读数据

**现状**

仓库里没有对外接口：没有 CLI、URL scheme、AppIntents、CSV 导出。`docs/AI数据分析指南.md` 约定的脱敏导出器也尚未实现。

**想法**

- 提供一个只读入口（命令行工具，或 Claude Code statusline 脚本，或 MCP），输出各服务的剩余额度、重置时间、用满预估。Agent 可以据此决定是否开始长任务，用户也可以在终端状态栏直接看到额度。
- 脱敏导出器可以并入同一个入口，输出 `AI数据分析指南.md` 定义的脱敏分析文件。

**待核实**

- 产品上是否需要：这是新方向，不在现有产品需求里。
- 数据来源：直接读 `quota-cache.json` 会把文件格式变成对外契约；通过 App 进程提供则需要进程间通信。
- 输出内容的隐私边界（账号标识、项目名）应沿用 `AI数据分析指南.md` §1 的规则。

### 实施补充

要不要做、做成什么形态**待用户决定**。下面是决定要做时的建议。

- 第 4 条已确定继续用 ad-hoc 签名，App Group 共享容器不可用。AppIntents 不要求付费身份，但 ad-hoc 签名下能否在「快捷指令」里稳定注册没有验证过。
- 建议的最小形态：App 在额度落盘时另写一份专供外部读取的文件，例如 `Application Support/CCBar/export/quota.json`。它有独立的 `schemaVersion`，只含各服务的剩余比例、重置时间、更新时间，不含账号标识。Claude Code statusline 脚本或 Agent 只读这个文件。这样内部的 `quota-cache.json` 格式不会变成对外契约，也不需要进程间通信。
- 文件里要带每个服务的更新时间。App 没有运行时文件内容是旧的，由读取方判断是否过期。
- 第 5 条把目录改成 700 后，同一用户的进程仍然可以读，两条不冲突。
- 写入应挂在现有的 `QuotaPersistenceCoordinator` 批次里，不新增独立的写盘时机。
- 脱敏导出器是另一件事，工作量主要在 `AI数据分析指南.md` 定义的脱敏规则上，建议拆成单独的任务。
