# 打包发布

本文只记录 cc-bar 当前工程的打包步骤。工程产物名为 `CCBar.app`，显示版本和 Sparkle 比较的构建版本均使用 `MARKETING_VERSION`（当前见 `ccbar.xcodeproj/project.pbxproj`）；发布版本必须按 `X.Y.Z` 逐版递增。不要保留固定的 `CFBundleVersion = 1`，否则后续更新无法识别。

## 0. 默认方式：`scripts/build.sh`（推荐，日常都用这个）

日常打包分发**只用**仓库自带的脚本，不要走下面第 1/2/4 节的 Archive 流程——那套会引入本机的 "Apple Development" 开发证书，产物只能在本机运行，拷给别人会打不开，也没有必要为了自用而覆盖 `/Applications` 里正在跑的安装。

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer   # 一次性，确保指向完整 Xcode
SPARKLE_PUBLIC_ED_KEY="已配置的公钥" ./scripts/build.sh                # 产物: dist/CCBar.dmg + dist/CCBar.app.zip
```

- 脚本内部用 `CODE_SIGNING_ALLOWED=NO` 做 Release 构建，然后按 Sparkle 的 XPC services、Autoupdate、Updater.app、framework、外层 App 顺序逐层 ad-hoc 签名。签名时不使用 `--deep`；最终用 `codesign --verify --deep --strict` 验证整个包。
- 正式打包必须传入有效的 `SPARKLE_PUBLIC_ED_KEY`，并将其写入 App 的 `SUPublicEDKey`。未配置时脚本在清理和构建前停止。工程的 App Target Debug / Release 配置保存相同的公开默认公钥，供本地 Xcode 构建使用；CI 用 GitHub variable 显式传入，发布生成器会验证 App 与 CI 公钥一致。Debug 开发构建不需要私钥；未内置公钥的开发 App 不能用于自动更新验收或分发。
- 当前仍不使用 Developer ID 证书或公证。主程序为兼容 ad-hoc 的 Sparkle framework 关闭 Library Validation；这与 Sparkle 的 EdDSA 下载包验证是两回事。首次手动安装仍受 Gatekeeper 与设备管理策略约束，不能保证所有 Mac 都无提示启动。
- 产物固定在 `dist/CCBar.dmg` 和 `dist/CCBar.app.zip`（`dist/` 已 gitignore，不进版本库）。
- DMG 用于首次手动安装，打开后将 `CCBar.app` 拖到 `/Applications`；ZIP 同时用于应用内自动更新与备用分发。不能从只读 DMG 内运行 App 后直接覆盖该安装。
- 想验证打包是否正常，在临时目录或 DMG 中查看，不要直接替换 `/Applications/CCBar.app`。
- 详见 [README.md「从源码构建」](../README.md#从源码构建)。

### GitHub Actions 自动发布

仓库配置了 [.github/workflows/release.yml](../.github/workflows/release.yml)：推送 `v` 开头的 tag 后，GitHub 的 macOS runner 校验更新签名配置和发行说明，执行 `scripts/build.sh`，用 SPM artifact 内同版本 Sparkle 的 `sign_update` 签名，上传全部产物到 draft Release，再发布。只有上传完整后，新的 `latest` 更新源才可见。

Release 包含五个产物：

- `CCBar.dmg`：手动安装包。
- `CCBar.app.zip`：由 App 内置公钥验证的自动更新包。
- `appcast.xml`：已签名的 Sparkle 更新源，含版本、最低 macOS、固定版本 ZIP 地址、大小、包签名和日志地址。
- `release-notes.md`：按版本聚合的完整 Markdown 更新日志，已签名；单版源文件和 Release 正文仍保持原样。
- `version.json`：保留 `{"tag","version","page"}`，供尚未含 Sparkle 的旧客户端继续检查新版本并打开发布页。

更新源地址固定为 `https://github.com/nanvon/cc-bar/releases/latest/download/appcast.xml`。其中安装包和本次日志引用 `releases/download/vX.Y.Z/...` 的固定版本资产，避免检查后下载到了另一版；完整历史入口引用最新 `release-notes.md`。本地 `build.sh` 只生成 DMG / ZIP，不生成上述更新源；没有更新私钥也能在传入公钥后打包。

生成器 `scripts/generate-update-feed.py` 校验 tag、App 版本、更新源、公钥与签名配置，并用 `lipo -archs` 读取实际 App 主执行文件架构：仅有 `arm64` 时在 appcast 标明 Apple Silicon 硬件要求，避免向 Intel Mac 提供不能运行的包；不改变现有打包架构，架构缺失或未知则停止发布。随后用 App 内置公钥再次验证最终 ZIP 的签名，阻止公私钥不匹配的产物发布，再签名历史日志和 appcast；**签名后不得修改这些文件或重新压缩 ZIP**。App 配置 `SURequireSignedFeed` 与 `SUVerifyUpdateBeforeExtraction`，只接受经过验证的更新源和包。

首个含 Sparkle 的版本仍需手动安装一次。旧版只有检查和跳转功能，无法自动把新更新器装进自己；保留 `version.json` 使这次迁移仍可被发现。后续更新允许用户在应用内下载、安装并重新启动；是否需要管理员凭据取决于安装目录所有权与系统策略。

### 首次配置更新签名密钥

此配置只需一次，并在首次发布含 Sparkle 的版本之前完成。**不要因普通发版重新生成或更换公钥**；现有用户的信任来自 App 内置公钥，丢失私钥可能需要再次手动安装。

1. 在本机解析完 SPM 依赖后，找到对应 Sparkle artifact 的 `bin/generate_keys`。例如 Xcode DerivedData 的 `SourcePackages/artifacts/sparkle/Sparkle/bin/`；脚本构建后则位于 `build/SourcePackages/artifacts/sparkle/Sparkle/bin/`。
2. 手动运行 `generate_keys --account cc-bar`。官方工具在登录钥匙串中保存私钥并显示公钥；已有同账户密钥时会复用，不覆盖。再次查看公钥用 `generate_keys --account cc-bar -p`。
3. 在 GitHub 仓库 **Settings → Secrets and variables → Actions → Variables** 添加 `SPARKLE_PUBLIC_ED_KEY`，值为显示的公钥。公钥可以公开，同时将相同值保存到工程 App Target 的 Debug / Release `SPARKLE_PUBLIC_ED_KEY` 构建设置；本地脚本打包仍用相同值显式传入。
4. 由维护者用 `generate_keys --account cc-bar -x <安全的私钥备份路径>` 导出私钥，并在 **Secrets** 添加 `SPARKLE_PRIVATE_ED_KEY`，值为该文件内容。私钥只经标准输入交给签名工具，不进入参数、构建设置、仓库或输出日志；导出文件必须存放在受保护的位置并安全备份。
5. 确认变量和 secret 均已配置。缺少任一项，CI 在构建前失败；格式或配对错误，CI 在创建 Release 前失败。

本说明中的密钥生成、钥匙串访问和 GitHub 配置由维护者明确执行；普通代码修改不执行这些操作。详细格式见 [Sparkle 官方配置](https://sparkle-project.org/documentation/)、[官方签名工具源码](https://github.com/sparkle-project/Sparkle/blob/2.x/sign_update/main.swift)。

runner 镜像默认预装的 Xcode 版本可能落后于本地(如 macos-15 runner 默认 Xcode 16.4，SDK 停在 macOS 15.5)，用旧 SDK 编译出的 App 在新版 macOS 上会渲染成旧一代系统外观，和本地新 Xcode 编译的效果不一致。workflow 里用 `maxim-lobanov/setup-xcode@v1` 把 Xcode 固定为 `latest-stable`，跟随 runner 镜像自动使用当前最新稳定版，避免这个问题。

```bash
git push origin main
git tag v1.0.0          # 版本号要和 project.pbxproj 里的 MARKETING_VERSION 一致，且改动已提交
git push origin v1.0.0
```

只有用户要求查看发布结果时，才查询仓库 Actions 或 Release 状态。CI 与本地脚本的 App 同为 ad-hoc 签名；CI 另外生成并签名更新源。

**更新日志放在哪**：唯一源文件仍是与 tag 同名的 `release-notes/vX.Y.Z.md`。发布前，AI 会对比上一个 tag 与本次真实改动撰写说明；工作流将全文原样作为 Release 正文，并自动聚合历史生成 App 内日志。HTML 注释从生成的聚合日志中移除。格式和撰写规则见 [release-notes/README.md](../release-notes/README.md)。

> 版本号从 `v1.0.0` 重新起算。仓库早期用过不带 `v` 前缀的 `0.x.y` 裸版本号 tag，属于历史遗留，新发布不再接续那条线。

完整的「提交代码 → 版本号+1 → 构建打包」标准流程（含 AI 代执行的固定步骤）见 [CLAUDE.md](../CLAUDE.md) 的「标准发布流程」一节。

下面第 1–4 节保留给需要 **Developer ID 签名 + 公证** 发布给他人（例如上架、企业分发）的场景，日常迭代不需要看。

## 1. 打包前检查（仅 Developer ID 场景需要）

1. 用完整 Xcode 打开 `ccbar.xcodeproj`，不要只安装 Command Line Tools。
2. 在 Xcode 左侧选中项目 `ccbar`，进入 target `ccbar` 的 `Signing & Capabilities`。
3. `Team` 选择你的 Apple Developer 账号。
4. `Bundle Identifier` 保持 `com.nanvon.ccbar`。如果这个 id 已被占用，改成你自己的唯一 id，例如 `com.yourname.ccbar`。
5. 顶部 scheme 选择 `ccbar`，运行目标选择 `Any Mac` 或本机 Mac。

## 2. 只给自己用（不推荐，优先用第 0 节脚本）

1. Xcode 菜单选择 `Product` -> `Archive`。
2. Archive 完成后会打开 Organizer。
3. 选择刚生成的 archive，点击 `Distribute App`。
4. 选择 `Copy App`，导出 `CCBar.app`。
5. 把 `CCBar.app` 拖到 `/Applications` 后启动。

这种方式签名用的是本机 "Apple Development" 证书，只适合自己电脑使用，发给别人时对方会遇到 Gatekeeper 的"无法验证开发者"提示；且第 0 节脚本已覆盖这个场景，一般不需要走 Archive。

## 3. 发给别人用（需要 Developer ID 证书）

需要 Apple Developer 账号和 Developer ID 证书。

1. Xcode 菜单选择 `Product` -> `Archive`。
2. Organizer 中点击 `Distribute App`。
3. 选择 `Developer ID`。
4. 选择 `Upload` 让 Apple notarize。
5. notarization 成功后导出 `CCBar.app`。
6. 压缩成 zip 后发布，例如：

```bash
ditto -c -k --keepParent CCBar.app CCBar.app.zip
```

## 4. 命令行归档（仅 Developer ID 场景需要）

如果要用命令行走 Developer ID 流程，先确认 `xcodebuild` 指向完整 Xcode：

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

归档：

```bash
xcodebuild archive \
  -project ccbar.xcodeproj \
  -scheme ccbar \
  -configuration Release \
  -archivePath build/CCBar.xcarchive
```

Developer ID 导出：

```bash
xcodebuild -exportArchive \
  -archivePath build/CCBar.xcarchive \
  -exportPath build/export \
  -exportOptionsPlist ExportOptions-DeveloperID.plist
```

导出成功后，app 在 `build/export/CCBar.app`。

## 5. 常见问题

- 如果 `xcodebuild` 提示 active developer directory 是 Command Line Tools，说明没有切到完整 Xcode，按第 4 节先执行 `xcode-select`。
- 如果签名失败，先回到 Xcode 的 `Signing & Capabilities` 检查 Team 和 Bundle Identifier。
- 如果设置里的「开机自动启动」提示 `Operation not permitted`，通常是当前 App 不是签名导出的 `.app`，或没有从 `/Applications/CCBar.app` 启动。用第 0 节的 `scripts/build.sh` 重新打包，打开 `dist/CCBar.dmg` 后手动确认再拖到 `/Applications`（会覆盖已有安装，替换前先确认这是你想要的）；同时检查「系统设置 -> 通用 -> 登录项与扩展」里 CCBar 是否被禁用。
- 如果只是自己使用，不需要 notarization；如果发给别人长期使用，建议走 Developer ID + notarization。
