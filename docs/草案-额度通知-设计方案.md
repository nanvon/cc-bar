## 多服务扩展（2026-10-09，当前实现范围）

用户已确认直接扩展现有通知机制，以下范围优先于后文保留的原始 Codex 方案。

| 服务 | 监控窗口 | 通知身份 |
|---|---|---|
| Codex | 默认与已启用导入账号的 5 小时、周额度 | account ID + 可选 user ID，保留现有镜像归一 |
| Claude Code | 当前会话、全模型周额度、未明确禁用的模型专属周额度 | account UUID + 可选 organization UUID，缺 UUID 跳过 |
| Antigravity | Gemini／Claude 的 5 小时与周窗口；兼容非分组 Gemini 独立字段 | 已有 UserInfo 流程取得的邮箱摘要，未取得时跳过 |
| Cursor | Total／Auto／API 的实际计费周期 | 本地已解析的 user ID |
| Command Code | 5 小时、周、已解析的月额度 | whoami 的 user ID + 可选 org ID，缺 user ID 跳过 |

共用阈值（默认 20%）和声音偏好。总开关改为「开启额度提醒」，默认关闭、兼容旧 Codex 开关；三个窗口开关为 5 小时／会话、周额度（包含模型周额度）、计费周期（Cursor 和 Command Code 月额度），默认全选、至少保留一项。服务全局关闭即不提醒，单独关闭菜单栏或悬浮窗展示不影响提醒。

所有 API 成功入口（含 Cursor／Command Code 凭据重读后的成功重试）接入；沿用刷新与 429 退避，不增加额度请求。Claude CLI 兜底输出没有可核实账号身份，继续显示额度但不触发提醒。缓存、失败、镜像和历史补记不产生观察。

不同服务身份隔离，同服务按实际 limit ID 独立去重；Codex 保留原 kind 键，Antigravity 非分组第三方窗口映射到分组 Claude ID。通知标题写服务名，正文包含实际窗口、模型或分组；同次刷新多个低额度窗口合并一条。缺失／无效／禁用窗口跳过，无限额度不提醒，Cursor 超过套餐上限视为剩余 0%。

计费周期采用真实重置时间与长度，允许自然月长度变化，不假设为 5 小时或周窗口；未知时间沿用两次独立恢复证据，显示继承时间不作为换周期证据。各入口携带账号和设置版本，异步刷新／身份回填后校验，旧账号结果不能发送给新账号。

提醒文件升级 v2，兼容读取 v1，缺服务字段视为 Codex，保留原摘要、窗口键和占用状态。重建先备份原文件，为所有入口保存基线标记，每个窗口首次有效观察低于阈值时只记为已提醒；后来出现或后来选中的窗口也单独建立基线。文件不存明文邮箱／登录名、token、通知正文或完整额度。

## 1. 原始 Codex 方案：结论与建议范围

功能可行。当前已有 Codex 额度窗口、剩余比例、重置时间、定时刷新和多账号身份信息，可以在成功刷新后判断是否提醒，不需要新增额度接口请求或推送服务器。

主要工作是通知权限、重复提醒控制、周期识别、账号身份归一和异常恢复。显示一条系统通知本身不是主要难点。

第一版建议采用以下范围，均为待评审的产品建议：

| 项目 | 第一版建议 |
|---|---|
| 服务 | 仅 Codex，包含默认账号和已启用的导入账号 |
| 监控指标 | 5 小时与周额度的剩余百分比；不使用本地 Tokens、费用或请求数推算 |
| 默认状态 | 额度提醒默认关闭，升级不弹权限窗口 |
| 默认阈值 | 20%，支持 5%～50%，步长 5%；两个窗口共用阈值 |
| 窗口选择 | 5 小时、周额度分别可选，默认都选中 |
| 触发条件 | 成功取得新额度，且剩余比例严格小于阈值 |
| 重复控制 | 每个实际账号、每个窗口、每个识别出的周期最多提交一次正常提醒 |
| 首次开启 | 下一次成功刷新时，已低于阈值且本周期未提醒，也提醒一次 |
| 声音 | 默认关闭，提供独立开关，遵从系统权限 |
| 点击通知 | 打开 CCBar 主窗口的统计页；不承诺定位到具体账号或额度卡 |
| 数据保存 | 偏好进入 `SettingsStore`；提醒记录单独保存，不混入额度历史 |

原始 Codex 第一版不包含（其他 Provider 已由上述扩展覆盖）：按账号单独阈值、多级阈值、额度耗尽后的第二次提醒、额度恢复通知、预测耗尽时间、邮件/Webhook/手机推送、自动切账号、额外后台守护进程，以及绕过专注模式的紧急通知。

这些是本方案控制范围的建议，不是对后续需求的限制。

方案编写前仓库没有 `UserNotifications` 用户通知实现。`NotificationCenter` 和系统锁屏通知是内部事件观察，不等于发送给用户的系统通知。

### 2.2 必须保留的现有边界

- 额度数据继续由现有刷新流程取得；通知不增加轮询频率，也不绕过 429 退避。
- 请求失败保留旧快照用于展示，但旧快照不能产生新的提醒。
- 不更改本地用量扫描、费用估算、历史补录、额度周期统计及凭据写回规则。
- 关闭服务后不为了通知继续查该服务；仅关闭菜单栏或悬浮窗展示不影响已启用服务的提醒。
- 主 Codex 关闭而某个导入账号启用时，该导入账号继续按现有独立刷新链路参与提醒。
- `产品需求.md` 当前仍有“一期不做额度告警通知”的历史条目；实施后应更新，不能据此否定新需求。

### 2.3 时效与运行条件

这是基于成功刷新结果的提醒，不是服务端实时事件。默认正常使用时约随 2 分钟刷新发现变化，但网络耗时、节流、请求失败等会增加延迟，不能承诺“两分钟内一定提醒”。

锁屏/息屏时默认间隔约 8 分钟；睡眠期间停止刷新，恢复后按现有调度补刷。退出 CCBar 后无法检测新的额度下降。系统已经接收的历史通知仍由系统管理，但不意味着 App 退出后还能监控额度。

不为可能发生的额度不足预先安排定时通知。重置时间只用于显示和周期判断，不能据此推算未来某时刻一定会低于阈值。

## 3. 产品行为

### 3.1 指标、阈值与显示精度

“额度不足”指官方窗口的剩余百分比，不指已使用的 Tokens 少，也不指消费金额低。

阈值判断使用未格式化的数值：`remainingPercent < thresholdPercent`。20% 阈值下，20.0% 不提醒，19.9% 提醒，0% 提醒。判断前检查原始 `usedPercent` 为有限值且在 0～100；无效值不依赖钳制结果触发通知。

通知百分比显示最多一位小数；若四舍五入会显示成阈值本身，则显示“低于 20%”这类明确文本。接近零但非零的值显示“低于 0.1%”，不要显示成“0%”或“已耗尽”。示例：

```text
Codex 额度不足
5 小时额度剩余 18% · 4h 37m 后重置
```

重置时间直接复用 `formatResetHint`，跟随「重置时间显示」设置（相对时长或 `MM-dd HH:mm 重置`），不另加「预计」前缀。

阈值范围限制为 5%～50%，第一版不提供 0% 或 100%，避免“低于 0% 永远不触发”和“几乎一直不足”的歧义。若以后需要“耗尽时提醒”，应单独定义 `remaining == 0` 的规则。

### 3.2 窗口规则

只检查能明确识别为 `.fiveHour`、`.weekly` 的窗口，不根据 primary/secondary 的位置猜测类型。账号仅返回其中一个窗口时，只检查实际存在的窗口。

未知窗口、缺失窗口、无限额度、无效数值跳过，不按 0% 处理，不自动换成另一种周期。两个已选窗口都缺失时保留设置，等待以后成功刷新；设置页可提示“当前账号暂无可用额度”。

同一份成功快照内：

- 两个窗口都首次符合条件，合并成一条通知，正文分别写明比例和各自重置时间。
- 一个窗口已提醒，另一个首次不足，只提醒新的窗口。
- 同一窗口已经提醒，从 18% 继续降到 5% 或 0%，第一版不再追加提醒。

不同账号分别发送，避免混淆额度归属。第一版不做跨账号摘要；同时启用很多账号时，首次满足条件可能收到多条通知，这一点应在评审时确认是否接受。

### 3.3 首次启用、设置变化与重启

| 场景 | 预期行为 |
|---|---|
| 安装或升级，未开启提醒 | 不申请权限、不发送额度通知 |
| 开启时已有低额度缓存 | 不使用缓存立即通知；等下一次成功刷新 |
| 首次新结果已低于阈值 | 若本周期没有提醒记录，提醒一次 |
| 额度从阈值之上降至阈值之下 | 提醒一次 |
| 同周期持续低额度 | 不重复 |
| 同周期小幅回升，再下降 | 不重复 |
| 正常重启或自动更新重启 | 读取提醒记录，避免重复 |
| 关闭后重新开启 | 保留记录，本周期已提醒的窗口不重发 |
| 阈值从 20% 提高至 30%，剩余 25% | 本周期未提醒则下一次成功刷新提醒；已提醒则不重发 |
| 阈值从 20% 降低至 10%，剩余 15% | 不提醒；保留本周期原有提醒记录 |
| 窗口关闭后重新开启 | 保留原记录，不靠切换开关重置去重 |
| 服务关闭后重新开启 | 新成功结果才参与判断；不重发同周期已提醒窗口 |
| 系统拒绝通知，随后用户允许 | 获取最新授权状态，下一次成功刷新符合条件时再判断，不补发旧事件 |
| 语言或声音偏好变化 | 不影响去重，不重发历史通知 |

设置变化只影响下一次真实成功观察，不主动发额外额度请求。用户需要立即检查时使用已有手动刷新。手动刷新和自动刷新遵循相同通知规则。

### 3.4 通知权限与 App 内开关

App 内开关表示用户意愿；系统授权表示系统是否允许发送。二者分开管理，不能通过反复关闭/打开开关不断请求系统授权。

首次主动开启时请求 `.alert`；若声音开关已开启，一并请求 `.sound`。首次启用声音时，根据系统当前状态申请所需能力；已被拒绝的权限引导去系统设置，不保证再次出现系统弹窗。不申请 badge、紧急通知或远程推送能力。

拒绝授权后保留 App 内“已开启”的意愿，在该行显示“系统通知未允许，请在系统设置中开启”。授权失败与额度刷新失败分开显示，不修改额度状态。

以下时机重新读取系统设置：进入通知设置区域、App 回到前台、实际提交提醒前。读取失败不发送、不消耗本周期机会，并显示可重试状态；不把失败当作授权成功。

权限读取只能判断已公开的授权与展示设置，不能据此保证通知横幅一定出现。专注模式、系统通知样式和其他系统策略仍可能影响展示。Apple 建议在用户理解用途的操作上下文中请求权限，见[通知权限文档](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications)。

## 4. 设置界面与通知文案

### 4.1 设置布局

位置：`设置 → 通用`，在“系统”和“诊断”之间新增“额度提醒”分组，继续使用项目现有原生控件与双语文案，不增加设置侧栏分类。

| 设置项 | 控件与默认值 | 行为 |
|---|---|---|
| Codex 额度提醒 | Switch，默认关 | 总开关；权限状态与错误放在本行附加文本 |
| 剩余低于 | Picker，默认 20% | 5%、10%……50%；总开关关闭时禁用 |
| 5 小时额度 | Toggle，默认开 | 选择是否检查对应窗口 |
| 周额度 | Toggle，默认开 | 同上；启用提醒期间至少保留一个窗口 |
| 播放声音 | Switch，默认关 | 只控制本功能；系统未允许声音时说明实际状态 |

分组只保留一条作用范围说明：“包含已启用的 Codex 账号，成功刷新后检查”。总开关关闭时保留子设置值，禁用依赖项。只有系统权限或本地存储异常需要用户行动时才显示附加状态，避免常驻冗余“正常”文案。

窗口选择采用阻止取消最后一项的方式，或在两项都取消时明确关闭总开关；推荐前者。实施时必须统一一种行为并测试键盘操作，不允许“开关显示已开但没有任何检查项”的隐性状态。

“打开系统通知设置”按钮使用当前系统可用的设置入口；若直达 CCBar 详情失败，退回系统通知页面，并显示“在通知列表中选择 CCBar”。深链必须在目标 macOS 版本验证，不能把未公开路径当作稳定协议。

### 4.2 文案与隐私

| 场景 | 中文建议 | English |
|---|---|---|
| 分组 | 额度提醒 | Quota alerts |
| 总开关 | Codex 额度提醒 | Codex quota alerts |
| 阈值 | 剩余低于 | Remaining below |
| 权限拒绝 | 系统通知未允许，请在系统设置中开启 | Notifications are not allowed. Enable them in System Settings. |
| 存储失败 | 无法保存提醒记录，提醒已暂停 | Could not save alert history. Alerts are paused. |
| 正常通知标题 | Codex 额度不足 | Codex quota is low |

通知内容使用提交时的应用语言。剩余比例、重置时间用现有格式化规范；无法得到有效未来重置时间时省略，不推测倒计时。

多账号名称遵循已有别名/账号显示规则。开启隐私模式时复用对应 UI 的账号键和 `PrivacyDisplay.account`，不写入邮箱、真实别名、原始账号 ID。不能新建另一套匿名编号，导致同一账号在设置页和通知中显示不同编号。

系统通知可能留在通知中心，关闭隐私模式时显示的身份信息也可能被系统保留。用户从非隐私切换到隐私模式时，移除本功能已有的已送达和待送达通知，再让未来通知按隐私规则生成；不重新发送、不清除去重。已经被用户看到或由系统同步展示的内容无法追溯收回，不能承诺彻底删除所有历史曝光。

`userInfo` 只保存通知类型、内部随机标识和必要的匿名关联键，不携带 token、邮箱、对话、项目或完整额度快照。

### 4.3 测试通知

已移除。系统不给最前台的 App 弹「临时」横幅，而点击测试按钮时 CCBar 的设置窗口正在前台，测试通知常常只进通知中心、不弹横幅，无法可靠验证通知链路；改为「持续」样式或提交前让出前台都未能解决，因此去掉该按钮。通知样式保持系统默认（临时）。

### 4.4 点击与前台展示

通知 delegate 在 App 启动早期安装，不能等到某个设置 View 出现时才安装。对象由应用长期持有。

正常提醒点击后，通过既有 `AppDelegate` 打开统计窗口的机制显示主窗口；冷启动时保存打开请求，待窗口 handler 安装后再消费。首次引导未完成时遵守既有引导优先级。

第一版不自动切换具体额度窗口、筛选账号或滚动定位。当前 `StatsView` 的视图选择和导航请求是内部状态，且现有 `StatsNavigationRequest.Target` 没有额度目标，精准跳转属于额外改动，不能当成已有能力。

App 在前台时也通过 `willPresent` 返回所需展示选项，避免只有后台才能看到提醒；声音仅在偏好与系统设置同时允许时启用。采用系统普通通知等级。展示选项参考 [Apple API](https://developer.apple.com/documentation/usernotifications/unnotificationpresentationoptions)。

## 5. 身份、周期与重复提醒

### 5.1 去重维度

逻辑记录键由“Provider + 实际账号身份 + 窗口类型”组成，每条记录保存当前周期和是否已经提交提醒。

阈值、语言、菜单栏位置、默认/导入槽位、账号别名均不进入去重身份，避免用户修改设置或切换默认账号后重复提醒。

不直接拿 `QuotaHistoryAccountKey` 当作通知身份：历史键包含默认/导入入口的语义，通知必须把同一实际账号的多个入口归到一起。同时不能直接使用日志短哈希作为唯一数据库键。

### 5.2 Codex 身份归一

1. 优先使用规范化的 `{account_id, user_id}` 组合，持久化用明确编码后计算的完整 SHA-256 摘要；不用字符串随意拼接，防止分隔符歧义。
2. 只有 account ID 时允许建立弱身份记录，保存 account 摘要；不使用邮箱、别名或 token 作为通知身份。
3. 当前代码在双方都有 user ID 时精确比较；任一方缺少 user ID 时回退 account ID。通知需要沿用已确认的镜像结果，同时避免把同一 workspace 下两个已知不同 user ID 合并。
4. 弱身份补全为强身份时，仅在无歧义时迁移/合并已有提醒状态；只要同周期任一记录已提醒，合并后仍视为已提醒。不得因身份补全生成第二次提醒。
5. 同一 account ID 同时出现多个不同的已知 user ID 时，不把它们合并。缺失 user ID 的入口暂停提醒，等身份完整；不能通过弱身份进行传递合并。
6. PAT 等身份需要接口回填时，先完成身份回填再判断。无法取得可用 account ID 时跳过本次提醒，只记脱敏诊断。

异步请求应携带开始时的账号上下文与运行时版本标记。发送前重新确认入口仍启用、账号未删除或切换、用户设置未关闭；过期请求不得向新账号发送旧结果。优先在通知接入处增加必要校验，不借此重构整个凭据系统。

同账号镜像函数不直接触发通知。默认账号 API 成功已经触发一次，导入镜像仅更新展示和历史。主账号关闭后的导入独立请求仍使用同一个通知身份，所以不会因入口变化重复提醒。

### 5.3 周期识别原则

`resetsAt` 不是完全稳定的周期 ID。当前解析器允许根据 `reset_after_seconds` 推导时间，网络时延可能造成偏移；当前快照还会在新结果缺时间时保留此前的未来重置时间。

通知观察值应区分“本次 API 原始窗口”与“供 UI 展示的合并窗口”：比例与周期识别使用本次原始数据；展示可以沿用仍有效的合并时间，但不能把继承的时间当作本次接口确认的新周期。

内部维护随机 `cycleID` 和固定的周期锚点。周期锚点不随每次小幅偏移累积移动，避免多轮缓慢漂移最终绕过去重。

建议规则：

| 情况 | 周期处理 |
|---|---|
| 首次有效观察 | 建立新周期，尚未提醒 |
| 新旧有效重置时间差不超过 30 分钟 | 同周期；该容差与现有额度历史规则量级一致，但使用独立常量和测试 |
| 已超过原周期结束时间，新时间明显晚于旧锚点且位于未来 | 确认新周期；下一次低额度可再提醒 |
| 原周期尚未结束，时间明显后移 | 先视为异常或提前重置候选，不凭单条时间变化立即清除去重 |
| 提前重置候选连续两次成功观察一致，且剩余比例从低位恢复到 `max(原提醒阈值, 当前阈值) + 5` 个百分点以上 | 可确认提前重置；两次观察需属于不同实际刷新，至少间隔 60 秒 |
| 时间突然前移、返回过去时间或窗口长度异常变化 | 不立即建立新周期；等待可确认的新数据，原提醒记录保留 |
| 新结果没有重置时间，旧周期结束时间仍在未来 | 保留原周期，不因缺字段解锁提醒 |
| 没有可靠重置时间，或旧时间过期后一直没有新时间 | 进入时间未知状态，使用下述保守恢复规则 |

“30 分钟”和“恢复 5 个百分点”是建议初值，应通过真实接口样本与确定性测试评审，不能把历史统计代码的私有方法直接搬来就认为通知规则正确。

### 5.4 缺少重置时间时的保守恢复

无可靠时间时允许首次低额度提醒，但不以自然日、整点或 App 重启人为划分新周期。

已经提醒的窗口，只有连续两次独立成功刷新确认剩余量达到 `max(原提醒阈值, 当前阈值) + 5` 个百分点，且两次相隔至少 60 秒，才重新允许未来一次低额度提醒。这是“已恢复后重新变低”的识别，不对用户宣称一定发生了官方周期重置。

修改阈值、权限变化、读取缓存、网络失败或同一结果重复投递均不能提供恢复证据。恢复确认之间出现新的低值，应清除候选恢复计数。

如果 App 整个恢复阶段都没有运行、再次启动时已低于阈值且接口仍没有重置时间，无法可靠区分旧周期和新周期。第一版优先避免重复，可能漏掉本次提醒；此限制应保留在技术说明和验收用例中，不以假定新周期掩盖不确定性。

## 6. 技术结构与事件流程

### 6.1 建议文件与职责

以下均为拟新增类型，当前仓库中尚不存在；最终文件名可随实施调整。

| 文件/类型 | 职责 |
|---|---|
| `Core/Notifications/QuotaAlertPolicy.swift` | 不依赖系统 API 的判断逻辑：数值有效性、窗口过滤、周期识别、候选提醒 |
| `Core/Notifications/QuotaAlertModels.swift` | 不可变观察值、账号身份、设置快照、周期记录、提交记录 |
| `Core/Notifications/QuotaNotificationService.swift` | 串行管理事件、去重、权限复查、提交与失败处理 |
| `Core/Notifications/SystemNotificationClient.swift` | 封装 `UNUserNotificationCenter`；可注入 fake；持有 delegate 或与独立 delegate 配合 |
| `Core/Storage/QuotaAlertStore.swift` | 独立提醒文件的加载、版本校验、原子写入与清理 |

按项目默认 MainActor 隔离设置，纯值和策略显式标注所需 `nonisolated` / `Sendable`；业务协调在 MainActor，文件操作交给独立串行存储对象。delegate 按 SDK 协议隔离要求实现，把需要 UI 的动作显式转交 MainActor。不要靠 `@unchecked Sendable` 消除编译错误。

不修改 `QuotaPersistenceCoordinator.Snapshot` 和额度文件版本。通知状态需要在发送之前确认写入完成，与目前额度缓存的批量异步写入语义不同，单独保存更容易控制失败边界。

### 6.2 观察值

观察值至少包含：

| 字段 | 用途 |
|---|---|
| Provider、规范账号身份与入口标记 | 去重及发送前检查入口是否仍有效 |
| observation ID、账号/设置运行时版本 | 去除重复事件，排除请求返回后的过时状态 |
| 本次成功时间、原始窗口数组 | 新鲜度、数值检查和周期判断 |
| 可用于显示的未来重置时间 | 只用于文案，明确是否继承自旧快照 |
| 本次所需账号显示上下文 | 最后提交前按最新语言与隐私偏好生成文本 |

不传 token，不从通知服务读取凭据文件，不读取用量聚合器来推算额度。

### 6.3 接入顺序

```text
现有调度 / 手动刷新 / 导入验证成功
  → 原有额度请求成功，完成账号身份回填
  → 原有快照、刷新状态、历史记录照常更新
  → 向通知服务传入本次原始成功观察值
  → 串行检查设置、身份、窗口、周期及去重状态
  → 查询系统权限，发送前再次核对当前开关与账号状态
  → 保存本次提交预留记录
  → 向系统提交即时本地通知
  → 保存系统接受/失败结果
```

接入 `storeCodex`、`storeImportedCodex` 对应的真实 API 成功路径，必要时显式传入原始快照和请求上下文。缓存恢复、失败处理、历史补记、镜像复制不产生观察事件。不要在 View 的 `onChange` 中根据展示快照发送，也不要在整轮刷新结束后扫描所有缓存补发。

通知错误不回滚成功额度、不修改 quota backoff、不让 UI 显示“额度刷新失败”。异步发送由通知服务持有任务并串行消费，不能每个调用点自行创建无序任务后依赖 actor 自动避免重入；每条记录必须有明确 in-flight/prepared 状态。

不增加新的周期性 Timer。发送失败只在后续新成功观察上重试；设置授权恢复也等待新观察。短期排队的结果若已超过 5 分钟，丢弃候选，等待更新数据，不补发历史额度警告。

### 6.4 系统通知请求

使用即时本地请求：`UNNotificationRequest(..., trigger: nil)`；API 依据见 [Apple `add` 文档](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/add(_:withcompletionhandler:))。

identifier 使用功能前缀、随机提交 ID；同一次明确失败后的重试保留同一 ID。同一通知包含的两个窗口必须作为一组预留和提交，成功后同时标记，失败时同时处理。系统 identifier 只辅助管理，业务去重仍由本地记录保证。

只移除带本功能前缀的通知，不调用无范围的“清除所有通知”。总开关关闭时取消尚未提交的业务任务、移除本功能待送达通知；已展示记录可随关闭一并清除，但本地去重保留。单个账号被删除后清理其通知，避免点击后误认账号仍存在。

## 7. 持久化、失败与退出

### 7.1 设置与文件

拟新增 `SettingsStore` 字段：

| 字段 | 默认值 |
|---|---|
| `codexQuotaAlertsEnabled` | `false` |
| `quotaAlertThresholdPercent` | `20` |
| `quotaAlertFiveHourEnabled` | `true` |
| `quotaAlertWeeklyEnabled` | `true` |
| `quotaAlertSoundEnabled` | `false` |

解码无效阈值时恢复为默认值，窗口配置缺失时使用默认值。开关、系统授权状态和业务去重分别管理；系统授权状态只查询，不作为永久偏好缓存。

建议文件：`~/Library/Application Support/CCBar/quota-alert-state.json`，初始 schema 版本 1。保存：完整匿名身份摘要、窗口类型、周期 ID、固定周期锚点、上次有效观察的必要状态、原提醒阈值、prepared/accepted 状态、请求 ID、提交时间、失败冷却时间。

不保存通知正文、邮箱、别名、token、项目或对话。哈希仅减少明文标识暴露，不宣称匿名数据绝对不可关联。文件与现有额度缓存分开，可独立禁用和排障。

### 7.2 写入与系统提交的一致性

系统通知提交和本地文件写入无法组成同一个原子事务，不能承诺崩溃、断电及文件损坏下绝对“不重复且不漏发”。第一版优先避免反复提醒，采用预留后提交：

1. 串行计算候选，在内存占用这些窗口的本周期机会。
2. 将 `prepared` 记录原子写入文件；失败则不提交系统通知，并显示提醒暂停原因。
3. 发送前再次核对总开关、窗口、账号和权限；已取消时撤销预留，正常发送时调用系统 API。
4. 系统明确接受后，将记录更新为 `accepted`。表示请求已被系统接受，不表示用户已看到或阅读。
5. 系统明确返回发送失败时撤销预留，保存重试冷却；至少 10 分钟后且有新的成功额度观察才重试。权限拒绝不靠定时重试，等权限改变。
6. 在 `prepared` 之后崩溃、无法确认系统是否接受时，重启后本周期按已占用处理，不盲目重发。若系统已送达列表包含相同 ID，可补记 accepted；列表中没有该 ID不能证明从未展示。

第 6 条可能在“预留已保存但还没发送”时漏掉一次提醒，是明确的故障取舍。系统已接受但结果落盘失败时，内存和磁盘预留都继续抑制重复，同时记录错误。

### 7.3 文件异常与恢复

- 首次安装尚无文件：建立空记录，正常支持首次低额度提醒。
- 已初始化记录文件意外丢失、损坏或版本高于当前支持：暂停自动发送，保留原文件，不直接当作首次安装清空。
- 用独立初始化标记区分首次使用与既有文件丢失；标记只在首次文件初始化成功后保存。权限、偏好和标记之间不假设跨存储事务，异常组合保守处理。
- 设置页仅在异常时显示“重建提醒记录”操作，并说明“当前低额度先记录为已提醒，恢复或重置后再提醒”，由用户主动执行。
- 重建时只处理下一次各账号的真实成功结果；当前低额度作为已占用基线，不立即批量提醒。重建前保留损坏文件备份，不覆盖额度缓存、账号或用量数据。
- 写入失败暂停发送，后续新成功观察可尝试恢复存储，间隔至少 10 分钟；恢复失败不持续写重复日志。

### 7.4 写盘频率与记录保留

只在周期建立/切换、提醒预留/结果、身份迁移、恢复确认和必要的重试状态变化时落盘；额度在低位继续变化且状态不变时不写。用于清理的最后见到时间最多每天合并保存一次。

每个身份与窗口仅保留当前周期及必要的在途提交信息，不建立通知历史数据库。账号临时隐藏、关闭或默认账号切走时保留去重。删除导入入口时若同身份仍被其他入口使用，不删除共享记录。

建议对连续 90 天未出现且不再属于任何当前入口的记录执行惰性清理；当前已保存但暂时关闭的账号不参与此类清理。清理后的重新添加视为新监控，可能出现一次新的低额度提醒。只在加载或已有写入中清理，不创建清理定时器。

### 7.5 正常退出与更新重启

通知服务必须纳入已有退出准备边界：停止接收新观察、取消尚未预留的候选，对已预留记录完成可控的本地保存。已经调用系统 API 的提交无法保证撤回，后续结果按同一事务 ID更新。

退出阶段不等待用户授权、不查询额度、不无限重试系统 API。未能确认发送结果时保留 prepared 状态，供下次启动保守去重。正常额度/用量保存流程仍使用原有超时和失败策略；通知无法保存时是否阻止退出，应在实施评审确认，推荐已有 prepared 安全落盘则不阻止退出，不能安全记录的任务则放弃发送。

## 8. 功耗、诊断与分发验证

### 8.1 性能预算

每个成功 Codex 快照最多检查两个窗口，CPU 成本与当前账号数线性相关。没有新额度请求、日志扫描、周期性唤醒或后台常驻进程。

系统授权查询集中在设置操作和存在实际候选时；普通额度刷新无候选时不查询系统通知中心。磁盘读取在初始化完成，正常判断使用内存记录。

### 8.2 诊断

沿用 `.quota` / `.app` / `.persistence` 分类即可，第一版不必为此重构日志系统。

默认只记录启用/禁用、请求被系统接受、提交失败、记录文件异常与恢复。详细日志可记录跳过原因：已提醒、窗口缺失、身份不完整、数据过期、账号已关闭、周期不确定。

账号标识必须走 `Redact`；不打印通知正文或 `userInfo`。诊断包只加入偏好、权限摘要、记录数、文件版本/大小、最近一次脱敏错误，不复制整份提醒记录文件。

### 8.3 系统与分发

当前工程最低 macOS 版本为 14.0，使用系统 `UserNotifications` 具备平台基础。按本地通知方案不需要 APNs 服务器或远程推送凭据，不改变现有日常分发方式。

但当前项目采用 ad-hoc 分发，不能把 Xcode 中能发送等同于正式安装包能正常授权和接收通知。实施阶段需验证实际 App bundle 的通知注册、权限保留、前后台展示、重启与升级后的行为。本文没有运行这些验证，也不预先保证结果。

若出现与 bundle 身份或签名有关的问题，先记录具体系统版本、安装方式和错误，再限定修复范围；不在本方案中预先改为付费签名、公证或替换用户 `/Applications/CCBar.app`。

## 11. 评审时需要确认的产品取舍

本文已给出一套可实施的默认建议。实施前重点确认以下几项，不需要先确定每个内部类型名：

1. 第一版仅做 Codex，还是同时要求 Claude 等服务；建议仅 Codex，避免不同额度语义扩大范围。
2. 同一阈值覆盖 5 小时和周额度，还是分别设置；建议第一版共用 20%，保留窗口开关。
3. 是否包含所有已启用的导入账号；建议包含，接受首次可能多条提醒。
4. 同周期只提醒一次，0% 不额外再提醒；建议保持此规则，后续需要再增加明确的“耗尽提醒”。
5. 点击仅打开主窗口，暂不定位具体额度；建议保持，以减少导航改动。
6. 崩溃不确定时优先少打扰，接受极少数漏提醒；建议采用预留后提交，并在技术说明中保留此限制。

用户于 2026-10-09 明确要求按本文实现，已采用上述推荐取舍；实际偏差和未验收内容见头部实施记录。
