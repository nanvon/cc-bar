# cc-bar 性能与功耗等价优化方案

> 状态：批次 A/B/C 已实现并通过 Xcode 测试（含新增的开关矩阵、Keychain 写入次数、增量矩阵与等价对照测试）；批次 D（统计页查询快照）已于 2026-09-24 实现，等价对照测试见 `CCBarTests/StatsOverviewModelTests.swift`
> 目标：降低常驻 CPU、磁盘写入、子进程唤醒与网络活动，同时保持现有产品需求、数据口径、刷新语义和异常恢复能力不变。  
> 范围：本方案基于当前 Swift / SwiftUI 实现做代码级优化，不把“少做功能”当成性能优化。

---

## 1. 结论：需要优化，但应分阶段做

有必要优化，原因不是代码存在持续空转或明显死循环，而是 cc-bar 是一个常驻菜单栏 App。实施前，以下小成本会长期重复并随数据规模增长：

- 额度刷新默认每 2 分钟唤醒一次；未启用的 Provider 当前仍可能读取凭据、访问网络。
- 用量扫描默认每 5 分钟递归枚举全部历史会话文件；即使没有新增日志，也要遍历目录和读取文件属性。
- 一轮额度刷新会多次同步编码并原子重写 JSON 文件。
- 统计概览的一次 SwiftUI 渲染会多次过滤、复制和聚合相同的用量桶。
- Antigravity 每轮会重复执行进程发现，并可能为多个本地请求反复建立短生命周期 URLSession。

这些问题在日志少、账号少、主窗口关闭时未必明显，但会影响长期常驻功耗，并随着历史会话、导入账号和周期记录增加而放大。

不建议一次重构全部调度、扫描和存储。首轮只实施可证明业务等价、容易回退的优化；涉及事件监听、刷新协议语义或历史保留策略的改动留到实测证明有必要后再做。

## 2. 不可改变的功能与数据边界

以下内容是本方案的硬约束。任何优化若破坏其中一项，应视为失败并回退。

### 2.1 额度与刷新

- Codex、Claude Code、Antigravity 的额度来源、解析规则和 UI 展示不变。
- 用户在“设置 → 账号”关闭某个主 Provider 后，该 Provider 不显示，也不查询其额度 API；重新开启后按现有调度恢复刷新。
- 导入的 Codex 账号仍以 `visibleInPopover` 决定是否独立刷新，不能因为主 Codex 被关闭而误停所有导入账号。
- 同一身份的主 Codex 与导入账号仍只请求一次额度，并保持镜像状态与必要的 token 同步。
- 周期刷新继续遵守成功后至少 60 秒、429 后 10 分钟退避；手动刷新仍绕过 60 秒限制，但不能绕过 429 退避。
- 网络失败继续保留已有快照，不清空可展示数据。
- 外部工具切换 Codex / Claude 账号后，cc-bar 仍需在下一次相关刷新时重读凭据并发现身份变化。
- Claude 凭据只读（不刷新、不回写）、进程内去重重读、以及凭据过期时的 CLI 兜底链路不变。

### 2.2 本地用量统计

- Codex、Claude Code、Pi、OpenCode 四个数据源继续完整采集。
- “设置 → 统计服务”只是展示筛选：关闭某个统计服务后仍必须扫描和入库，重新开启时历史数据立即可见。
- mtime + byte offset 的增量语义、文件截断恢复、seen ID 去重上限和价格指纹失效规则不变。
- 日聚合、对话聚合、周期聚合必须继续使用同一代 `generationID`；rollup 先写、scan-state watermark 最后写的提交顺序不变。
- 不降低短生命周期日志、sidechain / subagent、归档会话、Pi fork / clone 或 OpenCode WAL 数据的覆盖率。
- Token、费用、请求数、Standard / Fast、cache read / cache creation 的统计口径不变。
- 缺价刷新、价格目录安全边界和必要的全量重算不变。

### 2.3 UI 与常驻体验

- 菜单栏、Popover、悬浮窗、统计页和设置页的可见结果不变。
- Popover 可见时的秒级刷新文案、重置时间更新和刷新动画不因后台优化失效。
- 主窗口打开时，图表筛选、排序、悬浮反馈和对话详情结果不变。
- App 冷启动继续先恢复本地缓存，不被网络或全量扫描阻塞。

## 3. 当前热点与必要性判断

| 热点 | 当前行为 | 长期影响 | 是否建议做 |
|---|---|---|---|
| 未启用 Provider 轮询 | `refreshQuotas()` 先无条件读取 Codex / Claude 凭据，再尝试请求 | 网络唤醒；Claude Keychain 路径会启动 `security` 子进程 | 必做 |
| JSONL 空扫描 | 每轮递归枚举全部历史 JSONL，随后逐文件取 mtime / size | 会话越多，空扫描成本越高 | 必做 |
| 额度 JSON 写放大 | Codex/Claude 成功各写 cache+history+cycle 三文件，Antigravity 只写 cache，导入账号写 cache+history；多账号继续叠加 | 原子写和编码频繁，且当前调用位于 MainActor | 必做 |
| 统计概览重复聚合 | body 内多个计算属性重复 snapshot / filter / reduce | 主窗口交互和图表选择时增加 CPU | 建议做 |
| 镜像账号 token 同步 | 每轮镜像刷新都可能 `SecItemUpdate` 相同内容 | 不必要的 Keychain I/O | 必做 |
| Antigravity 重复发现 | 同一轮先 `detectAvailability()`，`fetch()` 内再 `ps`，随后 `lsof` | 周期性子进程唤醒 | 建议做 |
| 秒级 TimelineView | Popover / 对话页可见时更新相对时间 | 仅前台可见时生效，绝对成本有限 | 暂缓 |
| 服务状态固定刷新 | 即使状态圆点关闭，也每 5 分钟请求两次 | 有功耗，但当前文档明确要求随时打开即有数据 | 不在首轮改 |

## 4. 第一阶段：低风险、业务等价优化

第一阶段应优先落地。每项可以独立提交、独立验证和独立回退。

### 4.1 按 Provider 开关裁剪额度刷新链路

#### 当前链路

```text
Scheduler.quotaLoop
  → AppState.refreshQuotas
    → loadCodex
    → loadClaude
    → loadCodexQuota
    → loadClaudeQuota
    → loadAntigravityQuota
    → loadAllImportedCodexQuotas
```

当前只有 Antigravity 在 `loadAntigravityQuota` 内检查 `showAntigravity`。Codex 和 Claude 即使在账号设置中关闭，仍会读取凭据并进入刷新前置流程。

#### 优化方案

在 `refreshQuotas(reason:)` 的最外层按当前设置构造本轮刷新计划：

- Codex 主 Provider 启用：执行 `loadCodex()` 和 `loadCodexQuota()`。
- Claude 启用：执行 `loadClaude()` 和 `loadClaudeQuota()`。
- Antigravity 启用：执行现有 Antigravity 链路。
- 导入 Codex 账号：始终按导入账号自身的 `visibleInPopover` 独立判断，不能直接继承主 Codex 开关。
- 镜像优化只在主 Codex 启用、且本轮已经重读主账号身份时生效。主 Codex 关闭时，即使内存中还留有上一次主账号身份，可见导入账号也必须使用自己的 Keychain 凭据独立刷新，不能复制可能过期的主账号快照。

建议把计划表达成清晰的局部布尔值或小型值类型，不要把开关判断散落到各 Client 内。

#### 保持不变

- 开关关闭时保留内存和磁盘中的最后快照；只是不再主动请求。
- 重新开启后不立即清缓存；按当前设置变更链路决定是否立即补刷，至少下一次 Scheduler 周期必须恢复。
- 手动刷新只刷新已启用主 Provider 与可见导入账号。

#### 风险与验证

最大风险是“主 Codex 关闭 + 同身份导入账号可见”的镜像关系。需要覆盖：

1. 主 Codex 开、导入镜像开：只请求一次。
2. 主 Codex 关、导入镜像开：导入账号仍能独立刷新，不能因镜像短路而只复制旧主快照。
3. 主 Codex 关、导入非镜像开：正常独立刷新。
4. 全部关闭：启动时仍允许为账号检测 / 设置页读取一次凭据；完成 bootstrap 后的周期刷新和手动刷新不访问三个 Provider 的额度 API，也不再启动 Claude Keychain `security` 读取。

### 4.2 镜像导入账号 token 只在变化时写 Keychain

#### 当前链路

```text
loadImportedCodexQuota
  → importedCodexAccountMirrorsPrimary == true
    → mirrorPrimaryCodexQuota
    → syncPrimaryCodexTokensToImported
      → ImportedCodexStore.saveTokens
        → SecItemUpdate
```

#### 优化方案

把 token 同步从“每轮导入账号额度刷新”改为“主账号 token 可能变化的事件”：

- App 启动完成、导入账号新增 / 重载、主 Codex 身份变化、Codex token 实际续期后，调用一次镜像同步。
- 普通 `wham/usage` 成功但 token 三件套未变化时，不触发镜像同步。
- 同步时调用 `ImportedCodexStore.loadTokens(accountId:)`，与即将同步的 `ImportedCodexTokens` 做完整 `Equatable` 比较。
- 完全相同则直接返回；只有 access / refresh / id token 任一变化时才写 Keychain。

可在 `AppState` 内维护 `(accountID → token fingerprint)` 的进程内缓存，进一步避免同一次事件链重复读取：

- 首次需要同步时读取一次 Keychain 并建立 fingerprint。
- 主账号 token 变化或导入账号增删时更新 / 失效。
- fingerprint 只能用于避免写入，不能替代 Keychain 作为真实持久化来源。
- fingerprint 不落盘、不写日志，也不能包含可逆 token 文本。

首轮至少做到“事件触发 + 读后比较”。进程内 fingerprint 属于可选的小优化，不应成为正确性的依赖。

#### 保持不变

- 主账号刷新 token 后，导入镜像仍必须拿到新 token。
- Keychain 保存格式、service、account 和 accessible 属性不变。

### 4.3 JSONL 扫描先过滤变化文件，再创建解析任务

#### 当前问题

`JSONLDirectoryEnumerator.files()` 只返回 URL。各 Scanner 随后再次读取每个文件的属性；Codex 还会把未变化文件分批创建成 Task，进入任务后才检查 mtime / size。

即使没有任何新日志，仍会发生：

1. 递归枚举全部目录。
2. 对全部 JSONL 再取一次 attributes / resource values。
3. Codex 对全部文件创建并调度短任务。
4. Claude / Pi 重建全量 seeds 和项目候选。

#### 优化方案

新增轻量文件描述，例如：

```swift
struct JSONLFileDescriptor: Sendable {
    let url: URL
    let path: String
    let modificationTime: TimeInterval
    let size: UInt64
}
```

枚举阶段通过 `includingPropertiesForKeys` 已请求的资源值一次性构造 descriptor，Scanner 直接复用：

- `JSONLDirectoryEnumerator` 返回 descriptor，而不是仅返回 URL。
- 对比 previous watermark，在创建解析任务前拆成 `unchanged` 与 `changed`。
- Codex 只对 changed 文件创建最多 4 路并发任务；unchanged 文件直接从已有 `ScanFileState` 补 seed。
- Claude / Pi 同样复用 descriptor，避免第二次属性读取。
- 文件删除检测仍基于本轮完整 alive key 集合，不能因为只处理 changed 文件而丢失。
- Codex sessions 与 archived_sessions 的重复 ID 选择仍按 mtime 取最新，语义不变。

#### 首轮不做的事

- 不改成只扫描“最近 N 天”。归档文件和迟到写入仍必须被发现。
- 不取消完整目录枚举。仅靠 mtime 目录剪枝可能漏掉跨目录移动或外部恢复文件，需要更完整设计。
- 不改变最大并发数 4，避免并发和 I/O 行为同时变化导致难以归因。
- 不引入 FSEvents；先拿到“先过滤、少建任务”的确定收益。

#### 已知的时序差异

属性取值从“解析前逐文件读取”改为“枚举阶段一次性读取”后，若文件在枚举之后、解析之前被写入，本轮会按旧属性判为 unchanged 而跳过，新内容最多延迟到下一轮扫描（默认 5 分钟）入账；旧实现窗口更小。由于 offset 单调前进且全局 seen 去重兜底，两版最终收敛一致，不丢不重，但“单轮内立即可见”语义存在细微差异。

#### 验收指标

同一份 fixture / 真实日志快照下，新旧结果必须逐项一致：

- 四个 Scanner 的 entries 数量和每条字段。
- conversation seeds、标题、项目、subtask 标记。
- 新的 ScanState、offset、seen IDs。
- 日 / 对话 / 周期 rollup 和最终 totals。

性能对照至少包含：冷启动全量扫描、无变化空扫描、单个活跃 Codex 文件追加、Claude sidechain 追加、Pi fork / clone、OpenCode 新消息。

### 4.4 合并额度持久化，编码与写盘移出 MainActor

#### 当前问题

各 Provider 成功后会立即执行（按 Provider 差异，并非每个都写三个文件）：

- Codex / Claude：更新并保存 `quota-cache.json`、`quota-history-today.json`、`quota-cycle-history.json`。
- Antigravity：只保存 `quota-cache.json`（不写 history、不写 cycles）。
- 导入 Codex 账号：保存 `quota-cache.json` 与 `quota-history-today.json`（不写 cycles）；镜像路径仅写 cache。

Codex 与 Claude 顺序刷新时会分别重写包含全部 Provider 的 cache；导入账号也逐个重写。JSON 编码与原子写由 `@MainActor AppState` 同步调用。

#### 优化方案

把“内存状态更新”和“磁盘提交”分开：

1. 本轮每个 Provider 成功时，立即更新 AppState 内存和 UI 状态。
2. `recordQuotaHistory` / `recordQuotaCycles` 仍同步计算下一份值，确保周期边界、账号段和重建触发判断不变。
3. 只标记本轮哪些 payload 变脏，不立即逐个写盘。
4. `refreshQuotas` 所有 Provider 完成后，对不可变 snapshot 做一次批量异步持久化。
5. 编码与写盘放到 utility task；回到 MainActor 只处理成功 / 失败结果和必要的状态提示。
6. 所有 quota 持久化请求通过单一 coordinator 串行提交；后发的新版本不得被先发但较晚完成的旧 snapshot 覆盖。

建议抽出 `QuotaPersistenceSnapshot`：

```swift
struct QuotaPersistenceSnapshot: Sendable {
    let cache: QuotaCachePayload?
    let history: QuotaHistoryPayload?
    let cycles: QuotaCyclePayload?
}
```

其中 `nil` 表示该文件本轮没有变化。三个文件彼此不是一套 generation 事务，不需要引入复杂日志或数据库；但同一文件一轮只写一次。

`Scheduler` 周期刷新与用户手动刷新可能在时间上交错。持久化 coordinator 应为每份 snapshot 分配单调递增的进程内 sequence：

- writer 严格按 sequence 串行执行，或在旧任务尚未开始时合并为最新 snapshot。
- 已开始写入的任务可以完成，但后续必须继续写最新 snapshot。
- 禁止多个 detached task 无协调地同时原子写同一路径；原子写只能保证单次文件完整，不能防止旧内容最后覆盖新内容。
- coordinator 不持有 AppState；输入必须是不可变、`Sendable` 的值快照。

#### 失败语义

- 磁盘写失败不能回滚已经成功获取的内存快照和 UI。
- 保留现有日志，同时记录具体哪个文件失败。
- 下一次成功刷新仍会再次生成完整 payload 并尝试覆盖。
- 周期分区变化触发的 `rebuildCycleUsageForRecentChanges()` 必须依据内存 next payload 判断，不能等待写盘成功才触发，否则当前运行期统计会落后。
- App 退出时不应依赖任意长 debounce；因此优先采用“一轮刷新末尾立即批量写”，而不是延迟数秒的写合并。

#### 不建议的首轮方案

- 不把 quota 数据迁移到 SQLite。
- 不减少有效采样频率。`lastSampleAt` 对周期数据质量有意义，是否节流要单独定义产品口径。
- 不随意裁剪 `quota-cycle-history.json`；虽然 UI 只展示当前周期，既有周期边界仍参与去重、账号分段和当前周期重建。

### 4.5 统计概览建立统一查询快照

#### 当前问题

`StatsView` 在一个 body 周期内多次调用：

- `aggregator.snapshot()`。
- 按范围、服务可见性和侧栏筛选过滤。
- 分别计算总量、各服务 totals、speed breakdown、daily samples、model rows。
- 图表选择变化时，`selectedSample` 和 `barOpacity` 还会重复生成 / 搜索 `dailySamples`。

这与对话页此前已解决的“render path 重复聚合”属于同类问题。

#### 优化方案

在数据层增加 `UsageQueryRequest` / `UsageQueryResult`，按以下 key 缓存：

- aggregator revision。
- range / previous range / chart context range。
- serviceFilter。
- visible usage apps。

一次查询返回：

- 当前范围 filtered buckets 或直接返回聚合结果。
- current / previous totals。
- per-app totals 与 speed breakdown。
- daily samples。
- per-app model rows。
- selectedDay 到 selectedSample 的索引数据。

`UsageAggregator` 需要像 `ConversationAggregator` 一样只在真实数据变化时递增 revision；空扫描不能使缓存失效。

SwiftUI View 只消费一个 query snapshot。图表选中日期属于 UI 临时状态，不应触发底层数据重新聚合；从已经生成的 daily samples 中做一次 O(1) 字典查找或一次小数组查找即可。

#### 保持不变

- 所有范围边界、上一周期 delta、14 天上下文图表、可见服务分母与排序规则不变。
- 不持久化 UI 查询缓存；App 重启后由现有 rollup 恢复即可。
- 不引入 SQLite。

## 5. 第二阶段：需要更强验证后再实施

### 5.1 Antigravity 单轮复用发现结果

可以把 `processInfos + listeningPorts` 的结果封装为一次 discovery，供 availability 与 fetch 共同使用，避免同轮重复 `ps`。PID / 端口缓存只能短期使用，并需在连接失败、PID 不存在或进程命令变化时立即失效。

建议首步只做“单轮复用”，不跨轮长期缓存，功能风险较低。跨轮缓存必须防 PID 复用和 App / IDE 重启，实施价值应由 Instruments 证明。

### 5.2 复用 Antigravity URLSession

当前每个 loopback request 都创建 ephemeral URLSession 和 delegate。可以按一次 fetch 生命周期复用一个 session；不建议直接做全局长生命周期 session，避免端口、自签名证书和进程重启状态残留。

### 5.3 自适应相对时间刷新

对话页的“更新于 N 秒前”超过 60 秒后仍按秒刷新。可以按年龄调整：

- 0～59 秒：每秒更新。
- 1～59 分钟：每分钟更新。
- 1 小时以上：每 5 分钟或仅在视图状态变化时更新。

Popover 秒级文案只在可见时调度且体验价值明确，优先级低于后台 I/O。

### 5.4 FSEvents 驱动的脏源扫描

FSEvents 理论上能显著减少无变化时的全树枚举，但不能直接替换周期扫描：事件可能合并、丢失，App 睡眠 / 退出期间也可能错过细粒度信息。

若第一阶段后空扫描仍是主要能耗来源，可采用混合模式：

- FSEvents 只负责把 Claude / Codex / Pi 数据源标记为 dirty。
- dirty 时按现有增量扫描。
- App 启动、系统唤醒后和低频保底周期仍执行完整对账。
- OpenCode 保持基于 SQLite watermark 的扫描，不套 JSONL watcher。
- watcher 失败时自动回退现有周期扫描。

该方案必须有睡眠唤醒、目录移动、归档、文件恢复和日志截断测试后才能落地。

---

## 6. 明确不做的“伪优化”

以下措施虽然可能让 CPU 数字下降，但会改变需求或数据准确性，本方案禁止：

- 统计服务在设置中隐藏后停止扫描其日志。
- 只扫描最近若干天，忽略旧会话迟到追加或归档恢复。
- 降低 seen ID 去重覆盖，或移除 Claude sidechain / Pi clone 去重。
- 把 4 路 Scanner 改成只扫当前正在使用的 Agent。
- 为了减少写盘而放弃 scan-state 最后提交或 generationID 一致性。
- 价格表变化后不再全量重算。
- 遇到网络失败清空旧快照，以减少状态分支。
- 绕过 429 退避，或用更高并发换刷新速度。
- 删除周期边界记录、对话历史或缓存写入明细来缩小文件。
- 未经协议验证把 Antigravity 的 `forceRefresh: true` 改为 false。
- 仅凭一次 `ps`、Activity Monitor 或 Instruments 短采样宣称长期功耗已改善。

## 8. 验证方案

验证必须分成“结果等价”和“性能 / 功耗改善”两条线。只看编译成功不能证明功能不受影响；只看功能正常也不能证明能耗下降。

### 8.1 静态与自动化验证

每个批次至少执行：

- `git diff --check`。
- 针对受影响文件的 Swift 静态审阅。
- 相关 XCTest；涉及项目文件或跨模块类型变化时，再征得同意运行 Debug build。

建议新增测试：

- Provider 开关与导入账号组合矩阵。
- 镜像 token 相同 / access 变化 / refresh 变化时的写入次数。
- JSONL descriptor 与原枚举结果一致。
- changed / unchanged / truncated / deleted 文件的 ScanState 等价。
- quota persistence 一轮写入次数与失败恢复。
- Stats query snapshot 与旧 helper 输出逐项一致。

### 8.2 真实数据等价对照

在不修改用户原始日志的前提下，对同一份只读数据做旧版 / 新版对照，输出稳定的摘要 hash 或逐桶 diff：

- `usage-rollup`：按 day / app / model / speed 比较四项 token、费用、请求数、未定价标记。
- `conversation-rollup`：比较 info 与所有 conversation bucket。
- `cycle-usage-rollup`：比较 cycleID、account segment、Tokens、费用。
- ScanState：比较各文件 offset / mtime、seen IDs 和 OpenCode watermark。
- UI 查询：比较 today、yesterday、week、month、year、7d、30d、all、custom，及四个服务筛选。

### 8.3 性能与功耗 A/B

建议用相同日志快照、相同设置、相同前台状态分别跑旧版和新版，每个场景重复多次：

| 场景 | 观察项 |
|---|---|
| App 静置、主窗口关闭、无新日志 | 10～30 分钟 CPU、wakeups、子进程次数、网络请求、磁盘写入 |
| 默认 2m quota / 5m scan | 每个周期的 CPU time、wall time、写盘次数 |
| 全部主 Provider 关闭，且 bootstrap 已完成 | 后续周期 / 手动刷新中 Provider API 请求应为 0；Claude `security` 子进程应为 0 |
| 仅一个 JSONL 文件追加 | 扫描文件数、解析行数、结果延迟 |
| 冷启动全量重建 | 总耗时、峰值内存、结果一致性；不得为了空扫描优化显著劣化全量重建 |
| 主窗口概览图表拖动 | 主线程 CPU、SwiftUI body / 查询调用次数、交互流畅度 |
| Antigravity 开 / 关 | `ps` / `lsof` 次数、本地请求次数、额度结果 |

工具建议：

- Instruments 的 Energy Log / Time Profiler / System Trace。
- `os_signpost` 或现有日志增加扫描、持久化和 Provider 刷新的结构化耗时与计数。
- `fs_usage` 只用于辅助确认文件访问形状，不能单独作为能耗结论。
- URLProtocol / Client 注入统计请求次数；不要依赖肉眼看控制台日志。

### 8.4 首轮验收标准

功能标准：

- 所有基线数据逐项一致；允许变化的只有时间戳类运行元数据，且必须列明。
- 开关、退避、手动刷新、账号切换、缓存保留和错误恢复符合第 2 节。
- 无新增数据丢失、重复计费或周期归属变化。

性能标准：

- 全部主 Provider 关闭时，完成 bootstrap 后的周期 / 手动刷新不再产生对应额度网络请求和 Claude Keychain 子进程。
- 无变化扫描不再为全部 Codex 文件创建解析任务，不再二次读取全部 JSONL 属性。
- 一轮正常额度刷新中，`quota-cache` / `quota-history` / `quota-cycle` 各最多提交一次。
- 统计页同一 revision + query 下只做一次完整聚合，图表选择不重新遍历全部 usage buckets。
- A/B 结果至少在重复测量中稳定改善；若差异小于噪声，则不以“已优化功耗”作为发布结论。

## 9. 风险控制与回退

- 每批次保持单一主题，不同时修改统计口径、缓存 schema 和 UI。
- 首轮尽量不升级持久化 schema；若结构不变，只调整何时写、在哪个 executor 写。
- 扫描改造保留旧扫描实现或基准 harness，直到真实数据对照通过。
- 为关键优化增加 feature flag 仅用于开发 A/B；正式发布前移除或固定为验证通过的路径，避免长期双实现。
- 发现任一 rollup、周期边界、账号镜像或退避行为不一致时，优先回退对应批次，不用补偿逻辑掩盖差异。
- 发布说明必须区分“静态等价验证”“自动测试”“Debug build”“Instruments A/B”“用户真实运行验收”，不能混称全部验证完成。

## 10. 预期结果

完成本次批次 A/B 后，预期会发生：

- 完成 bootstrap 后，关闭的额度 Provider 不再由周期 / 手动额度刷新产生对应额度请求或凭据读取。
- 无新增日志时仍保留完整对账，但减少重复属性读取和短任务调度。
- 镜像账号不再反复写相同 Keychain 内容。
- Antigravity 单轮额度刷新只执行一次进程发现。

若后续 Instruments 数据证明仍有必要，再由批次 C/D 处理额度持久化写放大与统计页重复聚合；这两项不属于本次已实施结果。

不会发生：

- 不会减少数据源、历史范围、刷新准确性或统计字段。
- 不会改变额度 API、价格规则、周期算法、退避策略或缓存恢复协议。
- 不会因为某服务在统计页隐藏就停止采集。
- 不会用更长刷新间隔掩盖实现成本。

因此，这是一组值得实施的“等价优化”。推荐先完成批次 A 和 B，再用 Instruments 结果决定是否继续批次 C、D 及 FSEvents 等第二阶段方案。
