# GitHub Release 更新说明

每次发布都在此目录新增一份与 tag 同名的文件，例如发布 `v1.0.40` 时创建 `release-notes/v1.0.40.md`。该文件和版本号一起提交；GitHub Actions 会校验它存在且非空，然后把**全文原样**作为 Release 正文。

Release 标题不做定制，沿用 GitHub 默认的 tag 名（如 `v1.0.40`）。

这不是按时间持续追加的 `CHANGELOG.md`。每份文件只描述一个版本，方便发布前审阅、发布后追溯和重跑 CI。

同一份内容也供应用内更新窗口使用。发布工作流会按版本从新到旧聚合本版及已有版本说明，生成 `release-notes.md`，并与 ZIP 更新包和 `appcast.xml` 一起签名上传。HTML 注释不会出现在应用内日志；源文件及 GitHub Release 正文仍保持原样。聚合文件是生成产物，不提交到此目录，也不用维护第二份日志。

## 读者和场景

主要读者是在应用内更新窗口里决定要不要升级的用户。窗口会把当前版本之后的每一版依次列出，每版前面自动加上 `## 版本号`，跳过几个版本的用户会一次看到好几版。所以每一版都要让人读完第一句就知道这版改了什么，条目扫一眼就能找到和自己有关的。

应用内窗口只渲染 `- ` 列表、普通段落和行内粗体，不显示图片，空行会被忽略。

## 文件格式

一句话，加一组条目，不分组：

```
现在可以在应用内直接更新了。

- 在「检查更新…」里查看更新内容，下载后自动安装并重启；从旧版升级到本版需手动安装一次
- 在「设置 → 服务与账号」拖动服务可调整顺序，菜单栏、悬浮窗和统计页同步
- Codex 子代理的用量并入所属对话，统计页不再出现没有标题的行
- 模型价格更新到 10 月官方价，新增 Haiku 5.5、Gemini 3.6 等
```

**第一句**

- 说出本版最主要的变化，写用户能得到的结果，30 字以内，以句号结尾。
- 本版有几项同等分量的改动时，第一句概括它们共同的方向，不要用顿号并列。

**条目**

- 每条一件事，40 字以内，结尾不加句号；一般 1～6 条，超过 6 条说明拆得太细或混进了不该写的内容。
- 按对用户的影响从大到小排列。
- 需要用户操作、升级后默认值或行为会变、已有数据会被迁移的，写进相关条目或放在第一条，写清变成了什么、想改回去在哪里改。
- 新功能和位置变化写出入口，用界面上的原名，如「设置 → 服务与账号」「检查更新…」。
- 修复以「修复」开头，写用户遇到的现象，如「修复选了自定义日期后，统计页的对比区间没有跟着变化」。
- 只涉及某个服务的，在条目里点明服务名，如「Codex 子代理的用量……」。
- 条目补充细节，不原样复述第一句。

**特殊情况**

- 只有一处改动时，只写第一句，不列条目。
- 没有用户可感知的改动时，只写：`本版为内部维护更新，功能与上一版一致。` 不要虚构稳定性、性能或功能收益。

**不使用**：分类组头（新增 / 修复 / 优化等）、`#` 标题、加粗小标题、图片、emoji、徽章、下载表格、安装说明等每版重复的固定段落。

## 撰写流程

1. **盘点**：读上一个 `v*` tag 到当前 HEAD 的提交正文，必要时看 diff，重点看界面文案（`tr("…")`）和文档的改动。逐项记下：改了什么、用户在哪里看到、改之前怎样、改之后怎样、对应哪个提交。这一步只是草稿，不写进文件。
2. **取舍**：去掉用户感知不到的改动——重构、测试、文档、CI、构建脚本、文案微调，以及说不出"用户看到了什么不同"的布局调整。同一件事的多个提交合并成一条。
3. **排序**：找出本版最主要的变化写成第一句，其余按影响排成条目。
4. **写作**：名称以界面上显示的中文为准（`tr()` 第二个参数），不用代码里的类名、字段名和内部概念。
5. **自检**：每一句都过下面的问题，有一项不通过就重写或删掉。

## 自检问题

- 不看代码的用户能看懂吗？有没有缓存、快照、前缀、口径、归属、Provider 这类内部说法（界面上本来就这么叫的除外）？
- 用户知道在哪里用到、怎么触发吗？
- 写的是用户得到的结果，还是开发做了什么工作？
- 能对应到具体的提交吗？有没有夸大或没做的事？
- 删掉这条，用户会少知道什么吗？不会就删。
- 第一句能单独说明这版改了什么吗？

## 改写对照

以下是过去版本里的写法和改写后的写法：

| 原写法 | 问题 | 改写 |
|---|---|---|
| Codex 模型渠道前缀丢失，影响提供商归属 | 内部说法，用户看不懂 | 修复在 Codex 中经 Command Code 等渠道调用的模型，用量记到了错误的提供商下 |
| 统计页对比区间与自定义日期联动不正确 | 读起来像在报告一个现存问题 | 修复选了自定义日期后，统计页的对比区间没有跟着变化 |
| 额度周期在补记缓存时可能归错账号或被误判为不完整 | 写了实现过程 | 修复额度页的历史周期偶尔记到错误的 Codex 账号下 |
| 主窗口标题栏、长名称与 Codex 副账号套餐的显示 | 只说改了哪里，没说变成什么样 | 说不出用户能看到的变化，删掉 |
| 精简设置页、统计页和引导页的文案，凭据说明与实际行为一致 | 用户感知不到 | 删掉 |
| 概览新增用量构成与高消耗对话，单日图展示近 30 天 | 一条里并列几件无关的事 | 拆成两条，分别写清入口和效果 |
| 悬浮窗支持右键菜单 | 没说菜单里有什么 | 悬浮窗右键可隐藏悬浮窗或打开设置 |

## 示例

改动较多的版本：

```
「服务与账号」合并为一页，刷新失败的服务会直接标出来。

- 刷新失败时，点该行行尾按钮可查看失败原因
- 每个服务在同一行开关，并选择是否显示在菜单栏和悬浮窗
- 其他 Codex 账号移到 Codex 下方，重置次数和删除在 ⋯ 菜单里
```

带有行为变化的版本：

```
统计排行可以按 Tokens 或费用排序了。

- 统计排行默认按 Tokens 排序，可在「设置 → 外观与显示 → 统计 → 排行口径」改回按费用
- 隐私模式改为默认关闭，自动检查更新改为默认开启；之前手动设置过的保持不变
- 悬浮窗右键可隐藏悬浮窗或打开设置
- 修复选了自定义日期后，统计页的对比区间没有跟着变化
```

只有一处改动的版本：

```
「设置 → 服务与账号」中的「更多 Codex 账号」默认折叠，标题显示已导入的账号数。
```
