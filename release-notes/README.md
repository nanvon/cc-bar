# GitHub Release 更新说明

每次发布都在此目录新增一份与 tag 同名的文件，例如发布 `v1.0.40` 时创建 `release-notes/v1.0.40.md`。该文件和版本号一起提交；GitHub Actions 会校验它存在且非空，然后把**全文原样**作为 Release 正文。

Release 标题不做定制，沿用 GitHub 默认的 tag 名（如 `v1.0.40`）。

这不是按时间持续追加的 `CHANGELOG.md`。每份文件只描述一个版本，方便发布前审阅、发布后追溯和重跑 CI。

同一份内容也供应用内更新窗口使用。发布工作流会按版本从新到旧聚合本版及已有版本说明，生成 `release-notes.md`，并与 ZIP 更新包和 `appcast.xml` 一起签名上传。HTML 注释不会出现在应用内日志；源文件及 GitHub Release 正文仍保持原样。聚合文件是生成产物，不提交到此目录，也不用维护第二份日志。

## 文件格式

分类作为组头出现一次，组内每条一行。组头用加粗，不用 `#` 标题——Release 页里标题字号过大，与正文不成比例。

```
**新增**
- 菜单栏支持显示 Cursor 的额度和用量
- 悬浮窗支持自定义透明度

**修复**
- 公司网络或代理环境下检查更新经常失败
- 切换主题后统计图表配色不刷新

**优化**
- Cursor 额度界面减少冗余提示，关键数值更集中
```

- 分类固定为「注意 / 新增 / 修复 / 优化」，按此顺序排列，本版没有的分类不写。
- 只有一个分类、只有一条时，同样保留组头，格式统一。
- 「注意」放最前面，用于需要用户操作、有兼容性影响或已有数据可能变化的情况。
- 本版有重磅新功能时，可在第一个组头上方加一句话概括本版价值，只一句。
- 某条一句话说不清时，紧跟其后另起一段补一到两句，不要在条目里塞长句。
- 界面有明显变化时，可在最后附一张本版真实截图；普通修复不配图。

没有用户可感知的改动时，不写分类，如实说明，也不要虚构稳定性、性能或功能收益：

```
本版为内部维护更新，功能与上一版一致。
```

不写安装说明、下载指引这类每版重复的固定段落，Release 页的产物列表已经能看到 DMG 和 zip。

## 撰写规则

- 基于上一个 `v*` tag 至当前版本的真实代码、提交和文档撰写；必要时以 diff 为准，不只复述 commit message。
- 每条写用户看到的结果，控制在 30 字左右；不写 commit hash、文件名、内部模块、重构过程、CI、测试或版本号变更。
- 同一类改动合并成一条，不要把一次改动按文件或提交拆成多条；正常小版本 1～5 条，超过 8 条说明拆得太细。
- 条目结尾不加句号；独立成段的句子加句号。
